# Caerbannog BDD tests

Plain-language scenarios that describe what Caerbannog must do, written as a product owner and test engineer.
They follow `docs/spec.md` and the screens in `docs/ux/`. Each `.feature` file covers one area of the spec.

Status: the scenarios are written first (TDD/BDD). Step definitions do not exist yet.
The runner (Cucumber-JVM with Kotlin steps) is a proposal to confirm in the M1 spike; the files are plain
Gherkin and will work with any Gherkin runner.

## Tags

| Tag | Meaning |
| --- | --- |
| `@M1` to `@M7` | Milestone that must make the scenario pass (see the milestones table in `docs/spec.md`) |
| `@gate-M2`, `@gate-M3`, `@gate-M4`, `@gate-M5`, `@gate-M7`, `@gate-M8` | Scenario that is the gate check for that milestone |
| `@smoke` | Smallest set that proves the feature works; run on every commit |
| `@fake-broker` | Runs against in-memory fakes of the stream and management clients; no broker needed |
| `@broker` | Needs a real RabbitMQ 4.x broker with TLS and plain listeners (Testcontainers, needs Docker) |

| `@broker-3x` | M8 only: needs a real RabbitMQ 3.13 broker (`rabbitmq:3.13-management`) and, for the gate, a 4.x broker on the same container network. 3.x is a read-only migration source; no other feature is tested on 3.x. Run with `@broker` in the separate broker job |
| `@m8-01` | The scenarios of task M8-01 (definitions model and parser); the suite `RunMigrate3xDefinitionsAcceptanceTest` selects `16_migrate_from_3x.feature` and filters `@m8-01 and @fake-broker`. Later M8 tasks add their own `@m8-NN` tag the same way |
| `@m8-03` | The scenarios of task M8-03 (compatibility analyzer) in `16` and `18`; the suite `RunMigrate3xAnalyzerAcceptanceTest` selects both files and filters `@m8-03 and @fake-broker`. | `@migrate-3x`, `@shovel`, `@access`, `@mcp` | M8 scenarios (`16`, `17`); `@shovel` marks forwarding with a broker-side dynamic Shovel; `@mcp` an MCP tool scenario |
| `@negative` | Checks a refusal, an error or a safety rule |
| `@security`, `@safety` | Protects a security or data-flow rule from the spec (TLS on by default and never a silent fallback, never reading queue messages, browsing never changes offsets) |
| `@needs-spike` | Depends on something the M1 spike must confirm (API fields, keychain, search by name for streams) |
| `@needs-decision` | The product behavior is not decided yet; the scenario states the proposed behavior |
| `@needs-M2` | Step definitions exist and compile but are deliberately left pending (`PendingException`) because the scenario needs a later milestone's feature (in `02` the two topology-screen text scenarios and "Listing streams does not need the configure permission", which need the M2 topology screen, task M2-08; the browse half of that pair is `@needs-M3`); excluded from the default Cucumber run |
| `@needs-M4-02` | Filter and scan scenarios in `07_payload_viewer_filter.feature` deferred to task M4-02 (stream scanning engine); excluded from `RunPayloadViewerAcceptanceTest` |
| `@needs-08d` | Scenario of the topology feature (`09`) that belongs to task M2-08d (the bindings graph); no step definitions yet; excluded from `RunTopologyAcceptanceTest`. The tag goes when 08d builds the steps (`@needs-08c` is gone: 08c built its steps) |
| `@needs-M3` | Like `@needs-M2`, for a scenario that needs a later milestone (M3 message browser): steps are written when that feature exists, the scenario is excluded from the default Cucumber run; the part that can be asserted earlier is covered by a unit test (in `04` "Jump from a consumer to its offset in the browser": the core state carries the offset to browse from) |
| `@needs-M1-07` | Retired: the permission-state UI (task `M1-07`) is built and its five scenarios in `02` (sidebar pill, edit panel banner wording, asserted in core through `permissionPill` / `permissionBanner`) run in the normal `@fake-broker` set; the tag is no longer used on any scenario |
| `@needs-M1-06` | Retired: declared permissions on the profile (task `M1-06`) are built and their two scenarios in `02` run in the normal `@fake-broker` set; the tag is no longer used on any scenario |

The real-keychain JUnit tests (`KeyringSecretStoreTest`, `KeyringRoundTripSpikeTest` in `data-rabbit`) are outside the Gherkin tags: they carry the JUnit tag `keychain` and run only via `./gradlew :data-rabbit:keychainTest` (`task test:keychain`), never in `./gradlew test`.

Suggested runs: `@smoke` on every commit, `@fake-broker` in the normal build, `@broker` in a separate CI job.

## Vocabulary used in steps

- "the connection" is a saved profile; each profile is its own environment.
- "locked" and "unlocked" describe topology changes, decided by the configure permission.
- "offset" numbers start at 0; "page size" is the number of messages per page.
- "the broker" is the fake in `@fake-broker` scenarios and a real RabbitMQ in `@broker` scenarios.
