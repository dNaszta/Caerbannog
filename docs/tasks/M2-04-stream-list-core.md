## Goal
`core` has a stream list view model that, for the held connection, loads every stream (all pages of the management queue list, streams only), shows rows with counts, first and last offset, publishers and consumers as display strings, filters, sorts and pages them in memory, refreshes on a timer under the D3 rules, and reacts to the connection state. No Compose code. All `@fake-broker` scenarios of `03` that do not need super streams pass.

## Why
Spec "Stream list" and the D3, D4, D5, D8, D9 and UI1 decisions in `docs/tasks/README.md`; scenarios in `tests/bdd/features/03_stream_list.feature`. M2-05 draws this state; M2-06 and M2-07 extend it.

## Design notes
- Modules: view model, `RefreshPolicy`, paging strategy, `AppSettings`, row model and `Retention` rule in `core` (commonMain, no JVM types: clock and ticker are interfaces, tests use `kotlinx-coroutines-test` virtual time). `data-rabbit` gets only `publisherCounts` and F1. `ui` is untouched.
- State flow: one `StateFlow<StreamListState>` (same pattern as `ConnectionsViewModel`; no inheritance of StateFlow). The view model needs a coroutine scope for the timer: it is passed in and owned by the composition root; `close()` cancels it. Collect `ActiveConnection.state` for connection changes (a collector, not a synchronous session observer: the rule "observers must not call ActiveConnection" in the KDoc of `observe` and `ActiveConnection` stays; F1 of M2-01b is already written there, only verify it is still present).
- Accessor (decided): `class StreamSource(val catalog: StreamCatalog, val offsets: StreamOffsets, val vhost...)` built by `ActiveConnection` per held connection, wrapping them with a "still current" check (same token as the connect that opened it). `ActiveConnection.source: StreamSource?`, non-null only in Connected. Vhost comes from the profile, as the catalog calls already take it.
- Load token: every load gets an increasing token; results apply only if the token is current and the link is the same connection. This is the "latest started wins" rule applied to data calls.
- Paging: no use of the broker `name` filter in M2-04 (the app holds all streams and filters in memory), which also answers case-sensitivity for now (the in-memory filter is a case-insensitive substring; the broker-side case question stays open for the global search task). If a vhost is so big that the list is too heavy, see Open points.
- Calls per tick (to be measured and recorded in Status, with the real broker and the fake): list calls = `ceil(queues/500)`; publishers = 1 (FULL only) else 0; first offset = one `queryStreamStats` per visible row on the current page (at most page size, parallelism limit already in the gateway). Default page size for M2-04 is a constant (50, a view setting, may change in M2-05 UX); the scenario passes 5.
- Fakes: `FakeStreamCatalog`, `FakeStreamOffsets`, `FakeConnectionGateway` (and the small helpers they need) move to a new JVM module `core-testing` (Kotlin JVM, `main` source set, depends on `core`; consumers: `core` jvmTest, `acceptance-tests`, later `ui` and `data-rabbit` tests via `testImplementation(project(":core-testing"))`). Reason: three consumers (core tests, acceptance, ui in M2-05) and the current `srcDir` copy trick in `acceptance-tests/build.gradle.kts` does not reach `ui`. Keep the package `dev.caerbannog.core.connections.fakes` to keep the diff mechanical. Remove the srcDir hack and the "same file in core jvmTest and through an extra srcDir" KDoc lines. Risk: core's own tests depending on a module that depends on core; Gradle accepts it (no task cycle) but check `./gradlew test` and `verifyTestDiscovery`. If it cannot work, fall back to a `java-test-fixtures`-like setup and tell the architect; do not copy files. The module is test-only: it must not be reached from `desktopApp` runtime or the installer.
- Do the move as the first commit, with no behaviour change, so its diff can be reviewed alone. Plan: (A) core-testing move; (B) D9 retention rule, `RefreshPolicy`, `AppSettings` fake; (C) accessor and paging strategy and `publisherCounts`; (D) view model and the scenarios; (E) F1.
- Safety: no code path reads, gets or purges queue messages; list calls and `queryStreamStats` only; TLS paths untouched.

## Connection states and refresh (decisions of 2026-11-04)
- The view model follows `ActiveConnection.state` (Disconnected, Connecting, Connected, Failed(reason)) next to the catalog: no rows and the state "Not connected" while Disconnected; a loading state while Connecting; rows when Connected; the failure reason and a Retry action when Failed.
- Lost connection (D2, PROPOSED, NOT confirmed by the product owner; build it as a flagged default and keep it easy to change): a catalog call failing with unreachable or timeout makes the connection Failed("Connection lost"); the list keeps its last rows, marked stale, with a banner and Retry; no automatic reconnect. Retry = connect again, then load.
- D3 refresh: see "Refresh policy (D3)" below; it no longer blocks this task.
- Scenarios (`@fake-broker`): `13_connection_lifecycle.feature` (core level) and `03` ones listed above.

## Refresh policy (D3, decided 2026-11-04, default 5 s)
Product owner: the refresh interval is set in seconds, in the app bar connection control (see `M2-05-stream-list-screen.md`), next to a manual Refresh and "Updated N s ago". Allowed values Off, 5, 10, 30, 60 seconds; scope per app. The default interval is decided too: 5 seconds (below). Nothing here blocks M2-03 or M2-04.
- Behaviour: load on Connect; manual "Refresh now" at any time; with an interval set, a timer reloads the current page every N seconds while Connected and the Streams screen is shown. "Updated N s ago" counts from the last successful load. A refresh that is still running is never overlapped by the next tick (skip the tick); a failed refresh keeps the old rows, marks them stale and does not stop the timer; a lost connection stops it (D2). Changing the page, filter or sort reloads at once and restarts the timer.
- DEFAULT (DECIDED by the product owner 2026-11-04: 5 seconds; "try with that, after we can change"; one constant `DEFAULT_REFRESH = 5 s`). The architect had recommended Off (statistics lag up to about 5 s; each tick costs one list call plus one `queryStreamStats` per visible row), so treat this as a trial: record in the task Status how it behaves against a real broker (calls per tick) so the owner can change it. Consequences: (a) polling starts on connect, not on the first user action, so the first tick is 5 s after the first successful load; (b) it interacts with "latest started check wins" (`ConnectionSession`, M2-01): a tick is a data call on the held connection, not a permission check, so it must never write to the session, but a Disconnect, Connect to another profile or a re-check that supersedes the connection must cancel the running tick and the timer, and a late result of a superseded tick is dropped (test with a fake catalog that completes after the switch); (c) a tick that is still running makes the next tick skip, as before; (d) the "stream list is not shown" case must not poll. Allowed values (decided): Off, 5, 10, 30, 60 s; the type is a closed set (enum or sealed), not a free number.
- Scope (decided): per app, not per profile. Why: it is a viewing preference, and a per-profile value would have needed a field in the persisted profile JSON. Persistence (in M2-05, not here): a new `settings.json` next to the profiles file with one key `streamListRefreshSeconds` (0 = Off, missing = Off), read and written by a small `AppSettings` interface in `core` with a JSON file implementation in `data-rabbit` (same pattern as the profile repository: atomic write, tolerant read, unknown keys ignored; an unknown number such as 7 reads as the default).
- In this task: a `RefreshPolicy` in `core` (interval value, injectable clock and ticker so tests use virtual time, no sleeps), the "updated N s ago" derivation, and the scenarios "Refresh updates the statistics" and the two interval scenarios in `03` (no longer `@needs-decision`: they use 30 s and Off, both allowed values) and the scenario "The refresh interval is 5 seconds on a fresh install" (renamed from "... is off ...", no longer `@needs-decision`). Define the `AppSettings` interface in `core` with an in-memory fake; the value is in memory only here; the real file is M2-05.

## Inputs from part 2 (rulings of 2026-11-04, from the M2-03 part 2 tests-first report)
- Accessor (decided here, not in M2-03): `ActiveConnection` needs a way to reach the held connection's `catalog` and `offsets`. Write the test first. Recommendation: the view model depends on a small `StreamSource` (or the catalog and offsets passed in) that `ActiveConnection` exposes only while Connected and that is null otherwise, never a `HeldConnection` handed out whole (it is `AutoCloseable`; the UI must not be able to close it). The accessor must not let a superseded connection's catalog be used after a switch (see the refresh section on latest started wins).
- Paging over all queues: the management API ignores `type=stream` and pages over ALL queues, so a page can hold fewer streams than `page_size`, or none, and `StreamPage` counts (`itemCount`, `totalCount`) count queues, not streams. The scenario "Long lists are paged" (`03`, "streams 1 to 5 of 12") therefore cannot be served from the broker's numbers alone. Recommendation: the catalog reader (view model or a small paging strategy in core) fetches pages of 500 queues until `page == pageCount`, keeps only streams, and pages the streams in memory; the display total is the stream count. Cost: one call per 500 queues per refresh, so on a vhost with thousands of queues a 5 s tick is expensive; note the number of calls per tick in the Status and keep the tick skip rule. Alternative if the cost is too high: pass the name filter to the broker (it is applied over all queues, which is correct) and show the broker's numbers with the caveat; that changes the scenario wording and needs the architect. The developer decides nothing alone here: report the measured call counts first.
- Publishers column (D8 DECIDED (a), product owner 2026-11-04): the column shows "unavailable" unless `Capabilities.visibility` is `FULL` (user has `monitoring` or `administrator`); only then the count is shown, never a partial number for `OWN_CONNECTIONS_ONLY` or `NONE`. Source for FULL: one `GET /api/stream/publishers/{vhost}` call per vhost per refresh, grouped by stream (not one call per row); needs a new catalog method (for example `publisherCounts(vhost)`) with a test first. Add or adjust the `03` scenario "Stream statistics" with an example for the `management`-only user showing "unavailable". If the plugin is missing the column also reads "unavailable".
- Fakes: the third consumer of the fakes is the `ui` tests; at the start of this task create the `core-testing` module (or decide against it with the reason) and move `FakeStreamCatalog`, `FakeStreamOffsets`, `FakeConnectionGateway` there.
- `NotFound` on a row (stream deleted) means: reload the list; show nothing else.
- Retention display (D9, decided by the product owner 2026-11-04, coordinator's reading, confirm wording): a pure function in `core` (for example `Retention.displayMaxAge()`) turns the broker text into the compact natural form: the largest whole unit in RabbitMQ's notation Y, M, D, h, m, s. `604800s` gives `7D`, `7D` stays `7D`, `3600s` gives `1h`, `90m` stays `90m`, `5400s` gives `90m`, `86401s` stays `86401s`; no decimals. Input forms to test: the unit text (`7D`, `1h`) and the seconds text (`604800s`). Edge cases: `0s` (shows `0s`), a bad or unknown text (shown unchanged, never an exception), a missing value (blank, same as no retention), a very large number (no overflow). Month and year follow RabbitMQ's own meaning of M and Y (30-day month and 365-day year are NOT assumed: only convert a seconds value into D, h, m, s; M and Y appear only when the broker sent them). The data layer stays a pass-through (`ManagementJsonTest` already pins `604800s`). Copy yields the displayed text (see "Copyable values" below).
- Copyable values (product owner 2026-11-04, "it should be copyable"; coordinator assumed it covers all detail and list values, confirm): the view state exposes display strings so that what is shown is what is copied; M2-05 makes the cells selectable. A test checks that the copied text of retention is `7D` for a `604800s` input.
