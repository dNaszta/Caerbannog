## Slice 2: the policy step

### Scope
In (`core.planner`, all pure):
- `PolicyTarget` (enum with `wire` and `label`): `QUORUM_QUEUES("quorum_queues", "Quorum queues")`, `CLASSIC_QUEUES("classic_queues", "Classic queues")`, `QUEUES("queues", "Queues")`, `STREAMS("streams", "Streams")`, `EXCHANGES("exchanges", "Exchanges")`, `ALL("all", "All")`. `wire` is the `applyTo` text the format already has; an `applyTo` that is none of these six (a hand-written file) makes the policy read-only (A2).
- `PolicyValueKind` (sealed): `WholeNumber(min: Long)`, `Duration` (digits and a unit), `Text`, `Choice(values: List<ChoiceValue(wire, label)>)`.
- `PolicyKeyCatalog`: DATA, one `PolicyKeyEntry(key, label, kind, targets: Set<PolicyTarget>, evidence)` per offered key. `evidence` is a reference the test resolves (a `PolicyKeyMatrix.effect` row, a `PolicyKeyMatrix.wrongTypeRows` id, or a live row of this task); a test fails when it does not resolve, and a key without evidence is not in the catalog. API the tests pin: `PolicyKeyCatalog.entries`, `PolicyKeyCatalog.offeredFor(target): List<PolicyKeyEntry>`, `PolicyKeyCatalog.entry(key): PolicyKeyEntry?`.
- The label table ("D" = decided by the owner on 2026-11-16, item 2 of `M9-00c` and the scenarios; "P" = proposed here, see decision 3 below):

| Key | Label | Value | Offered for | Wording |
| --- | --- | --- | --- | --- |
| `max-length` | Maximum number of messages | whole number, 0 or more | quorum, classic | D |
| `max-length-bytes` | Keep at most (bytes) | whole number, 0 or more | quorum, classic, streams, queues, all | D |
| `overflow` | When the queue is full | choice: `drop-head` "drop oldest" (P), `reject-publish` "refuse new" (D), `reject-publish-dlx` "refuse new and dead-letter" (P) | quorum, classic | D / P |
| `message-ttl` | Message time to live (ms) | whole number, 0 or more | quorum, classic | P |
| `expires` | Delete the queue when unused for (ms) | whole number, 1 or more (`0` is a 400, S-F1c) | quorum, classic | P |
| `dead-letter-exchange` | Dead-letter exchange | text | quorum, classic | D |
| `dead-letter-routing-key` | Dead-letter routing key | text | quorum, classic | P |
| `dead-letter-strategy` | Dead-letter strategy | choice: `at-least-once` "at least once" (P), the only measured value | quorum | P |
| `delivery-limit` | Delivery limit | whole number, 0 or more | quorum | D |
| `queue-leader-locator` | Leader locator | choice: `balanced` "balanced" (P), the only measured value | quorum, classic, streams, queues, all | D |
| `target-group-size` | Target number of members | whole number, 1 or more (`0` is a 400) | quorum | P |
| `max-age` | Keep messages for | duration: digits and a unit | streams | D |
| `stream-max-segment-size-bytes` | Segment size (bytes) | whole number, 1 or more | streams | P |
| `alternate-exchange` | Alternate exchange | text | quorum, classic, streams, queues, all, exchanges | D |

  Boundaries the spike did not try (`max-length 0`, `message-ttl 0`, `delivery-limit 0`, `max-length-bytes 0`): the form lets them through and the apply reports the broker's answer; the catalog lists only the boundaries S-F1c measured. Choice values: only those with evidence; an unmeasured locator or strategy is not offered (adding one is an entry plus a live row).
- The whole-policy rule (S-F1b): `offeredFor(target)` for `QUORUM_QUEUES`, `CLASSIC_QUEUES` and `STREAMS` equals `PolicyKeyMatrix.effect` of that type (the catalog test compares both ways: nothing offered that the matrix says is ignored; nothing in the matrix left out without a named reason in the test). `QUEUES` and `ALL` offer the intersection of the three (`max-length-bytes`, `queue-leader-locator`, `alternate-exchange`; whether `apply-to: queues` includes streams is NOT measured, so this is the conservative reading and stays so). `EXCHANGES` offers `alternate-exchange` only. The form shows `Only settings that every kind of queue honours are offered here` for `QUEUES` and `ALL` (decided).
- `PolicyForm(name: String, pattern: String, target: PolicyTarget = ALL, priority: String = "0", settings: List<PolicySetting> = emptyList()) : StepForm`; `PolicySetting(key: String, value: String)` holds the value as typed text (as `HeaderMatch` does), with `fun typedValue(): ArgumentValue?` (`Whole(Long)` for whole numbers, `Text` for the rest; never a number for `max-age`: S-F1c, a JSON number is a 500 with an empty body, pinned by a unit test). `fun priorityValue(): Int?` (a whole number, negative allowed, within `Int`). `withTarget(target)` drops the settings the new target does not offer (a row for a key that is no longer offered is removed, not kept hidden). `actions(ctx)` gives one `DeclarePolicy(name, pattern, definition, vhost, applyTo = target.wire, priority)`; `DeclareOperatorPolicy` is never built.
- Problems (fixed messages, one per field, in this order: name, pattern, settings, each row, priority): `Give the policy a name`, `Enter a pattern`, `Add at least one setting`, `Enter a whole number` (a number value or the priority), `Enter a number and a unit, for example 7D` (a duration; wording proposed, decision 2). The name goes through `FormChecks.nameProblem` (empty, `.`/`..`, the parser round trip) but NOT `BrokerNameRules.reservedPrefix`: a policy named `amq.x` is accepted by the broker (201, S-H) and must not be blocked; a unit test pins it. A pattern is never refused for its content, only for being empty (an unevaluable pattern is a hint, below). A key used in two rows is refused with `Each setting can be added once` (proposed, decision 2).
- Duration syntax of `max-age`: digits, then one unit. Units accepted: `Y`, `D`, `s` (measured: `1Y`, `1000s`, `7D` are 201; `7d`, `7`, `abc` are 400), and `M`, `h`, `m` only if the live row of this task answers 201 (the constant `MaxAgeUnits.measured` gets exactly those; the refusal text does not list units, so nothing else changes).
- `PatternMatches.of(pattern: String, names: Collection<String>): PatternMatchResult` over the existing `PolicyPatternMatcher` (package `core.migrate3x`, `internal`: same module, no new dependency): `Matches(List<String>)` or `Unevaluable`. Hostile patterns cannot hang (the M8-03 cases are the test).
- Match line under the pattern (never blocks, O11): the scenario wording is `matches "orders" in this plan and "orders-archive" on "uat-eu"` (the sentence is built in `PlannerTexts` from the two lists; nothing matched: `Matches no name yet`; the broker part is dropped when the broker was not read). A pattern the matcher cannot evaluate: `The app cannot tell which names this pattern matches`. At most 10 names per source, then `and N more`.
- `ExactPattern.of(names: List<String>): String`: `^name$` for one name and `^(a|b)$` for several; every character of `\.^$*+?()[]{}|` is escaped with a backslash (the app's matcher supports groups and alternation, checked). Tests: the pattern of one and of two names matches exactly those names with the app's matcher (`ExactPatternTest`); `M9-09` reuses it and adds `nameOf`.
- `StepForms.formOf`: a `DeclarePolicy` whose `applyTo` is one of the six wires AND whose keys are all in the catalog for that target AND whose values have the type the catalog says opens in `PolicyForm`; anything else is a read-only step (A2). `DeclareOperatorPolicy` and `DeletePolicy` stay read-only.
- Retention block of `StreamForm`: new fields `keepFor: String = ""`, `keepAtMost: String = ""`, `sameRetentionForResponse: Boolean = true` (the tick is drawn only while the response stream is ticked; off, the policy covers the stream alone). Both fields empty: NO policy step is added (scenario). Otherwise `actions` appends `DeclarePolicy(name = PlanNaming.derived(streamName, RETENTION, style), pattern = ExactPattern.of(names), applyTo = streams, priority = 0, definition = {max-age?, max-length-bytes?})` AFTER all stream and route steps; `names` is the stream, plus the response stream when the pair and the tick are on. `FormContext` already carries the naming style, so `actions(ctx)` gets no new parameter. A stream step of an opened file that carries settings stays read-only (existing rule); an opened stream without settings opens with the retention fields empty (the policy step beside it is its own step and is never merged back in).
- `PlanValidation.problems(plan, known: KnownTopology = KnownTopology.None)` (the default keeps every caller). Notes (non-blocking, shown on EACH policy step involved):
  - two policies of the plan that WOULD BIND to one queue or stream the plan declares: the pattern matches the name, `applyTo` suits the type (a declared stream is `streams`, a queue its type; `queues` and `all` suit all), and EVERY key of the definition is honoured by that type (`PolicyKeyMatrix.effect`, through the catalog). Decided text: `The policies orders-dlx and orders-limits both match orders. RabbitMQ applies only one policy to a queue: put the settings into one policy.` Different and equal priorities get the same note. Two policies that cannot bind to one queue get none. A plan queue whose type string is not `quorum` or `classic` counts as unknown and the note is skipped for it.
  - a policy that matches a queue of the plan but has no effect on it (a key the type ignores): `This policy has no effect on orders: a quorum queue ignores Keep messages for, and RabbitMQ then applies none of the policy's settings.` (decided; the type words are `quorum queue`, `classic queue`, `stream`; the first ignored key in catalog order is named by its label, or by the broker key when the catalog has no label).
  - the two notes from `M9-00b` (at least once without `reject-publish`; a dead-letter exchange that is nowhere, from `known.exchanges` and the plan's earlier exchange steps, never a new call): code them as `PlannerTexts` constants once the owner answers (decision 1); until then their scenarios keep `@needs-decision` and stay out of the run.
- Check notes (`PlanCheck`, notes under a policy step, never a blocker): a policy step that would bind to a queue on which the broker already applies another policy gets one of three decided sentences (full texts in the scenarios): the step has the higher priority `The broker applies the policy limits to orders. Only one policy applies to a queue: this one would take its place.`; the lower `... which has a higher priority. Only one policy applies to a queue: this one would not apply.`; the same `... at the same priority. Only one of the two will apply, and RabbitMQ does not say which.` An operator policy on the broker is not warned about (S-F2b). Nothing is merged, changed or removed.
  - What the check reads: (1) the names list of the plan's virtual host through the existing `KnownTopologyReader`, READ AGAIN when the check starts and only when the plan holds a policy step (the copy in the planner state is as old as the screen; a plan without a policy step makes exactly the requests it makes today; the graph takes the fresh value too; a user-started read, not polling); (2) one GET per DISTINCT policy name found on a matching queue, through the new read port below, at most `MAX_POLICY_READS = 20` per check (a pattern matching thousands of queues names few policies; beyond the cap the note is left out, never guessed). A policy that cannot be read (404, 403, no answer) gives no note and changes no step's finding.

## Design notes
- Layers: `core.planner` pure and testable with fakes; `data-rabbit` knows RabbitMQ (the two parsers and the policy reader); `ui` has no network code; `desktopApp` wires `BrokerPolicyReader` next to `DeclareCheck`.
- The catalog is data, not code paths: adding a key is one entry plus its evidence. Values are `ArgumentValue` (numbers stay numbers; `max-age` is text).
- The pattern text is untrusted once files are opened: only the app's own matcher reads it, never `kotlin.text.Regex`.
- `PlannerTexts` holds every sentence as a constant or a small builder; names echoed from a file go through `echoableName` (existing rule).
- Notes are derived, not stored: `PlanValidation.problems(plan, known)` runs on every change like today; the check notes are part of `StepCheck.notes`.
- M9-14b rule: anything that reads a policy row or a queue declaration reads `definitionComplete` and `typedArgumentsComplete`.
- Merge risk: `StepForms.kt`, `PlannerTexts.kt`, `PlanCheck.kt` and `PlanValidation.kt` are touched; do not run in parallel with another task that edits them (`M9-09`, `M9-12`, `M9-13` come after).
