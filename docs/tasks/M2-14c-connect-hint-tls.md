# Connect hint "the broker may not use TLS"

Milestone: M2    Depends on: M2-14 (14a and 14b, the TLS switch and the Check hint)    Size: S/M (grew with the D7 fix, ruling R1)

## Goal
When Connect with "Use TLS" on fails because the broker does not answer the TLS handshake (it is probably a plain broker), the failed state says so and names the switch: "The broker did not answer the TLS handshake. It may not use TLS; turn off 'Use TLS' in this connection's settings if that is intended." A wrong CA keeps its own reason ("The certificate was not trusted"). The hint only tells: the app never turns TLS off, never retries without TLS, and sends nothing in clear text.

## Why
Spec D9a (TLS default, per-profile switch, plain only behind that switch, no credential before the user has chosen). M2-14 ruled in P4 (`docs/tasks/M2-14-plain-connections.md`, "Step 2 architect rulings") that the Check result gets the hint but Connect does not, because Connect and Check map every `SSLException` the same way and a wrong CA and a plain broker cannot be told apart. The user's own first trial was exactly this: a local broker, TLS on, an unhelpful failure. The follow-up row "M2-14c" is in the M2-14 brief ("Follow-ups") and says: measure first, then ask the user. The user has now asked for it.

## Design notes
- Data: classify in one place (the `SSLException` catch in `ManagementHttp`), returning a typed reply, e.g. split `ManagementReply.TlsRefused` into `CertificateRejected` and `NoTlsAnswer`, instead of the gateway inspecting exceptions. The problem it removes: one catch-all that makes two different user actions (set the CA, turn TLS off) look the same. Not a boolean flag on the reply.
- Core: `ConnectionFailureReason` gets one constant (suggested name `NO_TLS_ANSWER`); the Check text and the Connect reason share the sentence. `LinkState.Failed.reason` stays plain text without secrets; the UI shows it as today, no new screen state.
- The wrong-CA text and the "certificate" naming stay for the certificate case. With TLS off no reason mentions TLS (the gateway cannot raise either TLS reason then).
- Faked in `@fake-broker` scenarios: `FakeConnectionGateway` and the fake broker "only offers plain". Real in `@broker`: dev or Testcontainers broker with plain listeners (shared fixture from M2-14, not a copy).

## UX
`docs/ux/` Connections screen: the Failed state of the profile row and panel already shows `reason`; no layout change. The longer text must wrap, not clip (check in `ConnectionsScreenUiTest`; add a test only if the text is cut off).

## Open points
- Unverified: whether the exception shape differs between "plain broker" and "wrong CA". Expected to be a guess until measured: a wrong CA likely shows `SSLHandshakeException` with a `CertPathValidatorException` or `ValidatorException` cause, a plain stream port likely shows an SSL "unrecognized message" or a closed connection, and a plain HTTP port answers HTTP to a ClientHello (JDK HTTP client maps this to its own exception). These are not facts. Meanwhile the test developer measures as described under Scope.
- If the cases are NOT reliably separable (decision D-A below): fallback is a hedged hint on the generic TLS failure, i.e. the certificate reason gets a second sentence "If this broker does not use TLS, turn off 'Use TLS' in this connection's settings." Recommended over doing nothing, because it is true in both cases and never claims a cause.
- Wording is the architect's and is fixed above; it matches the Check text.

## Decisions for the product owner
- D-A (only if measurement shows the cases cannot be told apart): (1) hedged second sentence on the certificate failure (recommended; slightly noisier for a real wrong-CA case, but accurate); (2) no hint on Connect at all, keep P4 as is (the user then sees the hint only on Test connection); (3) classify by guess (rejected: a wrong claim on a security screen). Blocked until decided: step 3 only for this case; the measured-separable path needs no decision.

**Separable?** On the Connect path (management HTTP, `whoami`): YES, by typed signal. A plain broker is a bare `SSLException` (not an `SSLHandshakeException`, no cause); a certificate failure (wrong or missing CA, and today also a host name mismatch) is an `SSLHandshakeException` with a `java.security.cert.CertificateException` in the cause chain (`ValidatorException`). Suggested rule: certificate rejected iff the cause chain holds a `CertificateException`; any other `SSLException` is "no TLS answer". The message text is JDK wording, so tests pin the classes and chain, not the text; the shape is JDK 21 (the app's runtime); other `SSLException` shapes (for example `SSLHandshakeException: Remote host terminated the handshake` from a server that closes) are not measured and would fall into "no TLS answer" under this rule, which is true to the hint's wording. Stream client: NOT separable for a plain broker (a closed channel, no SSL signal), but the stream client is not a Connect failure (Out of scope), so no decision D-A is needed. D-A does not block the build.

**Finding (not M2-14c, for the architect): D7 is broken on the management path.** `TlsSupport.permissiveSslParameters()` sets `endpointIdentificationAlgorithm = ""`, but the JDK HttpClient still verifies the host name (case 3). Spec D7: host name not verified, "same as the M1 probe". The stream client tolerates it. Effect for users: a TLS profile whose certificate does not list the host name used (typical: an IP or an alias) fails Connect with "The certificate was not trusted" while the note says "Host name is not verified". Tests (red today, independent of the build of 14c): `ManagementHttpTlsReplyTest` "a certificate for another host name is tolerated", `RealBrokerCatalogTest` "a host name the certificate does not list still connects". Fix (developer's call): the JDK HttpClient needs `-Djdk.internal.httpclient.disableHostnameVerification=true` set before the client class loads, or a different engine. Architect decides: fold into 14c or a separate task.

**Tests, build handoff** (red evidence: with a throwaway stub of the typed split and the constant, all new tests were green except the two D7 tests; the stub is not committed): see the README row. The developer builds: (1) `ManagementReply.TlsRefused` split into `CertificateRejected` and `NoTlsAnswer` in the `SSLException` catch of `ManagementHttp` (the names the tests use); the exhaustive `when` in `RabbitMqConnectionGateway.probe` and `ManagementStreamCatalog` (two places) must handle both (catalog: `Unreachable` as today); the Check's mapping in `StreamAndManagementReachabilityChecker` is unchanged. | R1 | D7 broken on the management path: fold in or separate? | FOLD IN, as build step 3a with its own commit before the hint (3b). | R1a | Technically sound fix | The JDK HttpClient ignores `SSLParameters.endpointIdentificationAlgorithm` (it sets its own "HTTPS" check), so the name check must be removed in the trust manager. In `TlsSupport`, wrap the profile trust manager (the `X509TrustManager` from `trustManagerFactory`, profile CA as the ONLY anchor, or the JVM store when no CA) in an `X509ExtendedTrustManager` whose `checkServerTrusted(chain, authType, socket/engine)` calls the delegate's plain `checkServerTrusted(chain, authType)` (chain validation, no name check; it must be an Extended subclass, otherwise the JDK wraps it and checks the name again). Hand it to `sslContextOf` for the management client only. Not trust-all: a wrong or missing CA still throws `CertificateException`, so R2's classification still sees it; the existing wrong-CA tests are the guard. Mark the class as the single place where the name check is dropped and point to D7 in its KDoc. Not verified by the architect: the red D7 tests are the proof; if the wrapper does not turn them green, the developer stops and reports, no fallback to the system property without a new ruling. |
| R1b | System property `-Djdk.internal.httpclient.disableHostnameVerification=true` | REJECTED. It is an internal, undocumented flag; it is process-wide (every present and future JDK HttpClient, for example an update check, loses the name check, which makes D7 global instead of per profile and ready for the M5 per-profile "Verify host name" switch); it must be set before the class loads (desktopApp JVM args, every test JVM, the packaged app), so it is easy to lose silently; and it cannot be unit tested per client. A different engine (OkHttp, CIO) is also not needed: it would be a new dependency for a problem a 30-line trust manager solves. No new dependency and no build-tool or JVM flag change, so NO user decision is needed. |
| R1c | Spec D7 and the Check path | D7 promises "host name not verified, same as the M1 probe" and the panel says "Host name is not verified": the code broke the promise, the spec stays and the code is fixed. The Check has the same bug on its management leg (it uses `TlsSupport.buildHttpClient`, same call); its stream leg uses an `SSLSocket`, which honours the empty algorithm, so the Check today passes the stream leg and fails the management leg for a host mismatch. The wrapper fixes both because both use `buildHttpClient`. Spec line D7 (Management) updated by the architect today. The `permissiveSslParameters()` call on the HttpClient may then be deleted (it is dead there); keep it for the SSLSocket. |
| R2 | Classification: certificate rejected iff a `CertificateException` is in the cause chain; any other `SSLException` is "no TLS answer" | ACCEPTED, with three conditions. (a) Walk the chain with a depth limit (cause loops). (c) Wording: "did not answer the TLS handshake. It may not use TLS" is literally true for a closed connection and a plain answer; for a fatal alert from a TLS server (wrong protocol version, a server that requires a client certificate) "did not answer" is loose, but the hint is conditional ("may", "if that is intended"), claims no cause, changes nothing, and never turns TLS off. The sentence is shared with the Check and pinned in `ConnectionCheckTextsTest`, so it stays. Follow-up if it bites: measure a server that requires a client certificate and one that offers only old TLS (not now). The measured plain shape is also guarded: bare `SSLException`, not `SSLHandshakeException`, no cause. |
