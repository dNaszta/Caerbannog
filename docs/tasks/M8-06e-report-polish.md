# Migrate-from-3.x screen: report polish (follow-up of the M8-06a, 06b and 06c reviews)

Milestone: M8    Depends on: M8-06a, M8-06b, M8-06c (all merged)    Size: M (was S; seven items, one design, an API ripple in eight files; not split, see Status)

## Goal
A decision, a chip or a group toggle on a report of 240,000 findings does not group the findings again; the saved notice, the text copy and the virtual host prompt are fixed; the failure states and the picker look like the mockup.

## Why
Findings of the M8-06a, 06b and 06c reviews. Item 1 and 6 are felt on every click of a large file (about 1 s each). `docs/ux/Migrate3x.dc.html` is the design source for items 5 and 7.

## Scope
Order of work: 1+6 first (one design), then 4, 3, 2, 5, 7.

### Item 1 and 6: group once per held analysis (one design)
Today `ReportViewBuilder.build` makes three passes over `report.findings` on every call (`groupFindings`, `lossBlock`, plus `skippedItems` over `review.items`), and `rebuild()` runs it for every chip, group and decision event.

Design (decided):
- A new `internal class GroupIndex` (own file `GroupIndex.kt`, `core/migrate3x`, immutable, no state) built by `GroupIndex.of(findings)` in ONE pass. It holds `groups: List<IndexedGroup>` in display order (message-loss class first, then severity, then key; the sort the builder has now) where `IndexedGroup(key, rule, severity, findingClass, findings: List<Finding>)` keeps the findings of one rule and severity in report order, and `lossNames: List<String>` (escaped with `escapeForText`, report order, from the findings of class `MessageLoss`). Class is constant per key (a rule has one class, `Rule.kt`), so the order does not depend on which findings remain; a test asserts it over the whole catalogue of a large fixture.
- It lives in `HeldAnalysis` as `internal val groupIndex: GroupIndex = GroupIndex.of(report.findings)` (eager, next to `review`). Both places that create a `HeldAnalysis` (`showReport` and `analyseLive`) already do it inside `withContext(analysisDispatcher)`, so the one pass runs off the UI thread and `present()` stays cheap. Invalidation: none needed. The report is immutable and a new analysis is a new `HeldAnalysis`; decisions are not in the index, they are applied on top (below). Do not move the index into the view model (the held analysis outlives it, ruling 12 of 06a).
- `ReportViewBuilder.build` no longer iterates `findings`. It takes `held.groupIndex` and applies, on every call:
  1. `skipped = skippedItems(review)` (one pass over `review.items`, hash lookups; `ReviewViewBuilder.state` makes the same kind of pass; both stay, this is the "recount").
  2. When `skipped` is not empty: `removed = skipped.flatMap { review.findingsOf(it) }`. This is exactly the set the old `groupFindings` dropped (`isReviewFinding` and the item in the skipped set equals `findingsOf(item)`: same predicate in `ReviewRules.findingsByItem`). Per key: `removedCount[key]` and a `HashSet<String>` of removed finding ids (`Finding.id` is unique in a report).
  3. Per indexed group: `count = findings.size - removedCount[key]`; a group with count 0 is omitted; the chip filter (`severity in selected`) and `key in openGroups` are applied as now. No copy of any list happens here.
  4. `rows(key)`: a group without removals returns a `RowSource` over the index list itself (no copy). A group with removals, and only when it is open and asked, filters its list once by `id !in removedIds` (cost: that one open group, never the report).
  5. The Skipped group, the pills (`decorate`) and `skippedRow` are unchanged.
- The loss block comes from `lossNames`: `title`, `queueCount`, `preview = take(10)`, `queueAt` need no pass. `LossBlockView.copyText` becomes a computed property over a supplier (`names.joinToString("\n")`, built on the first read, which only the Copy button does); the public name and the text are unchanged. `LossBlockView` is built only in `ReportViewBuilder`, no other caller changes.
- Result equality: the new view must equal the old one. `build` keeps its signature (`held, selected, openGroups, rowFormatter, liveConnectionName`).

Tests (first, in `core/src/jvmTest/.../migrate3x/`; a new file `ReportGroupingCacheTest.kt`):
- Counter, no production hook: wrap the findings of a report in a `CountingList` (a test class delegating to a `List<Finding>`; it counts `iterator()`, `listIterator()`, `get()`, `subList()`, `forEach` and `stream`), `report.copy(findings = CountingList(report.findings))`, then `HeldAnalysis(...)` (the review and the index passes happen in the constructor). Reset the counter after construction. On a held analysis of 240,000 findings (for example 120,000 queues with 2 findings each; the fixtures of `ReportLargeInputTest` show how), assert the counter stays at 0 after: the first `build`, `toggleSeverity` off and on, `toggleGroup` open and close, open a sheet, accept one item, skip one item, un-skip it, and a second skip while a group is open. Only the zero-after-construction assertion is required (the review passes at construction are not known to the test, so "exactly one index pass" is not asserted).
- View-model level, same fixture size: `MigrateFromThreeViewModel` with the held analysis, the same events, counter stays 0 after the first state (this is item 6: a decision event only re-filters by the skipped set and recounts), and the state's `ReviewState` counts and the Skipped group (title, count) and the pill of the item equal the expected values.
- Equality with the old result: keep a `ReferenceGrouping` in the test source (a copy of the old `groupFindings` and `lossBlock` logic) and compare, on a mixed fixture of a few thousand findings with several rules, severities, a message-loss rule and review items: groups (key, title, severity, class, count, open), chips, loss block (title, count, preview, every `queueAt`, `copyText`), and the full row sequence of every group (`rows(key).at(i)` for all i) for: nothing skipped; some items skipped; all items of a group skipped (the group disappears); filter off for each severity; groups open. The existing `ReportViewBuilderTest`, `ReviewItemsTest`, `ReportOrderAndSummaryTest` and `ReportLargeInputTest` stay green and unedited.
- `copyText` equals the old string and is not built by `build` (checked by reading it only after the build, no counter).

### Item 2: the virtual host prompt keeps the typed text
Finding while reading the merged code: `VirtualHostPrompt` already holds the text as `remember(state.fileLabel) { mutableStateOf("") }` and the view model re-emits `NeedsVirtualHost(label, error)` with the same label, so the text should already survive a refusal in the real window; no test proves it (the test `state 4 - a refused name ...` starts with the error state, so the typed text is never there). Decided: the field text stays owned by the composable (`VirtualHostPrompt`, `ui/.../MigrateFromThreeScreen.kt`), keyed on `state.fileLabel` only, NEVER on `state` or `state.error`; add a comment that says so. No hoisting, no field in `NeedsVirtualHost` (the view model never holds typed text; a Loading in between or Choose another file leaves the composition, so a new file starts empty as the mockup state 4 shows). Tests:

This test may be GREEN when it is first written (characterization of the keying); the test developer proves it can fail by a mutation (`remember(state)` instead of `remember(state.fileLabel)`) and records that in the Status.
- BDD: the line "And the field still holds what I typed" is added to "A virtual host name that cannot be used is shown as an inline error" (done in `16`). The cucumber suite is view-model level and has no field: bind the step in `Migrate3xScreenSteps` to what the view model owns, the state is `NeedsVirtualHost` again with the label of the opened file (the screen keys the field on it); the typed text itself is asserted by the Compose test above (README says so).

### Item 4: `reportText()` is `suspend`
- Core: `suspend fun reportText(): String = withContext(analysisDispatcher) { holder.held.value?.let { CompatibilityReportText.render(it.report) }.orEmpty() }`. The held analysis is read inside the block, on the analysis dispatcher (default `Dispatchers.Default`; tests pass their test dispatcher). It does not use `job` or `scope` (a copy is not work of the report job, so it never cancels or is cancelled by an export or a new file) and it changes no state; a cancelled call throws `CancellationException` and nothing else happens.
- UI: `MigrateFromThreeScreen(reportText: suspend () -> String)`, `ReportState(reportText: suspend () -> String)`. In `ReportState`: `val scope = rememberCoroutineScope()`, and the copy button does `scope.launch { copy(reportText()); onReportCopied() }`. The sequence is fixed: render, copy to the clipboard, then `onReportCopied()`. If the screen leaves the composition (a reset, another screen) before the text is ready, the scope is cancelled, nothing is copied and no notice shows. `desktopApp` `MigrateFromThreeWiring` keeps `reportText = vm::reportText` (a suspend function reference fits). The loss and row copy buttons (`copy(loss.copyText)`, `copy(name)`) stay synchronous.
- Callers that change: `MigrateFromThreeViewModelTest` (line 308), `LiveSourceNoEchoTest` (75), `SecretsOnScreenTest` (40), `MigrateFromThreeExploratoryTest` (34) call it inside `runTest`/`runBlocking`; the acceptance steps `Migrate3xScreenSteps` (lines 160, 165, 350) use `runBlocking` (the step code is not a coroutine); ui `MigrateFromThreeTestKit` (line 120, the lambda `{ calls.copied += text; text }` is already fine) and `MigrateFromThreeReviewKit` (107, `vm::reportText`).
- Tests: view model (a text export of the 240,000-finding report is rendered on the analysis dispatcher: a `StandardTestDispatcher` as `analysisDispatcher` and a test that `reportText()` does not return before the dispatcher runs); a cancelled `reportText()` call leaves the state and the notice as they were; Compose test (existing "copy as text" test): after the click the clipboard holds the text and the notice is shown only after the copy; a second Compose test: the copy button of a screen whose `reportText` never returns shows no notice. The scenario "Export the report from the screen as JSON or copy it as text" stays unedited and green.

## Design notes
- Modules: `core` (`GroupIndex`, `HeldAnalysis`, `ReportViewBuilder`, `LossBlockView`, `MigrateFromThreeTexts`, view model), `ui` (screen, `ReportState`, `FailureBanner`, `AppIcon`), `desktopApp` (wiring: no change expected), `acceptance-tests` (`runBlocking` in three steps and the new step). Nothing touches a broker; fakes as today.
- Do not make the 06f split harder: do not add fields or jobs to `MigrateFromThreeViewModel` for generation; `reportText` and the notice change stay in the report part (`reportText`, `exportReportJson`); no new coupling between `rebuild()` and the generation fields; `GroupIndex` and `HeldAnalysis` are not touched by 06f. Keep each change in the view model to the lines named (item 3: one line; item 4: one function). Do not grow the view model; if a helper is needed, it goes in the texts or the builder.
- No `java.*` in `core` (`GroupIndex` uses only `HashMap`, `HashSet`, Kotlin lists).
- No `!!`, no new dependency.
