Lag ruling (architect, 2026-11-05, after spike S-A; closes the stop condition): the tolerance rule is dropped. Facts: `offset_lag` counts every offset tracking entry written after the consumer's read position, so it grows with the number of stores (2 and 3 for the same 3-store consumer in two runs, 0 for unnamed and non-storing consumers, also when another application stored). The Management API gives no per-consumer store count (the stream `tracking` figures are the stream's, not per consumer, and stores are asynchronous), so subtraction (b) is not derivable, and a fixed tolerance (a) is arbitrary and would still be wrong for a consumer that stores often. Rule: "Caught up" only at `offset_lag` 0, which is exact in both directions (a lag of 0 means nothing is left after the position; the first stats refresh can show 0 early, already covered by the "approximate" footnote). Above 0 the status reads "<lag> behind" (the broker's number, grouped digits), neutral style, tooltip "Stored offsets count as messages, so a consumer that stores its offset can read a few behind when it has read everything." The screen never says "Behind" as a verdict and never says "Caught up" for a non-zero number. Not a product decision (wording follows the owner's rule of never claiming exactness; the owner may veto the wording at the review). Changed: `04` outline rows (analytics "349 behind", audit "199 behind", reports "2 behind"; billing stays "Caught up"), the scenario "A consumer that stored its offset is caught up at one message behind" is renamed and changed (3 behind reads "3 behind" and carries the hint), the feature header, `Clients.dc.html` (rows, footnote, notes), `docs/spec.md` (tab paragraph, consumers row, open item). S-A must assert, on the real broker: (1) the unnamed consumer and the named non-storing consumer settle at `offset_lag` 0 (exact claim, used as the Caught up example); (2) every consumer's `offset_lag` is >= 0 and at most the number of stores it did plus 1 (upper bound, a loose sanity check; the value is printed, not pinned, because it varies between runs); (3) the unnamed and non-storing consumers stay 0 although another application stored (they must not borrow its lag). No assertion that a storing consumer reads 0 or 1. ## Goal
Opening a stream from the stream list shows a stream screen with a "Publishers and consumers" tab: the publishers with connection and counters, the consumers with connection, offset, messages behind and a Caught up or Behind status, all states of `docs/ux/Clients.dc.html`, refreshed with the app-wide interval only while the tab is shown, with counts that match the stream list.

## Why
Spec "Screens and UX" (row Publishers and consumers), "Management API facts" (publishers, consumers, visibility by tag, tab paragraph), decisions D2, D3, D8, S3a, S3b, UI1; scenarios in `04`; the product need is "is a consumer behind and which service is responsible".
