Lag ruling (architect, 2026-11-05, after spike S-A; closes the stop condition): the tolerance rule is dropped. Facts: `offset_lag` counts every offset tracking entry written after the consumer's read position, so it grows with the number of stores (2 and 3 for the same 3-store consumer in two runs, 0 for unnamed and non-storing consumers, also when another application stored). The Management API gives no per-consumer store count (the stream `tracking` figures are the stream's, not per consumer, and stores are asynchronous), so subtraction (b) is not derivable, and a fixed tolerance (a) is arbitrary and would still be wrong for a consumer that stores often. Rule: "Caught up" only at `offset_lag` 0, which is exact in both directions (a lag of 0 means nothing is left after the position; the first stats refresh can show 0 early, already covered by the "approximate" footnote). Above 0 the status reads "<lag> behind" (the broker's number, grouped digits), neutral style, tooltip "Stored offsets count as messages, so a consumer that stores its offset can read a few behind when it has read everything." The screen never says "Behind" as a verdict and never says "Caught up" for a non-zero number. Not a product decision (wording follows the owner's rule of never claiming exactness; the owner may veto the wording at the review). Changed: `04` outline rows (analytics "349 behind", audit "199 behind", reports "2 behind"; billing stays "Caught up"), the scenario "A consumer that stored its offset is caught up at one message behind" is renamed and changed (3 behind reads "3 behind" and carries the hint), the feature header, `Clients.dc.html` (rows, footnote, notes), `docs/spec.md` (tab paragraph, consumers row, open item). S-A must assert, on the real broker: (1) the unnamed consumer and the named non-storing consumer settle at `offset_lag` 0 (exact claim, used as the Caught up example); (2) every consumer's `offset_lag` is >= 0 and at most the number of stores it did plus 1 (upper bound, a loose sanity check; the value is printed, not pinned, because it varies between runs); (3) the unnamed and non-storing consumers stay 0 although another application stored (they must not borrow its lag). No assertion that a storing consumer reads 0 or 1. The compile stub changes: remove `CAUGHT_UP_MAX_LAG`, make `ConsumerStatus.Behind` carry the lag (`Behind(lag)`, text "<lag> behind") and add `STORED_OFFSETS_HINT`; the build handoff for the senior developer stays as in this brief with these texts. S-B ruling: the view model treats null, empty and blank reference or consumer name as "unnamed" (tests pin all three).

## Goal
Opening a stream from the stream list shows a stream screen with a "Publishers and consumers" tab: the publishers with connection and counters, the consumers with connection, offset, messages behind and a Caught up or Behind status, all states of `docs/ux/Clients.dc.html`, refreshed with the app-wide interval only while the tab is shown, with counts that match the stream list.

## Why
Spec "Screens and UX" (row Publishers and consumers), "Management API facts" (publishers, consumers, visibility by tag, tab paragraph), decisions D2, D3, D8, S3a, S3b, UI1; scenarios in `04`; the product need is "is a consumer behind and which service is responsible".

## Design notes
- Modules: `core` (view model, state, texts, refresh driver, `RefreshTarget`), `data-rabbit` (nothing new expected: `StreamCatalog.publishers` and `consumers` and the plugin detection exist; spikes may add parser cases), `core-testing` (fake additions), `ui` (screen), `desktopApp` (navigation, composition). Broker faked in all tests except the `brokerTest` items.
- Data per stream, from what exists: management `publishers(vhost, stream)` (per-stream path), `consumers(vhost, stream)` (vhost path filtered by `queue.name` in `data-rabbit`), `capabilities()`, `streamDetail` for `messages`, `StreamOffsets.firstOffset` from the stream protocol. The connection name is `connection_details.name`; `user` is `connection_details.user`. Nothing needs `/api/stream/connections`.
- Cost per tick: capabilities once per source, then 1 (streamDetail) + 1 (first offset) + 1 (publishers) + 1 (consumers) calls; the consumers call lists the whole vhost for a `monitoring` user and filters on the client. That is fine at 5 s for a normal vhost; record the call count and time in Status like M2-04 did, so the owner can decide on a longer default.
- Unidirectional flow, sealed states, immutable data, display strings in state (UI1), `RefreshLoop` as the one place for timer, token and D2, no boolean flags that switch behaviour (use the sealed `screen` and the sealed `status`).
- Settled values: the first consumer row after a subscribe can be off by one for up to about 5 s (`offset` = next offset, lag 0). The tab cannot detect that from the data; it refreshes with the interval and does not label the first row as final beyond the "approximate" footnote. The rows with an empty connection name are the detectable case and show "updating". With the interval Off the user presses Refresh. Tests wait for the settled row by value (M2-02c).
- Rules to protect: read only (no write call, no message read, nothing for a queue); no secret in logs or UI; D2 no automatic reconnect; D8 is not touched (the tab shows per-stream rows to a `management` user with the S3b notice, the list column stays "unavailable").

- S3b: users with the `management` tag see only their own connections' publishers and consumers: show the lists with a fixed notice "Showing only your own connections; the monitoring tag shows all", never an empty state that looks like "nobody is connected".
- S3a: users with no management tag get 401 on every management call: the Streams area shows one message ("This user cannot read stream statistics; ask for the monitoring tag") and no lists. A stream-protocol-only mode for these users needs the open spike question (can such a user call `queryStreamStats`?) and has no stream list (the stream protocol cannot list streams).

Scenarios added in `04` for these states: "A user with only the management tag sees their own connections", "A user without the management tag", "A consumer that stored its offset is caught up at one message behind". The stream-protocol-only mode for no-tag users is not built (decided).

## Inputs from the M2-03 part 2 build (2026-11-04)
- Unknown connection name: right after a client attaches, publisher and consumer rows carry `"connection_details":{}` and zero counters for some seconds. The catalog returns the row with an empty connection name (not `Unexpected`); the tab shows "unknown" for it (and treats the counters as not settled, see "Settled values only") and the window after attach is covered by a test. Add a `04` scenario for it if none fits.
- Plugin missing, 400 versus 404: per-stream paths (`/api/stream/publishers/{vhost}/{stream}`) answer 400 with an empty body and the top-level path answers 404 when the plugin is absent. The real catalog therefore asks the top-level probe after a 400 or 404 and maps to `PluginMissing`; the tab must not read the 400 as a bad request. Already implemented in `data-rabbit` and covered by `RealBrokerCatalogTest`; spec "Management API facts" row "Plugin missing" is the source.
- `NotFound` on `publishers` or `consumers` means the stream is gone: show "stream no longer exists" and go back to the list.
