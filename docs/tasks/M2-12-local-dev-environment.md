# Local development broker: docker-compose, repeatable topology files, Kotlin seed tool

Milestone: M2 (optional developer tooling, not part of the product)    Depends on: none (uses data-rabbit; merged)    Size: M (about 2 days; split in two commits: broker files, then seed module)

## Goal
A developer runs one command and gets a local RabbitMQ with TLS, the stream and stream management plugins and a known topology (vhosts, users with different tags and permissions, exchanges, queues, streams, bindings); a second command publishes messages into the streams so the list shows real offsets and counts. Reset is: remove the container and its volume, start again.

## Why
The app needs a realistic broker to look at by hand: users of every tag for the permission states, many queues for the refresh-cost trial of M2-04 ("Refresh policy (D3)": 1000 queues), streams with offsets for M2-05, super streams for M2-07. Today only the Testcontainers tests have a broker, and it is gone after the run. This serves the developer, not the product spec; nothing here changes `docs/spec.md` rules. The app stays read-only: if the product owner meant a write feature inside the app (create queues, publish a test message from the UI), that is a different thing (publishing a test message is already in the spec for M3 and topology migrations for M4/M5) and not part of this task.

## Scope
In:
- (a) `dev/broker/docker-compose.yml` (path may be `dev/` at the repo root): image `rabbitmq:4-management` (same tag the real-broker tests use), plugins `rabbitmq_stream` and `rabbitmq_stream_management`, TLS like the real-broker tests: stream 5551, management HTTPS 15671, AMQP TLS 5671 (the config mirrors `data-rabbit/src/test/resources/tls/rabbitmq.conf`); no plain ports published. The certificates: reuse the test fixture CA and server cert by copying them or mounting them from the test resources (decide in the spike below; a copy under `dev/` with a README line "throwaway, never real" is acceptable). A named volume for the broker data so `docker compose down -v` is the reset.
- (b) Topology as versioned, repeatable definition files, numbered, applied in order: `dev/broker/definitions/001-base.json` (vhosts, users, permissions, a few exchanges, quorum queues, streams, bindings), `002-super-streams.json`, `003-many-queues.json` (about 1000 quorum queues plus a handful of streams, for the refresh-cost trial; generated by a script in the seed module or committed as a file, developer's choice, but one source). Users: one per tag combination used in the spec (administrator, monitoring, management, no tag), each with permissions on one vhost, and one user with permissions on several vhosts (to prove the vhost filter of M2-04 F-1). Passwords are documented dev-only values in `dev/README.md`, never a real secret. "Migration" here only means these numbered topology files; it has nothing to do with the app's topology migrations (spec "Topology migrations").
- (c) A Kotlin module `dev-seed` (JVM only, a `main`) that connects with the stream client over TLS and publishes N messages into named streams (and optionally replaces the default stream retention), so offsets and counts are not zero; arguments: connection, stream names, message count. It may depend on `data-rabbit` (reuse of the TLS support and the `Environment` factory is the point); nothing in `desktopApp` or `ui` or `core` depends on it, and it is not part of the installer (check the packaging task configuration, see Acceptance). A Taskfile entry `dev:up`, `dev:seed`, `dev:reset` as thin wrappers, as in `Taskfile.yml`.
Out: any change to the app's code or screens; any write feature inside the app; Windows or Linux scripts beyond the compose file; CI use; Testcontainers tests (they keep their own containers).

## Acceptance
- BDD: none (developer tooling; no product behaviour). Tag nothing in `tests/bdd`.
- Unit test for the seed module's pure parts (argument parsing and the message generator), written first; the publishing itself is checked by hand.
- Manual check recorded in Status: `docker compose up -d` gives a broker where `GET https://localhost:15671/api/queues` lists the expected queues, each user can log in and sees the tag and permissions listed in `dev/README.md`; `dev:seed` makes the streams show a first offset and a count above zero in the Management UI; `docker compose down -v` then `up` gives the same topology again (idempotent reset).
- `./gradlew :desktopApp:packageDistributionForCurrentOS` (or the equivalent used by the project) output does not contain the `dev-seed` classes; the module is not in any `desktopApp` dependency list. Add a one-line check in Status.
- `./gradlew test` stays green (the new module adds no test that needs Docker).

## Design notes
- Definitions load: RabbitMQ imports a definitions file at boot with `load_definitions` (and in recent 4.x a directory of files, also loaded in sorted order). Both are to be confirmed in the first hour: if a directory works, the numbered files are all mounted and loaded together; if not, either one merged file generated from the numbered files by a small script (still one source), or the seed module applies files 002 and later through `POST /api/definitions` after start (it is idempotent: queues and exchanges already declared with equal arguments are accepted).
- Users in definitions need a password hash (`password_hash` with `hashing_algorithm`) or a plain `password`; confirm which one the import accepts and use the simpler one.
- Super streams. FIRST CHECK (spike, before writing 002): can a super stream be fully declared in definitions? A super stream is a `direct` exchange with `x-super-stream` = true, the partition streams, and bindings with the partition-order header (spec "Management API facts", Super stream row). If a definitions file with those three pieces yields a super stream that the stream client and `rabbitmq-streams list_stream_group_consumers` treat as a super stream, `002-super-streams.json` declares it; if not, the seed module declares super streams through the stream client (`Environment.streamCreator().name(..).superStream()`) and 002 is dropped. Record the result in Status and in the spec's "Management API facts" only if it is a general fact.
- The seed module is a separate Gradle module in `settings.gradle.kts`, `implementation(project(":data-rabbit"))`, `application` plugin or a plain `JavaExec` task; it never starts in `./gradlew test`. Secrets: the passwords of the dev users are on the command line or in `dev/README.md` only because they are throwaway; the seed tool does not log them.
- No new third-party library without asking: argument parsing by hand (a few flags), JSON by what `data-rabbit` already uses. Ask the architect before adding Clikt, Docker SDKs or any other library.
- Fakes: none; this is real broker only.

## Open points
- Can definitions declare a super stream completely, and does the import accept a directory and a plain `password`? To confirm first; fallbacks are in Design notes. Mark both as unverified until the spike confirms them.
- TLS certificate reuse: the fixture cert is valid for the names and IPs used by the tests only (an IP SAN is known, a DNS SAN mismatch is known not covered, spec "Not covered"). The app does not verify the host name in M2 (D7 (a)), so `localhost` works; confirm.
- Does the user mean a write feature in the app (declare topology, publish)? Assumed no; it would be a product-spec change (M3 and later), to decide by the product owner.
- The 1000-queue file: generated or committed (about 200 KB). Developer's choice; one source only.
