# A consumer row without a lag number is a settling row, never 0 or "Caught up"

Milestone: M2 (hardening)    Depends on: none (builds on M2-06 and M2-17, both merged)    Size: S

## Goal
When the management API sends a consumer row with no usable `offset_lag` (the key is absent, JSON `null`, or not a number), the Publishers and consumers tab shows that row the way it shows a client that has just attached: Offset, Messages behind and Status read "updating", the row cannot be browsed, and it adds no point to the lag trend. It never reads "0" and never "Caught up". A lag that is present, including 0, reads exactly as before.

## Why
Lag ruling (`docs/spec.md`, "Publishers and consumers tab", paragraph "Corrected 2026-11-15"; `docs/tasks/M2-06-publishers-consumers.md`, lag ruling): the screen shows the broker's number as reported and "Caught up" only at 0. `ManagementJson.parseConsumers` (`data-rabbit/.../ManagementJson.kt:187`) reads `row.long("offset_lag") ?: 0`, so a row for which a broker sent no number is turned into the broker's "0" and reads "Caught up": a number the broker never sent, which is what the ruling forbids. The same invented 0 would also enter the lag trend (a "Draining" or "Growing" badge computed from a value nobody reported).

No known bug: the recorded 4.x row has the field (`fixtures/m2-02/stream-consumers.json`), and the S-A pass-through (`RealBrokerClientsTest`) compares the catalog with a raw `Long?` read until they agree, so settled rows of a stream that holds messages do carry it. This is a robustness fix. The owner approved it on 2026-11-15 as a small follow-up after v1.0.1 and said: treat such a row as settling, in line with the existing "updating" state of a row with an empty `connection_details`. The idea first stood in the Open points of `docs/tasks/M2-17-s-a-lag-steady-state.md`.

## Rulings (architect, 2026-11-15)
1. **Fields: `offset_lag` only.**
   - `offset_lag` is the field the ruling is about, and the only one whose invented 0 produces a false claim ("Caught up", a trend point).
   - `consumed` and `credits` stay `?: 0`. Production code never shows or reads them (a search of `core`, `ui`, `desktopApp`, `mcp-server` finds them only in the parser and in `FakeStreamCatalog.consumer`), so an invented 0 is invisible and hiding a row because of them would cost the user something for no gain.
   - `offset` stays `?: 0` on purpose, although the screen does show it (Offset column, and `browseFromOffset` for the tape pin). A row that lacks only the offset has no state to fall into except hiding a lag that is known, and widening exposes more rows to the omission risk in Open points 1 (a consumer that has read nothing may legitimately lack `offset`; not measured). The live probe below records whether `offset` is always present, so the architect decides a follow-up on facts, not on a guess. The M2-17 Open point said "`offset_lag` or `offset`"; this brief narrows it knowingly.
2. **Where the decision lives: the parser reports, `core` decides.** `ConsumerRow.offsetLag` becomes `Long?` (`null` means: the broker sent no whole number). `data-rabbit` stops inventing (`offsetLag = row.long("offset_lag")`, no `?: 0`). `core` decides what "no number" looks like: the private `ConsumerRow.isSettling()` in `StreamClientsViewModel.kt` becomes `connectionName.isEmpty() || offsetLag == null`, so there is still one predicate for the state, the browse offset and the trend. `core` keeps its rule (no RabbitMQ, Paho or `java.*`): `Long?` is plain Kotlin. No `!!`, no `?: 0` on the lag anywhere after step 3.
   Rejected: (a) the parser blanks `connectionName` for such a row: it lies about the connection and mixes two causes in one field; (b) a `lagKnown: Boolean` next to a dummy 0: the next reader will use the 0; (c) dropping the row: a consumer would vanish from the table and from the delete dialog's consumer count (`Main.kt:223`, `clients.consumers.size`).
3. **Product decision: no.** The row falls into the existing state with its existing words (`ConsumerStatus.Updating`, "updating"; no new state, no new text, no row disappears, no number changes in the common case because the broker sends one). One visible consequence, for the owner to veto in the report, not a block: the existing state is all-or-nothing, so the Connection cell of such a row reads "unknown" even though the broker named the connection (the mockup says "unknown" means "just attached"). No broker is known to send this row. The alternative (keep the name, only the three cells "updating") would split the state in two and draw a combination no mockup shows; it is a separate decision if the owner wants it.

## MCP
None, and no new MCP capability. No MCP tool reads consumer rows: `caerbannog_list_streams` and `caerbannog_get_stream_details` return the stream's consumer count from the stream list (`StreamSummary.consumers`, `McpServer.kt:618`), `caerbannog_browse_stream` reads messages, and nothing in `mcp-server` calls `StreamCatalog.consumers` or uses `ConsumerRow` (checked by search in `mcp-server/src`). So no tool returns a lag or a status and what the MCP stream tools return for a stream with such a consumer is unchanged. A future tool that lists consumer rows would be a separate decision and would have to carry this rule (a missing lag is null, never 0).
