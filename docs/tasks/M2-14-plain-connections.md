# Plain (non-TLS) connections, per-profile TLS switch

Milestone: M2    Depends on: M2-05 (builds on its CA field work; M2-05 itself is not merged, branch `m2-14-plain-connections` starts from its accepted head)    Size: L as one piece (about 2 days); split below into M2-14a and M2-14b (each about 1 day)

## Goal
A connection profile has a TLS switch, default ON, that the user can turn OFF for any host. With TLS off the app talks plain stream protocol and plain HTTP management, the CA is ignored, and the app says "Not encrypted" wherever the connection is shown. The dev broker also offers plain listeners, and the dev seed can use them.

## Why
Product decision of the user, 2026-11-05: for local development you normally do not use TLS, and on a local TLS dev broker the app failed with `certificate_unknown` because the CA was not set. Decision: a per-profile switch, default ON, works for ANY host (no localhost-only rule), with a visible "Not encrypted" warning. This REVERSES the earlier rule "TLS is always on" (spec "Architecture" line 44 to 52, "Connection lifecycle" TLS lines, "Screens and UX" Connections row line 158, "Testing" line 245; the `01` scenarios "TLS is always on" and "The app refuses a broker that does not offer TLS"; the comment in `ConnectionProfile.kt`; `ManagementRequests` "https only"). The reversal is a decision, not a drift, so the spec is updated in this task (step 1 below).

## Scope
In:
- Spec update (done in the same commit series, step 1 below): see "Spec changes".
- Model: `ConnectionProfile.tls: Boolean = true`; `ConnectionProfileInput.tls: Boolean = true`-style nullable with "keep" semantics like the level (null on update = keep the saved value, so a caller that does not know the field cannot silently turn TLS off or on).
- Persistence: `connections.json` gets a `"tls"` boolean per profile, always written. A file without the key loads as TLS on (backwards compatible, no migration step). An unreadable value (not a boolean) loads as TLS on (the safe side) and the rest of the profile still loads.
- Validation: with TLS off the CA path is not required, not validated and not used; the CA field is disabled in the form (the saved path is kept but unused, see O3). The "Host name is not verified." note shows only with TLS on (M5 `M5-verify-host-name` note stays, only TLS on).
- Port defaults that follow the switch (see Design notes).
- Plain stream `Environment` (no `.tls()`), plain management HTTP (`http://`), in all four places that assume TLS: connection check (`StreamAndManagementReachabilityChecker`), permission check (`ManagementApiPermissionChecker`), held connection (`RabbitMqConnectionGateway`, `StreamEnvironments`, `ManagementRequests`), and error mapping (`TlsRefused`, `CERTIFICATE_NOT_TRUSTED` only occur with TLS on).
- "Not encrypted" warning: connection edit panel, app bar chip (visible text and accessible label), chip popup row of that profile.
- Test connection wording (see UX).
- No password in any log or message on the plain path (the password then travels in clear text; that is the point of the warning).
- Dev environment: plain listeners, compose, conf, README, Taskfile, `dev-seed --no-tls`.
- Review item (a) from M2-05 (finding 6): the CA path validator does file IO on every keystroke on the UI thread. Validate on focus loss (and on Save), and run the file read off the UI thread (`Dispatchers.IO` behind the existing `CaCertificateValidator` port). The same form is touched anyway.
- Review item (b): the flaky `StreamManagementApiSpikeTest` Q1 (about line 307) asserts `message_stats.publish == 1000` right after awaiting `messages == 1000`; await `publish` the same way (the management stats are sampled, the two counters do not update together). Tag stays `broker`; no behaviour change.
Out: a localhost-only rule or a confirmation dialog (decided: any host, visible warning only); a "Verify host name" switch (M5); AMQP; client certificates; changing the rule that quorum queue messages are never read; HTTP to HTTPS auto-upgrade or fallback (the app never silently falls back from TLS to plain, see Design notes).

## Design notes
- Core (`core`, common): `tls` on the profile and the input. The comment in `ConnectionProfile.kt` that forbids a toggle is replaced by one that says why the default is on and that nothing may fall back silently. A small value, e.g. `BrokerEndpoints.defaultsFor(tls)` (stream 5551/5552, management 15671/15672), is the one home for the four port numbers; `01` scenarios and the form read it. "Only while the user has not edited them" is a UI/view-model rule: the form keeps `streamPortEdited` and `managementPortEdited` flags (or compares the field with the current default) and on toggling sets a port only if it still equals the default of the old mode. Edited-then-equal-to-the-other-default counts as not edited; accepted, it is harmless. RabbitMQ defaults confirmed from the RabbitMQ docs: stream 5552 (TLS 5551), management 15672 (TLS 15671), AMQP 5672 (TLS 5671); verify the container values in the step 2 spike.
- Data (`data-rabbit`): one `BrokerTransport` (sealed: `Tls(trust)`, `Plain`) built from the profile in one place and passed to `TlsSupport`/`StreamEnvironments`/HTTP client builders, instead of `if (profile.tls)` in each of the four places (the problem: four call sites each with its own boolean branch; a missed one would silently send plain or TLS). `ManagementRequests` takes the scheme from that value; its `require(base.startsWith("https://"))` becomes "scheme matches the transport", so a plain base can only come from a TLS-off profile. The check classes keep returning typed results; `TlsRefused` is only produced with TLS on. With TLS on against a plain port the failure is the TLS handshake error; map it to the same result plus the hint in the message (the hint is shown only when TLS is on and the handshake failed).
- No silent fallback in either direction, and the profile switch is the only source of the mode. The held connection (D1) is rebuilt when the profile is edited, as today; toggling TLS is an edit, so "Connection settings changed. Connect again." applies without extra code. Verify with a test.
- Persistence: `JsonFileConnectionProfileRepository` DTO gets `tls: Boolean? = null` read as `?: true`; written always. A newer file read by an older app version: the old version ignores the key and would connect with TLS to a plain port and fail with a handshake error (not a leak). Accepted; note in the Status when built.
- UI (`ui`): no broker code. The form shows a switch "Use TLS" (on by default), the "Not encrypted" warning line directly under it when off, the CA field disabled with the helper "Not used without TLS". `ConnectionControlModel` exposes `encrypted: Boolean` (or `notEncrypted`) for chip and popup; the accessible label is built in one place from it (for example "uat-local, connected, not encrypted"). CA validation: the field reports focus loss; the view model validates then and on Save; the validator runs on the IO dispatcher, not the UI thread.
- Logs: nothing new is logged; the existing rule "only the exception class name" covers the plain path. Add the test, not a new logger.
- Dev broker (`dev/broker`): the throwaway TLS fixture `data-rabbit/src/test/resources/tls/rabbitmq.conf` is shared with the Testcontainers recipe (one home). Add the plain listeners there (`stream.listeners.tcp.default = 5552`, `management.tcp.port = 15672`, AMQP plain `listeners.tcp.default = 5672` only if the broker needs it to boot; do not publish it) so both the compose file and the Testcontainers recipe get them, instead of a second file. Compose publishes `5552:5552` and `15672:15672`. Whether the `rabbitmq:4-management` image already enables these by default must be measured first (spike S-D below). Definitions unchanged. `dev/README.md`: the "Only TLS is published" paragraph and the A1 profile get a plain A2 profile (host `localhost`, 5552, 15672, TLS off, `admin`/`dev-password`) and a plain `curl -u admin:dev-password http://localhost:15672/api/queues/%2F`. Taskfile: `task dev:seed -- --no-tls --password dev-password` works as is because args pass through; update the desc and `dev:up` desc ("TLS and plain").
- Spikes first: S-D (step 2): does the broker boot and serve plain 5552 and 15672 next to the TLS ones with the fixture conf, in compose and in Testcontainers; are `message_stats` and the stream plugin the same over plain (expected yes). S-E: the stream client builder without `.tls()` against a plain stream port, with a user's `Environment` and `host` set; does it need `.host`/`.port` only (expected).
- The CA TrustManager, `endpointIdentificationAlgorithm` and D7 stay exactly as they are for TLS on; do not touch them.
