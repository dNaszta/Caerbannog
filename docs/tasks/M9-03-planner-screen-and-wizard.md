# M9-03: Planner screen: the step list, the wizard dialog, the entry on the Migrations screen, the limited states

Milestone: M9    Depends on: M9-02    Size: M

PLANNED 2026-11-15. Step 1 (brief confirmed against the real M9-01/M9-02 code) done 2026-11-16, round 0; waits for the owner's mockup review only for wording (see Open points). Third task of the earliest working slice: after it a user can plan a queue, an exchange and a binding, save the plan as a migration and apply it on the Migrations screen.

## Goal
The planner is on screen as drawn in `docs/ux/Planner.dc.html`: opened from the Migrations screen, with the plan header, the step list, the three-page wizard, the JSON view, save, dismiss, and every limited state. The composables are thin: every decision and text comes from `PlannerState`.

## Why
Spec "Topology planner (M9)" (owner decisions O1, O3, O5), Screens table row "Topology planner". The mockup is the design source.

## Design notes
No decision in a composable: enabled, disabled, texts, order of banners all come from the state. The step list is a `LazyColumn` (a plan can come from a large file in `M9-12`). Scroll containers follow the CLAUDE.md rule (no `weight` or ellipsis inside a scroll; a scrollbar for mouse users). The wizard is a dialog; its content scrolls when the window is short. Reuse the shared components (`SearchField` is not needed; `CenteredMessage`, the banner and pill composables of the Migrations screen). No broker is touched by this task; UI tests run on fakes.

States to build: empty, draft with steps, problem in the plan, save disabled with its reason, saved, write failed, dismiss question, 3.x, unreadable draft, Read-only level, no configure permission, not connected, no folder and read-only folder, another virtual host.

## API shape confirmed (architect, step 2.5, 2026-11-16, round 0)
The tests of commit be3d098 are the API spec; the senior developer follows them. Confirmed as written, with these additions:
- Debounce: in the view model (`descriptionDebounceMillis`, 500 default, public `flush()`); text in state at once. Save, Dismiss, `flush()` and any other plan change write at once; nothing is written after the draft is cleared; a locked planner never writes. The screen calls `flush()` on leaving.
- `canDismiss = !isLocked && (steps present || description present)`: confirmed; the earlier "false for an empty plan" meant no steps and no description.
- `migrationText` is a parameterless property (version unpinned, as the tests parse it). No folder input; the real version is chosen at save.
- `WizardState.Details` carries `pageMessage`, `exchangeSuggestions`, `destinationSuggestions`, `asksRoutingKey`, so the screen needs no `FormContext`.
- `PlannerEvents` (ui): the methods the tests use, including `flush`; later additions need default bodies. `PlannerScreen(state, events, control, controlEvents, onNavigate)`; `MigrationsScreen(..., plannerEntry, onOpenPlanner, onDismissDraft, plannerNotice: String? = null, onDismissPlannerNotice)`. Card Dismiss asks `PlannerTexts.dismissQuestion(n)` first; an unreadable draft has a card and no Dismiss.
- desktopApp: `AppNavigation.plannerOpen/openPlanner()/closePlanner()/planSaved/savedPlan/savedPlanHandled`; `createAppComposition(planDraftFile)`, `planDraftStore`, `createPlannerViewModel(inputs, scope)`, `followPlanner`, `plannerEntry()`; `newPlannerScope()` = `Dispatchers.IO.limitedParallelism(1)` + `SupervisorJob`; `PlannerEventsAdapter`.
- The planner passes `activeItem = "Migrations"` to the frame. Test tags: the list in the KDoc of `PlannerUiKit` extends the list in Scope (additions are allowed; none may be renamed later).
