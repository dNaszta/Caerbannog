# Forwarding screen: pick a queue, plan, typed confirmation, progress, remove

Milestone: M8    Depends on: M8-07, M8-08 (both merged, main `ab5ae6a`), M8-06a/b/c (merged)    Size: M (not split)

LEAN (owner, 2026-11-11): the smallest screen that lets the owner forward ONE queue from a 3.x broker to a 4.x queue safely. No extra states, no history, no persistence of progress, no settings.

## Goal
From the Migrate from 3.x screen, with a live 3.x analysis held and a 4.x connection Connected, the user picks one queue, sees the dry-run plan (facts, blocks, warnings), confirms by typing the source queue name, watches the broker move the messages, and can remove the shovel. Every safeguard is already enforced in `core` (`ForwardingService`); this task only drives it and shows it.

## Why
Spec "Forwarding messages with a dynamic Shovel" safeguards 1, 2, 3, 9 and the typed-confirmation UX rule; `docs/tasks/M8-07-*.md` (rules) and `M8-08-*.md` (gateway).

## Scope
In:
1. **Entry point** (owner decision D1, recommendation A): a button "Forward messages" in the app bar of the report (`migrate3x-forward`), shown only while `HeldAnalysis.kind == Live`. It opens the forwarding view inside the same screen (state `Forwarding`, no new drawer item, no new navigation destination).
2. **Pick a queue** (`ForwardingState.Pick`): a find field and a lazy list of the queues of the held analysis document (`document.queues`: name and virtual host), one "Forward messages" button per row (`forward-pick-<index>`). One queue at a time; no "forward all" anywhere. Each button is disabled with its reason when forwarding cannot start now: no Connected 4.x connection ("Connect to a RabbitMQ 4.x broker first"), or the connection is locked (`ForwardingPlanner.gate`, text below). The analysis is of "legacy-eu"; if that connection is not the live source any more nothing changes here (the probe reads it by profile name and its stored password; an unreachable source is a `ProbeFailed` text).
3. **Plan** (`Preparing` then `Plan`): `service.prepare(request)` (the dry run sends only GET). Shows the facts (source counts, destination type), the blocks as error banners, the warnings as warning banners. A `Blocked` plan shows no confirm form. `ProbeFailed` shows one fixed text per outcome (`SourceUnreachable`, `SourceNotPermitted`, `DestinationUnreachable`, `Failed`). A `ShovelExists` block shows the shovel's state and forwarded count and, at Full control, the Remove shovel button.
4. **Confirmation** (`Confirm`, a `Prepared.Ready`): the lines of `ForwardingConfirmation`, a field "AMQP host and port as `<dest>` reaches them" (prefilled with the source profile host and the default port of its TLS switch, P8, never saved), a switch "Use another user for this Shovel" with a user name and a masked password field (P14; memory only; cleared when the dialog closes or the screen is left), a switch "Keep the shovel running after the messages are moved" (`SrcDeleteAfter.NEVER`; off by default; turning it on adds the `KeepsShovelAndCredentials` warning line), and the typed-name field (`forward-typed-name`). The button `forward-confirm` is enabled only while the typed text equals the queue name exactly (the service refuses anyway). Cancel (`forward-cancel`) goes back to the list and sends nothing.
5. **Start and progress**: confirm calls `service.start(request, typed)`. `StartResult.Started` begins polling: `service.poll(request, state)` every 2 seconds (a constant `FORWARDING_POLL_MILLIS = 2_000`) while the view is open, stopping at `Finished` or `Failed`; the state shown is `ForwardingState` ("Moved about N of M messages", N = forwarded, M = source ready of the dry run; with `NEVER` "Moved N messages; the shovel keeps running"). The other `StartResult`s show their fixed text (`NotConfirmed` and `Blocked` can only come from a stale plan: back to the plan).
6. **End states**: `Finished`: the view model calls `service.prepare(request)` once more (a read-only dry run) and reads `facts.source.ready`: "Finished. About K messages stayed on the source because they were published meanwhile" or "Finished. No messages stayed on the source"; when that call gives no facts (a gate block or a failed probe) it shows "Finished." alone. `Failed(reason, cleanedUp)`: "The forwarding failed: <reason>" plus "The shovel was removed, so no stored credentials remain." when `cleanedUp`, else "The shovel could not be removed here. It and its stored password remain on `<dest>`; a user with the level Full control must remove it." with the Remove shovel button.
7. **Remove shovel** (`forward-remove`): `service.remove(ref)`; `NeedsFullControl` shows the disabled reason "Removing a shovel needs Full control" (the button is disabled below Full control, so the text is the reason; no request is ever sent below it). Offered on the running view, on a `ShovelExists` plan and after a `Failed` that was not cleaned up; NOT after `Finished` (decision D4).
8. **Wiring** (`desktopApp`, composition root): see Design notes.
9. **Texts into `ForwardingTexts`** (core): the fixed failure texts of `ForwardingService` (M8-07 finding 1: "The broker could not be reached", "The broker did not allow creating the shovel", "The broker did not allow removing the shovel") and the new screen texts: the six block texts, the two warnings, the probe-failure texts, the progress and end texts, the disabled reasons, labels of the form. The exact wording is owner decision D2 and D3 below; the key words stay what `ForwardingConfirmationTest` checks.
Out: starting or removing from MCP (none), a shovel list screen, forwarding from a file report (no source broker), any persistence of progress, multi-queue forwarding, editing the destination queue name or virtual host (D5), the `amqps` TLS options (M8-08 open point).

## Design notes
- **Core** (`dev.caerbannog.core.forwarding`): `ForwardingViewModel(service: ForwardingService, held: AnalysisHolder, destination: () -> DestinationConnection?, profiles: (String) -> ConnectionProfile?, scope, pollMillis = FORWARDING_POLL_MILLIS)`. State in, events out, one `StateFlow<ForwardingScreenState>`: `Closed | Pick(query, rows) | Preparing(queue) | Plan(prepared, form) | Starting | Progress(state, plan facts) | Ended(...)`. Events: `open()`, `close()`, `setQuery`, `pick(queue)`, `setAmqpHost/Port`, `setAnotherUser(on, name, password)`, `setKeepRunning`, `setTyped`, `confirm()`, `cancel()`, `remove()`. One job at a time (a new event that starts work cancels the old one; polling is a job tied to the view being open; `close()` cancels it and wipes the form). `DestinationConnection(profile: ConnectionProfile)` is the held 4.x connection. The request is built in one pure function `ForwardingRequests.of(sourceProfile, sourceVhost, queue, destinationProfile, form)`: destination queue = same name, destination vhost = the destination profile's virtual host (D5), address = `ShovelAddress.forProfile(sourceProfile, host, port, credentials)`.
- The typed password becomes a `ShovelSourceCredentials` only when the request is built and is dropped from the state with the form; the state, the logs and every text never hold it (a sentinel test over every state value's `toString`, like `ReviewSecretsTest`).
- **ui**: `ForwardingView.kt` (list, plan, confirmation, progress) in `ui/migrate3x`, composables thin; test tags: `migrate3x-forward`, `forward-find`, `forward-pick-<n>`, `forward-plan`, `forward-block-<n>`, `forward-warning-<n>`, `forward-amqp-host`, `forward-amqp-port`, `forward-other-user`, `forward-user`, `forward-password`, `forward-keep-running`, `forward-typed-name`, `forward-confirm`, `forward-cancel`, `forward-progress`, `forward-ended`, `forward-remove`, `forward-remove-reason`. Reuse `FailureBanner` (M8-06e) for blocks and failures; add `AppIcon`s only if missing (`move_up`, `history`, `sync`, `inbox`, `block` check).
- **Wiring** (`data-rabbit` and `desktopApp`; the only non-UI changes): (a) `StreamSource` gets `val shovels: ShovelGateway = UnavailableShovelGateway` (core; every method answers `Failed("No 4.x connection is held")`; like `definitionsSource`); (b) `RabbitMqConnectionGateway` gets a constructor parameter `profiles: (String) -> ConnectionProfile? = { null }` and builds `ManagementShovelGateway(http, requests, profiles, secretStore)` into `RabbitMqHeldConnection` for a connection that is NOT a migration source (a 3.x connection gets the unavailable one, so the app can never shovel from the 3.x connection as destination); (c) the composition root passes the profile repository lookup to the gateway and builds `ForwardingService(source.shovels) { ForwardingContext(level of the held profile, session topologyUnlocked of the held connection) }` for the held 4.x connection, read at every call (the level can change); `MigrateFromThreeWiring` owns the `ForwardingViewModel`, the held analysis comes from the existing `AnalysisHolder`. No new module, no new dependency.
- Fakes: `FakeShovelGateway` (exists). Real broker: none here (M8-08 covers it); the end-to-end proof is `@gate-M8` in M8-11.
- Do not add a name length rule (M8-08).

## Owner decisions (ask in one go; each with options and the architect's recommendation)
- **D1. Where the entry point lives.** (A) A "Forward messages" button in the app bar of the Migrate from 3.x report, live analyses only, opening a queue list of the analysis. (B) A button on each queue row of the report. (C) From a queue of the 4.x connection. Recommendation A: the report lists only queues WITH findings (compatible queues are "not listed below"), so B would miss most queues; C has no source side. A needs the live analysis of the 3.x connection to be held, which the user has just made.
- **D2. The confirmation text (exact strings).** Proposed, from the spec and already in `ForwardingTexts`: "From: `<connection>`, virtual host `<v>`, queue `<q>` (`<amqps://user@host:port/vhost>`)"; "To: `<connection>`, virtual host `<v>`, queue `<q>`"; "The messages are moved: they leave the source queue when the destination confirms. The app cannot undo it."; "The source queue itself is not deleted."; "The shovel keeps credentials on the destination broker until it finishes or is removed."; "The source password is stored there in clear text, and any administrator of that broker can read it until the shovel finishes or is removed."; with keep-running: "The shovel and its credentials stay until you remove the shovel."; plain: "Not encrypted: the shovel reaches the source over a plain connection."; button "Forward messages"; field "Type the source queue name to confirm". Options: approve as proposed, or edit. Recommendation: approve (the content was decided on 2026-11-09, P1, P14; only the wording is new).
- **D3. Block and warning wording.** Proposed: locked "Topology changes are locked on `<dest>`: forwarding needs the level Declare and edit and the configure permission."; policymaker "The user of `<dest>` needs the policymaker tag to create a shovel."; status "The user of `<dest>` cannot read the shovel status and needs the monitoring tag. Without it the app could not see a failed shovel or remove it."; plugins "The shovel plugins are not enabled on `<dest>`. Enable rabbitmq_shovel and rabbitmq_shovel_management."; missing destination "The queue `<q>` does not exist on `<dest>`. Apply the migration that declares it first."; existing shovel "A shovel named `<name>` already exists on `<dest>` (`<state>`, `<n>` forwarded). The app never replaces a shovel."; warning "The destination queue is a `<type>` queue, not a quorum queue." Recommendation: approve as proposed.
- **D4. Remove after Finished.** (a) No Remove button after Finished (the shovel removed itself with `queue-length`, S-J; with Keep running the shovel is Running and has the button). (b) Always show Remove. Recommendation (a): a Remove that has nothing to remove invites confusion. After a Failed that could not be cleaned up, or for an existing shovel, Remove shows (Full control only).
- **D5. Destination name and virtual host.** (a) Fixed: the same queue name, the virtual host of the connected 4.x profile; the destination must already exist (the migration declares it). (b) Editable destination queue and virtual host. Recommendation (a): lean; an editable destination invites a typo that the dry run would only catch as "missing". Can become (b) later without a rule change (the request already carries both).
- **D6. Polling and leaving the screen.** Decided by the architect (technical, no wording): poll every 2 seconds while the view is open; leaving stops the polling, not the shovel; coming back shows the shovel through the dry run (`ShovelExists` with its state and Remove). A failed shovel that nobody was watching stays until the user removes it (needs Full control). Flagged here only because it means a failed Shovel can keep a stored source password on the 4.x broker if the user leaves; the alternative (a background poller that outlives the screen) is not built (lean). Recommendation: accept.
Already decided, no question: P1/P14 credentials and the disclosure, P4 Full control to remove (and the cleanup exception, M8-07 spec 9a), P5 `never` with a warning, P8 AMQP host and port asked in the dialog.
