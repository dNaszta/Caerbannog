# Management API and stream statistics spike (real broker)

Milestone: M2    Depends on: none (M1 TLS fixture and `brokerTest` exist)    Size: M

Branch: `m2-02-management-api-spike` from `main`. Needs Docker. Runs in parallel with M2-01b.

## Goal
We know, from a real RabbitMQ 4 broker with the stream plugins over HTTPS and TLS, exactly which management API endpoints and fields give the stream list, publishers, consumers, offsets and super stream partitions, what a non-admin sees, and whether offsets need the stream protocol. The answers are asserted by `@broker` spike tests and written into this Status and `docs/spec.md`, so M2-03 can be briefed without guessing.

## Why
`docs/spec.md` open question "Confirm the exact fields returned by the stream publisher and consumer endpoints"; Risks entry on the Testcontainers deprecation warning; `03_stream_list.feature` (counts, first/last offset, size, publishers, consumers, message count = committed minus first plus one), `04_publishers_consumers.feature` (tagged `@needs-spike`: published, confirmed, errors, consumer offset, lag), `06_super_streams.feature` (partitions as one entry, per-partition stats) and `11_global_search.feature`. Without this, M2-03 (`StreamCatalog`, real client) and M2-06 would be built on guesses.

### The seven questions (record real status, field names and JSON types)
1. **Stream list.** Which endpoints list stream queues (`GET /api/queues`, `/api/queues/{vhost}`, `/api/queues/{vhost}/{name}`, and any stream-specific listing in `rabbitmq_stream_management`) and which fields each carries for a stream with data: `name`, `vhost`, `type`, `messages`, `consumers`, `publishers` (if any), `arguments` (retention `x-max-age`, `x-max-length-bytes`, `x-stream-max-segment-size-bytes`), `policy`, `node`, `leader`, `members`/`online`, size and segment fields, `message_bytes`, `memory`. Record exact names, types and which are absent for streams. Use data published via the management publish endpoint (see "How to publish"), so counts are known exactly.
2. **Publishers and consumers per stream.** Probe at least `/api/stream/publishers`, `/api/stream/consumers`, `/api/stream/connections`, `/api/stream/connections/{vhost}/{name}/publishers` and `.../consumers`, and the `/{vhost}/{stream}` variants if they exist in 4.x. Record fields (publisher reference, connection, published, confirmed, errors; consumer offset, offset lag, subscription id, properties, `active`) and what an empty stream returns (200 with `[]` or an error). For non-admin: record status and visible rows for tag `monitoring` and for no tag (same users as `PermissionsEndpointSpikeTest`), and whether a user sees streams in vhosts or with names they have no permission on.
3. **First and last offset.** Do the management queue objects carry first offset, last offset, committed offset, first or last timestamp (candidates to check: stream-specific fields on `/api/queues`, the stream plugin endpoints, `/api/stream/.../tracking`)? If not, the source is the stream protocol `queryStreamStats` (first offset, committed chunk id). Record which, and whether the "about N messages" formula in `03` (committed minus first plus one) can be computed from the management API alone. Compare the management `messages` value with the offset-derived count for the same stream, with and without a consumer that stored an offset (offset tracking entries inflate the offset; this is the `@gate-M2` tolerance).
4. **Search by name.** Server-side options on `GET /api/queues`: `name` with `use_regex=true`, pagination (`page`, `page_size`, `pagination` object fields `total_count`, `filtered_count`, `item_count`, `page_count`), the maximum `page_size` (spec assumes 500: confirm or correct), sort params, a `columns` parameter to shrink the payload, and whether `?name=` filters type. Record whether a "streams only" filter exists server side (for example a `queue_type` filter or only client-side on `type`). Test with at least 12 queues and streams mixed, page size 5. Conclusion needed: server-side name filter yes or no, and how the app finds streams only.
5. **Super streams.** Create a super stream with 3 partitions without a new dependency: `rabbitmq-streams add_super_stream orders --partitions 3` through `execInContainer` (check the command exists in the image; if not, say so). Record how the partitions appear (names such as `orders-0`, `arguments` such as `x-super-stream`?), whether the exchange `orders` of type `x-super-stream` shows in `/api/exchanges`, which binding keys and arguments mark the partition order, and how the app can tell a partition from a normal stream and group partitions under the super stream (queue argument, binding, or name convention only).
6. **Testcontainers deprecation.** Reproduce the warning on the pinned 1.21.3 (`RabbitMQContainer.withPluginsEnabled`; run `./gradlew :data-rabbit:brokerTest --info` and capture the exact message). Say what it says and what to change. Maven Central (checked 2026-11-04): `org.testcontainers:rabbitmq` stops at 1.21.4 (2025-12-16); the 2.x line (2.0.5, 2026-04-20) renamed artifacts to `testcontainers-rabbitmq`, `testcontainers-junit-jupiter` and the BOM. See D2.
7. **Plugins and fixture.** Is `withPluginsEnabled("rabbitmq_stream", "rabbitmq_stream_management")` enough with `rabbitmq:4-management` plus `tls/rabbitmq.conf` (stream TLS on 5551, management HTTPS on 15671)? Record what `/api/overview` and `/api/stream/...` return when `rabbitmq_stream_management` is NOT enabled (feeds the `@negative` scenario in `04`: "told to enable rabbitmq_stream_management"; record status and body so M2-06 can detect it). Also record whether the stream listener answers on 5551 over TLS with the fixture (a TLS handshake check is enough without a client).

### How to publish and consume without a new dependency (verified: repo has no `stream-client` or `amqp-client` in any `build.gradle.kts`)
- Publishing messages to a stream: declare the stream via `PUT /api/queues/%2F/{name}` with `{"durable":true,"arguments":{"x-queue-type":"stream"}}` and publish through `POST /api/exchanges/%2F/amq.default/publish` (routing key = queue name). The broker publishes over AMQP internally, so no client is needed. Expected to work; confirm (and confirm `/api/exchanges/.../publish` is allowed for the stream type).
- Publishers and consumers on a stream exist only while a client holds a stream-protocol (or, for consumers, AMQP) connection. The management API cannot create them and `rabbitmqctl` cannot either. So question 2 for non-empty results, and `queryStreamStats` in question 3, cannot be completed without a client. Empty results, endpoint existence, non-admin status codes and everything in questions 1, 4, 5, 6, 7 can.
- Fakes: nothing in this spike is a fake. Everything is a real broker, so the whole spike needs Docker; tests are skipped without it (`@Testcontainers(disabledWithoutDocker = true)`). Fakes come later in M2-03 (`FakeStreamCatalog`) built from the recorded JSON.

**S1 (needed for questions 2 and 3 only): a stream client dependency.**
Facts (Maven Central, checked 2026-11-04): `com.rabbitmq:stream-client` latest release 1.13.1, published 2026-11-03 (one day old, younger than two weeks, so it must not be adopted now); the previous release 1.12.0 published 2026-10-09 (26 days old, passes the two-week rule). `com.rabbitmq:amqp-client` latest 5.37.0 published 2026-10-01. The spec's tech-stack table already names `com.rabbitmq:stream-client` as the production stream access (spec "Stream access"), so it is coming anyway for M3 browsing and probably for `queryStreamStats`.
Options:
- A. `testImplementation("com.rabbitmq:stream-client:1.12.0")` in `data-rabbit` for this spike only (test scope). Creates publishers and consumers over the stream protocol (TLS on 5551 with a trust-all `SslContext`, test only), calls `queryStreamStats`, stores consumer offsets. Adds Netty and Micrometer-style transitive jars to the test classpath only (list the transitive tree in Status from `./gradlew :data-rabbit:dependencies`). It becomes `implementation` later without re-deciding the library; only the version and scope change.
- B. `amqp-client` 5.37.0: can publish to and consume from a stream queue over AMQP 0-9-1, but gives no stream-protocol publishers, no `queryStreamStats`, and is a second client we will not ship. Not recommended.
- C. No dependency: run `pivotalrabbitmq/stream-perf-test` as a second Testcontainers `GenericContainer` on a shared network to create publishers and consumers. No jar added, but a second image, TLS options unverified, no `queryStreamStats`, and offsets/consumers cannot be controlled precisely. Fallback only.
Recommendation: A with 1.12.0, test scope. If the product owner prefers to wait for 1.13.1 to pass two weeks (after 2026-11-17), start with C or run the non-client questions first.
Nothing is blocked now: S1 is decided (A), so questions 2 and 3 run in full.

**S2: Testcontainers version.** Facts: 1.21.3 pinned, 1.21.4 is the last 1.x, 2.0.5 is current (2.x renames artifacts, may change `RabbitMQContainer` package and `withPluginsEnabled`, may drop the Docker API workaround or not). Options: (a) stay on 1.21.3 and record the exact message (default, no decision needed); (b) bump to 1.21.4 (patch, no rename); (c) move to 2.0.5 (older than two weeks), done as a separate commit in this task only if the spike shows the warning is fixed there and the `api.version=1.43` pin still works.
