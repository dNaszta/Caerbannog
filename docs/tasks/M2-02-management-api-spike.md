## Goal
We know, from a real RabbitMQ 4 broker with the stream plugins over HTTPS and TLS, exactly which management API endpoints and fields give the stream list, publishers, consumers, offsets and super stream partitions, what a non-admin sees, and whether offsets need the stream protocol. The answers are asserted by `@broker` spike tests and written into this Status and `docs/spec.md`, so M2-03 can be briefed without guessing.

### How to publish and consume without a new dependency (verified: repo has no `stream-client` or `amqp-client` in any `build.gradle.kts`)
- Publishing messages to a stream: declare the stream via `PUT /api/queues/%2F/{name}` with `{"durable":true,"arguments":{"x-queue-type":"stream"}}` and publish through `POST /api/exchanges/%2F/amq.default/publish` (routing key = queue name). The broker publishes over AMQP internally, so no client is needed. Expected to work; confirm (and confirm `/api/exchanges/.../publish` is allowed for the stream type).
- Publishers and consumers on a stream exist only while a client holds a stream-protocol (or, for consumers, AMQP) connection. The management API cannot create them and `rabbitmqctl` cannot either. So question 2 for non-empty results, and `queryStreamStats` in question 3, cannot be completed without a client. Empty results, endpoint existence, non-admin status codes and everything in questions 1, 4, 5, 6, 7 can.
- Fakes: nothing in this spike is a fake. Everything is a real broker, so the whole spike needs Docker; tests are skipped without it (`@Testcontainers(disabledWithoutDocker = true)`). Fakes come later in M2-03 (`FakeStreamCatalog`) built from the recorded JSON.

### Answers to the seven questions (all asserted in the test class)

**1. Stream list.** Endpoints: `GET /api/queues` (bare JSON array without paging params; object `{items,page,page_size,page_count,item_count,filtered_count,total_count}` with `page`), `GET /api/queues/{vhost}` (same), `GET /api/queues/{vhost}/{name}` (full object). There is NO stream-specific listing: `/api/streams` and `/api/stream` are 404. Streams are queues with `type == "stream"`.

Single object, stream with 1000 messages (fixture `queue-stream-with-data.json`), name: JSON type:
`name` string; `vhost` string; `type` string ("stream"); `state` string ("running"); `messages` number (live count, see 3); `messages_ready` number (equals `messages`); `messages_unacknowledged` number (0); `consumers` number; `memory` number (Erlang process memory, NOT disk size); `segments` number (segment files); `first_timestamp` number (ms epoch of the first retained entry); `durable`/`auto_delete`/`exclusive`/`internal` boolean; `arguments` object; `effective_policy_definition` object; `policy` and `operator_policy` null when none; `node`, `leader` string; `members`, `online` array of node names; `readers` object (node -> number); `consumer_details` array; `message_stats` object (`publish`, `publish_details`); plus `garbage_collection`, `reductions`, `deliveries`, `incoming`, `*_details`.
`arguments`: `x-queue-type` string, `x-max-age` STRING ("7D"), `x-max-length-bytes` number, `x-stream-max-segment-size-bytes` number, `x-queue-leader-locator` string (set by client creator and super stream, not by PUT).
ABSENT for streams: `message_bytes` (and every `message_bytes_*`), `publishers`, `consumer_utilisation`, any first/last/committed offset, any last timestamp. There is NO size-in-bytes field: the "size" column of `Streams.dc.html` cannot come from the management API (gap for the UX; stream protocol has no size either: `StreamStats` has only first offset and committed chunk id).
The list item (paginated or not) is slimmer than the single object: it has the fields above but NO `policy`, `operator_policy`, `consumer_details`, `garbage_collection` (use `columns=...,policy` to get `policy`). A just-declared queue has no `messages` key until its first stats emission (about 5 s). Nullable: `policy`, `operator_policy` (null), `leader`/`members`/`online`/`readers` may be missing on non-stream queues (classic has none, quorum has them).

**3. First and last offset.** The management API has NO first offset, last offset, committed offset or last timestamp, on the queue object or on `/tracking`. It has only `first_timestamp`. First offset comes from the stream protocol: `Environment.queryStreamStats(stream)` returns `firstOffset()` and `committedChunkId()` (no timestamps, no size). Measured: (a) 1000 messages published one by one (each its own chunk): first 0, committed chunk id 999, management `messages` 1000 = 999 - 0 + 1. (b) 100 messages batched by a client producer: `committedChunkId` was 36 (it is the START offset of the last committed chunk, not the last message offset), management `messages` 100. So the `03` formula "committed minus first plus one" UNDERCOUNTS with batched chunks and must not be used; the management `messages` is exact. (c) After a consumer stored an offset, management `messages` became 101 and committedChunkId 100: a tracking entry occupies an offset (this is the @gate-M2 tolerance: management `messages` counts tracking entries, so it can exceed the number of user messages by the number of offset stores/named consumers). (d) After retention (1 MB max length, 500 KB segments, 3000 x 2000 B): `firstOffset` moved to a positive value and management `messages == published - firstOffset` exactly. So: last written offset = firstOffset + messages - 1 (next offset to be written = firstOffset + messages) (derive), count = management `messages`, first offset = stream protocol only. Management alone cannot give first offset; a stream-client connection is needed for first offset (D4: stream protocol for first offset; D5: client needed in production for offset display, not for counts).

**4. Search by name.** `GET /api/queues?page=1&page_size=N&name=...&use_regex=true|false` filters on the NAME only, server side, with and without regex (without `use_regex` it is a substring match). Pagination fields (all numbers): `page`, `page_size`, `page_count`, `item_count`, `filtered_count`, `total_count` (+ `items`). 13 items at page size 5: page_count 3, last page item_count 3. Maximum `page_size` is **500** (spec assumption confirmed): 501 gives 400 `{"error":"invalid_pagination_parameters"}`; `page_size=0` and `page=0` also 400; a page beyond page_count gives 400 `page_out_of_range`. Invalid regex is not an error: 200 with `filtered_count` 0. `sort=name&sort_reverse=true` works; `columns=a,b,c` trims each item to those fields (and only those that exist yet). There is NO server-side streams-only filter: `type=stream` and `queue_type=stream` are silently ignored. Conclusion: name filter yes (server side, optional regex); streams-only is client side on `type == "stream"` (so a server-filtered page can contain fewer streams than `page_size`; the app must page through and filter, or fetch with `columns=name,type` and a large page).

**5. Super streams.** `rabbitmq-streams add_super_stream <name> --partitions 3` exists in the image (also `--binding-keys eu,us`, `delete_super_stream`). Result: three ordinary stream queues `<name>-0`, `<name>-1`, `<name>-2` (with `--binding-keys eu,us`: `<name>-eu`, `<name>-us`), `type` "stream", arguments only `x-queue-type` and `x-queue-leader-locator: balanced` (NO marker on the queue). An exchange `<name>` of type **direct** (not a special type) with argument `x-super-stream: true` (boolean). Bindings `GET /api/exchanges/{vhost}/{name}/bindings/source`: destination `<name>-<key>`, `destination_type` queue, `routing_key` = binding key ("0","1","2" by default), `arguments.x-stream-partition-order` number (0-based, defines the order). Rule for M2-07: super stream = exchange with `arguments.x-super-stream == true`; its partitions = destinations of its bindings, ordered by `x-stream-partition-order`; the partition queues carry no marker, so a flat `/api/queues` list needs one extra call (`/api/exchanges` or `/api/exchanges/{vhost}/{name}/bindings/source`) to mark and group them; do not infer from the name alone (naming is convention).

### M2-02c correction (spike test stability, 2026-11-04)
`Q2 publisher and consumer rows ...` failed about 1 run in 6 (`offset` was 10, not 9). Investigated on the real broker (4.4.0, stream-client 1.12.0). Facts, replacing the imprecise statements above:
- The consumer row's `offset` is NOT stable right after delivery. `consumed` is live, but `offset` is refreshed with the periodic stats: until the first refresh (0.8 to 5 s) the row shows `offset` = 10 (the next offset) with `offset_lag` 0, afterwards 9 (last delivered) and the settled lag. Seen for unnamed, named and no-tracking consumers alike. A client must not treat the first row as final; the test now waits for the settled row (`consumed` 10, `offset` 9, `offset_lag` 1).
- The tracking entry was not mysterious: the stream client's manual tracking strategy has a safety net (`OffsetTrackingCoordinator.ManualTrackingTracker.flushIfNecessary`, about 1 s after consuming): a named consumer that never stored gets `store(lastRequestedOffset)` and that field starts at 0, so `tracking.offsets` = `{"spike-cons": 0}`. With the default (auto) tracking a named consumer gets `store(9)` after about 1 s. With `noTrackingStrategy()`, or with an unnamed consumer, nothing is stored: `messages` 10, `offset_lag` 0, `tracking.offsets` empty.
- Every stored offset is a write to the stream: a tracking chunk takes offset 10, it is not delivered to the consumer (last delivered stays 9), the committed chunk id becomes 10, so `offset_lag` = 10 - 9 = 1 and management `messages` = 11. It is deterministic; only when it becomes visible varies (`offset_lag` and `messages` refresh separately, lag 1 was seen before `messages` 11 and the other way round).
- Consequence for M2-06 "Caught up": a caught-up consumer reads lag 0 if it never stored an offset and lag 1 (per stored-offset entry written after its last read) if it did, so the architect's option (a) "0 or 1 is Caught up" is what the broker does. Consequence for D4/D5 and M3: a browsing consumer must be unnamed (or `noTrackingStrategy`), otherwise browsing writes to the stream, which breaks the "browsing never changes broker state" safety rule. Streams that other applications' named consumers use will always carry tracking entries in `messages`.
- Not changed: fixtures (the settled values equal the saved ones), the `@gate-M2` tolerance statement (still true, now with the cause).
