## Goal
On the Permissions tab an administrator picks an action (publish, read, configure), a virtual host, a name and, optionally, a routing key, presses Check, and sees whether the patterns the broker returned would match, which pattern and kind decided, where the patterns came from, and that this is a prediction. The pure `AccessMatcher` agrees with a real broker on a differential case table; anything it cannot be sure of is reported as "Pattern could not be read.", never guessed.

## Why
Spec "Access view (M10)", goal 2, "No probing", risk "the match preview is a prediction" (a wrong "would match" is worse than none). Wording approved by the owner (AQ5, 2026-11-25). The matcher is also the engine of `caerbannog_check_access` (`M10-08`).

## Scope
In, part A (core, data-rabbit tests; no UI):
1. **`AccessMatcher`** in `core/access`, a pure function over `UserPermissions` (as merged in M10-03: `PermissionRow`, `TopicPermissionRow`, `PatternCell` with `text`, `reading`, `hidden`) and an `AccessQuestion`. No gateway, no `java.*`, a regex engine behind a small interface in `core` (`PatternEngine`: `compile(text): CompiledPattern | Rejected`, `CompiledPattern.containsMatchIn(name)`), the library per "Library proposal" (PD-2 decided: a library, not `kotlin.text.Regex`).
   - `AccessQuestion(action, vhost, name, routingKey: String?)`. `action` is a sealed type: `PublishToExchange`, `ReadFromQueue`, `Configure`, `BindQueue(queue, exchange)`, plus the stream forms `PublishToStream`, `ReadFromStream` (same patterns, S-I). The UI offers the first three only (mockup Q3; PD-1 decided (a) by the owner, 2026-11-27); the other forms exist for the unit table, the live test and `caerbannog_check_access`.
   - Result, sealed: `WouldMatch(hits: List<Hit>)`, `NoMatch(deciding: Hit)`, `UnreadablePattern(kind)`, `PermissionsNotReadable(reason)`. `Hit(kind: PatternKind, pattern: DisplayPattern, exchange: String?)`; `PatternKind` = configure, write, read, topicWrite, topicRead. A vhost with no permission row is `NoMatch` with the pattern shown as "no permission" (same cell wording as the table).
   - The action-to-kind mapping is a data table in code, one line per rule with the S-I row id as comment: publish to an exchange = write; read from a queue = read; configure = configure; bind = write on the queue AND read on the exchange; default exchange asked as `amq.default`, never as the target queue; publish to an exchange that has a topic row for the vhost = write AND topic write on the routing key; with no topic row nothing is limited (measured).
2. **Check order, fixed:** (a) permissions not available (locked, token, not loaded) returns `PermissionsNotReadable` before anything else; (b) the vhost row; (c) for each needed cell, `hidden` FIRST: `SecretGuard.HIDDEN` is the word "hidden", which is a valid regular expression and would match any name containing "hidden"; a hidden cell is always `UnreadablePattern`; (d) the empty pattern (`PatternReading.NoPermission`) is "no permission", a `NoMatch` that allows nothing (measured), not an error; (e) the engine compiles the pattern and the pattern is not on the "differs from the broker" list of the live rows, else `UnreadablePattern`; (f) unanchored, case-sensitive search (`containsMatchIn`). An answer is `WouldMatch` only when every needed cell matched; the first failing cell is the deciding `Hit` of `NoMatch`, but an unreadable cell anywhere wins over a `NoMatch` of another cell (no half answers).
3. **What the engine reads is what is predicted, and the live rows decide.** The engine (OQ-1) reads a pattern the same way as the broker's Erlang `re` (PCRE) or it does not: a pattern the engine rejects (syntax error or a construct it does not support) is `UnreadablePattern`. A second, small, data-only list in `core` (`KnownDivergences`: pattern shape and the live row that proved it) turns constructs that the engine accepts but the live differential rows show to differ from the broker into `UnreadablePattern` too; it starts empty and every entry names a row. The old allow-list is dropped. Work bound stays: pattern at most 256 characters, name and routing key at most 255 characters (the broker's limit); over a limit is `UnreadablePattern`. A linear-time engine needs no step budget; a backtracking engine needs one or a rule against nested quantifiers (decided with OQ-1).
4. **The case table as a fixture** in `core-testing` (`AccessMatchCases`): the 137 S-I rows (`data-rabbit/src/test/resources/fixtures/m10-00/s-i-pattern-rows.tsv`, columns `permission, pattern, name, operation, outcome`; copy it into `core-testing` resources or read it from one agreed location, one source only, a test fails if the two differ) PLUS new rows for the unmeasured differences (below), at least 190 rows in all. Used by the fast matcher test and by the live test.
5. **Live differential test** `RealBrokerAccessMatchTest` (tags `broker`; not `spike`; in `:data-rabbit:brokerTest`; Testcontainers; throwaway users and vhosts removed afterwards). For each row: a user with that pattern as the one permission under test and `.*` for the others, a fresh connection (permissions are checked per connection, as in the spike), the real operation (publish, `basic.get`, declare, bind, stream publisher), the broker's answer against the matcher's answer. Three row classes: **allowed/refused** (matcher `WouldMatch` / `NoMatch` must equal it); **cannot be set** (the broker answers 400 `invalid_regexp` for `PUT /api/permissions`: the matcher must say `UnreadablePattern`); **engine differs** (rows where the engine accepts the pattern but its answer differs from the broker: the matcher must say `UnreadablePattern`, through `KnownDivergences`; the row stays in the table with both answers so a later engine upgrade starts from a fact; a pattern the engine rejects needs no row but is listed with the broker's answer). A disagreement fails the test and names the row (permission, pattern, name, operation, broker, matcher). Reuse the spike's operation runner by extracting it into a shared test helper in `data-rabbit/src/test`; `RealBrokerAccessSpikeTest` stays green. Keep it out of `RealBrokerM7GateTest`/`RealBrokerM8GateTest`; the gate hook for this table is `M10-09`'s job and reuses `AccessMatchCases`.
   New rows to measure first (all unmeasured, spec "Measured facts of M10-00"): character classes (`[a-z]`, `[^a]`, `[[:alpha:]]`, which Java reads as a union of characters and PCRE as a class), `\d` `\w` `\s`, lookahead, named groups (`(?<n>x)`, `(?P<n>x)`), `\x41`, `\p{L}`, `(?s)` `(?m)` `(?x)`, backreference, lazy and possessive quantifiers, `{2}` `{1,3}`, `a|b` against `^a|b$`, `$` with a trailing newline in the name, `\A` `\Z` `\z`, a non-ASCII name against `^.$` (Erlang byte versus Java character) and a non-ASCII pattern, a very long name, an empty routing key against a topic pattern (`^a\..*` and `.*`), a topic row for a custom (non-`amq.topic`) topic exchange, publish to a topic exchange with both the vhost write and the topic write failing in turn, configure on an exchange and on a queue, read topic permission on consume. Which Erlang/PCRE the pinned image has is recorded in the test output (not assumed).
Out of scope: probing any operation from the app (non-goal), token users (`M10-05`), MQTT topic translation (`a/b` to `a.b`; the preview takes an AMQP routing key), queue policies and Shovel permissions, probing, a second regex engine.

In, part B (UI; after M10-03b merged):
6. **The form and the verdict** below the topic table of the Permissions tab (`ui/access`), a `MatchPreviewState` and `MatchPreviewViewModel` in `core/access` in their own files (not in `PermissionsState`). It takes the already loaded `UserPermissions` plus the reason when none are available; one read-only accessor on `PermissionsViewModel` is the only change to a M10-03 file. Pressing Check calls `AccessMatcher` only: no gateway call, no request (test asserts the fake gateway's request log is unchanged).
7. **Form fields:** action (three choices, as drawn), virtual host (the user's hosts, as drawn), name (label "Exchange" for publish, "Queue" for read, "Name" for configure: see PD-3), routing key (optional, shown for publish). An empty exchange name for publish means the default exchange: after Check the box shows `amq.default`, never an empty box (mockup note). Typed text passes `SecretGuard` before it is echoed in a verdict (a user may paste a token or the profile password into the box): the echo becomes "hidden".
8. **Verdict:** icon and the four approved verdicts (plus "Would match (topic permission)."), the sentence naming the pattern, kind, name and virtual host, "Patterns read from the broker." (the label of the source, as `PermissionsState.readLabel` does for the table), and the note "Prediction from the patterns above; the broker decides. Check sends nothing to the broker." next to every verdict. A hidden pattern is shown as the hidden marker, never its text. The verdict is cleared when the chosen user, the shown permissions or the connection state change (a stale prediction is not shown against new data).

## Design notes
- Modules: `AccessMatcher`, `PatternSupport`, `AccessQuestion`, result types, `MatchPreviewState/ViewModel` in `core/access` (no `java.*`, `commonMain`); `AccessMatchCases` and its resource in `core-testing`; `RealBrokerAccessMatchTest` and the shared probe helper in `data-rabbit/src/test`; form in `ui/access`; wiring in `desktopApp` (none expected: no new gateway call).
- Sealed results, immutable data classes, no boolean that switches behaviour, no `!!`; the verdict text built in `core` as pure functions (as `PermissionsTexts` does), composables thin.
- Read-only: the preview adds no request. The live test is the only new broker traffic and it is test code against a throwaway container (GET/PUT/DELETE on its own users; never the product's gateways for writes). Secrets: the live test's passwords never enter a fixture (`AccessFixtureGuardTest` stays green); verdict texts pass `SecretGuard`.
- Dependency placement: see "Library proposal", "Where it lives".
- Version risk: the matcher is verified on the pinned image (4.4.1, Erlang 29.1.2 per the spike). Older Erlang uses an older PCRE. The engine is only as good as its agreement with Erlang `re` on that image; run the table also on the oldest 4.x image the repo already pins for other tests if one exists (not checked by the architect), else record it as a known limit.

## Library proposal (OWNER QUESTION OQ-1, 2026-11-27)
Facts checked on Maven Central and GitHub on 2026-11-27 (poms and metadata read, not recalled). The newest versions are newer than the Maven search index shows; the table uses the metadata.

| | A. RE2/J | B. Joni | C. PCRE4J |
| --- | --- | --- | --- |
| Coordinates | `com.google.re2j:re2j:1.9` (runtime dependency `org.jspecify:jspecify:1.0.1`, annotations only) | `org.jruby.joni:joni:2.2.12` plus `org.jruby.jcodings:jcodings:1.0.67` | `org.pcre4j:regex:1.0.1` plus `api`, `lib` and a backend (`jna` or `ffm`) |
| Licence | "Go License" in the pom = BSD-3-Clause text (Google, derived from Russ Cox's RE2); GitHub reports NOASSERTION; the LICENSE file begins with the Go Authors BSD notice (read) | MIT (pom and GitHub); jcodings MIT on GitHub (its pom lists no licence) | LGPL-3.0 (pom, GitHub) |
| MIT-compatible | yes (permissive, notice needed) | yes | not as bundled: LGPL, plus a native PCRE2 library for each OS; contradicts the "permissive only" rule of `THIRD_PARTY_NOTICES.md` |
| Maintenance | Google; GitHub pushed 2026-11-26, Maven 1.9 released 2026-11-25 | JRuby; pushed 2026-11-20, 2.2.12 released 2026-11-20 | one author; pushed 2026-09-09; 1.0.1 |
| Jar size | 116 KB, no real dependency | 233 KB plus jcodings (size not read) | 26 KB plus native libraries |
| Compatibility with Erlang `re` (PCRE) | Not PCRE. RE2 syntax: a large Perl-like subset, linear time. It rejects lookaround, backreferences and possessive quantifiers (the README says features that cannot be linear are absent), so those become "Pattern could not be read.", the safe direction. Differences for the rest (for example `$` before a final newline, `\p{L}` outside UTF mode, non-ASCII: UTF-16 characters against Erlang bytes) are exactly what the live rows test. No catastrophic backtracking, so no step budget | Not PCRE either: Oniguruma with a Perl syntax option; accepts lookaround, backreferences, named groups; works on bytes like Erlang (a plus for non-ASCII); backtracking, so a step budget or a nested-quantifier rule is needed; more constructs accepted, so more rows can differ | The same engine family as Erlang `re` (Erlang's `re` is PCRE; OTP 28 is said to use PCRE2, NOT verified). Closest answer, but native code |
| Works from `core` | JVM jar (`java.util.regex`-like API in `com.google.re2j`) | JVM jar | JVM jar, native |

Honest note on `core`: `core` is Kotlin Multiplatform with one `jvm()` target, and commonMain has no regex library at all (only `kotlin.text.Regex`, which on the JVM is `java.util.regex`). A library from A, B or C is JVM-only. It fits in two ways, both keep `commonMain` free of `java.*` and of the library's types: (1) recommended: the `PatternEngine` interface and the matcher in `core` commonMain; the implementation `Re2jPatternEngine` in `core` `jvmMain` behind `expect fun defaultPatternEngine()`, so the fast matcher test over the 190 rows runs in `core:jvmTest` with the real engine; the library is a `jvmMain` dependency of `core` only; (2) the interface in `core`, the implementation in `data-rabbit` (the matcher test with the real engine would then live in `data-rabbit`, and every composition root, `desktopApp` and `mcp-server`, must wire it; `data-rabbit` is meant to know RabbitMQ and Paho, so a regex engine there blurs its role).

Where it lives: option (1) above. `PatternEngine` is also what the unit tests fake to test the order of checks without a regex.

Recommendation: **A, RE2/J**, with the live differential test deciding what is trusted. Reasons: permissive licence and tiny, one pure-JVM jar with no native code (installers stay four, no per-OS library); it fails safe (a construct it does not support is "could not be read", never a guess); no catastrophic backtracking; a boolean "does it contain a match" search is the one question where RE2 and PCRE agree on the large common subset; the owner's goal of "PCRE-compatible" is met as far as the live rows show, and `KnownDivergences` records where not. Second choice B (closer on bytes and constructs, but accepts more and so risks more divergence, and needs a step budget). C is not recommended (LGPL, native library per OS, 0.x/1.0 single maintainer) unless the owner wants exact PCRE2 behaviour above all; then the cost is shipping `libpcre2` for macOS, Windows and two Linux packages. Not verified: that RE2/J agrees with Erlang `re` on any given row (that is the live test), the size of jcodings, and which PCRE the pinned broker uses.
