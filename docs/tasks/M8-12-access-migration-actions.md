# Access migration: vhosts, users, permissions (umbrella, cut into three tasks)

Milestone: M8    Depends on: M8-04, M8-05, M5-08 (all merged, main `ce58253`)    Size: L, therefore CUT: `M8-12a`, `M8-12c`, `M8-12b` (each M or S)

LEAN (owner, 2026-11-11): the smallest slice that lets the owner stand up on 4.x the virtual hosts, users and permissions that the migrated topology needs. No per-user review, no guest acceptance path, no password entry, no extras.

## Goal
From a full 3.x export (a file, or the live 3.x connection with an administrator user) the app generates ONE access migration (virtual hosts, users with their exported password hash, permissions, topic permissions) that is applied on the 4.x broker through the existing Migrations screen, safely: hashes are secrets that pass through and are never shown, applying needs an administrator and Full control, nothing existing is overwritten.

## What exists already (merged code, so this is NOT rebuilt)
- Parsing: `DefinitionsModel` reads virtual hosts, users (`passwordHash: SecretValue?`, `hashingAlgorithm`, tags), permissions, topic permissions from a full export (file or `GET /api/definitions` of the live 3.x connection, `ManagementThreeXReads.definitions`). A per-virtual-host export has none (P17).
- Analysis: `AccessRules` already gives the report findings (declare vhost/user/permissions/topic permissions as Info, `guest` as Warning with default Skip, administrator tag warning, blockers for a missing or unsupported hash algorithm with the allow-list sha256, sha512, md5).
- Generation: `MigrationGenerator` writes topology migrations only (`ACCESS_NOTE`: "Handled by the access migration"); `ConversionReview` decides queues, exchanges, policies, operator policies only.
- Apply: the M5-08 Migrations screen applies a folder of files; `MigrationRunner` has `ApplyOutcome.Conflict` and `FailureKind.Conflict`; `ManagementTopologyMigrationExecutor` with `ExecutorPathAllowList`; `AtomicFileWriter(ownerOnly)`.
- NOT there: the four access actions in the migration format and parser, the runner rules for them (administrator tag, V1 exemption), the tags of the connection user in core, the executor requests and the hash comparison, the generation of the access file, the secret-file warning, owner-only write of a file that holds a hash.

## Design (decided; every product point already decided by the owner is marked P#, new ones are D#)
1. **Same flow, no separate path.** The access migration is an ordinary migration file (M5-04 format) written by the SAME "Generate" of the review (M8-06b), into the same migrations folder, numbered BEFORE the topology files of that generation (lower version, P10), and applied from the same Migrations screen with the same history, checksum and Conflict handling. No second apply path, no second file format.
2. **No per-item review for access (D1, recommended).** The generator takes everything the report proposed as Info and nothing else: all virtual hosts, every user that has a supported hash, their permissions and topic permissions. Not generated and LISTED in the generation result ("not migrated"): `guest` (D2) and every user that is a blocker (no algorithm, unsupported algorithm: "set a new password on the broker", P12), and the permissions of those users ("left out"). Users without a password hash (external authentication) are listed as not migrated too (the app never invents a password). A user that the owner does not want cannot be skipped one by one in v1; they delete the line from the generated file by hand or do not apply it.
3. **Format.** Four new actions, "up" only, no delete action of any kind: `declareVhost(name, description, tags, defaultQueueType?)`, `declareUser(name, passwordHash, hashingAlgorithm, tags)`, `setPermissions(vhost, user, configure, write, read)`, `setTopicPermissions(vhost, user, exchange, write, read)`. Order inside the file: vhosts, users, permissions, topic permissions. They are "broker-level": `MigrationAction.isBrokerLevel`.
4. **Secrets.** `passwordHash` is a `SecretValue` (exists: no `equals`, redacting `toString`) in `DeclareUser`. The file on disk holds the real value (the broker needs it). Everywhere else a hash is replaced by "hash hidden": dry run rows ("Declare user svc (administrator), password hash hidden"), the Migrations screen raw view of the file (D4), parse and apply error strings, history (version and checksum only), logs, the compatibility report, MCP output (the dry-run tool shows `Declare user svc`). A migration file that holds a hash is written with `ownerOnly = true` (P13; best effort on Windows) and saving or exporting it shows the secret-file warning (D3). The app never computes, generates, types or stores a password or hash.
5. **Guardrails (P2, spec "Users, virtual hosts and permissions in the migration").** Each broker-level action needs the `administrator` tag of the 4.x connection's user (from `GET /api/whoami`, read with the permission check and kept in the session result; not a secret) AND the level Full control; the configure permission and the V1 single-vhost rule do NOT apply to them (P10); Read-only blocks everything as before. The rule is in `MigrationRunner.dryRun` per action (a topology action keeps its old rules), so a file that mixes both is checked action by action. Disabled apply shows the reason ("needs the administrator tag" or "needs the level Full control").
6. **Idempotency, conflicts, comparison.** Identical existing vhost, user, permissions or topic permissions = no-op. A different user (hash or tags), different permission patterns or different topic permission = `Conflict` (existing `ApplyOutcome.Conflict`): the apply stops, says what differs, never shows a hash; nothing is overwritten. An existing VIRTUAL HOST is left as it is whatever its description, tags or default queue type (D5: `/` always exists with its own settings; the migration never changes a vhost). The user hash is compared before writing (4.4 overwrites a different hash silently): the hash of the existing user is read from the target's `GET /api/definitions` through the redacting parser (it also holds Shovel URI passwords, which the parser drops), kept in memory for the comparison only (S-M). The request always sends `hashing_algorithm` with the hash.
7. **Where the executor writes:** `PUT /api/vhosts/{name}`, `PUT /api/users/{name}`, `PUT /api/permissions/{vhost}/{user}`, `PUT /api/topic-permissions/{vhost}/{user}` on the HELD 4.x connection only (a 3.x connection is never written to, existing rule; `GET /api/definitions` read only for the comparison). `ExecutorPathAllowList` gets exactly these four PUT shapes and the one GET; no DELETE of any of them (a test asserts none).
8. **MCP (D-none).** No tool creates, applies or reveals access data (spec decision 2026-11-09, `M5-09`): the read-only `caerbannog_dry_run_migration` shows `Declare user <name>` without a hash, the analysis tool already shows no hash. No change to `:mcp-server`; a test asserts the dry-run output of a migration with a hash has none.
9. **Test plan.** Core and acceptance with fakes first (`@fake-broker`); the real proof (a hash from 3.13 lets the user log in on 4.x, a second apply is a no-op, a different hash is a conflict) is ONE live class in `M8-12c` (`@broker-3x`, two containers). Per step run only the affected module: `:core:jvmTest --tests '*Access*'`, `:acceptance-tests:test --tests '*AccessMigration*'`; the live class `./gradlew :data-rabbit:brokerTest --tests '*RealBrokerM8Access*'` once in step 4 of `M8-12c`. Not run: the other brokerTest classes (no shared transport change), screenshots only for the two UI lines of `M8-12b`.

## Owner decisions (ask in one go)
- **D1. Review of access items.** (A) None in v1: everything with a usable hash is generated, the rest is listed as not migrated (recommended; lean, and the listing tells the owner what to do by hand). (B) Each user is a review item with Accept and Skip like a queue. Recommendation A. B costs a larger review (users as `ReviewItem`s, counts, mockup changes) and can be added later.
- **D2. `guest`.** (A) Never generated, listed as not migrated (recommended). (B) P11 as decided: skipped by default, accepting it asks for an explicit confirmation that it carries a publicly known password. Recommendation A: nobody needs `guest` with the default password on a new production broker, and B needs a confirmation UI. This narrows P11; the owner decides.
- **D3. Secret-file warning text.** Proposed: "This file contains password hashes. Anyone who has it can try to guess the passwords offline. Keep it secret: do not commit it to git or put it in a shared or synced folder." shown in the generate result when a file has hashes and again on "Export the files". Options: approve, edit. Recommendation: approve.
- **D4. Raw view in the Migrations screen.** (A) Show the file with every hash replaced by "hash hidden" (recommended). (B) Show it as is. Recommendation A: it only hides the value in the display; the file keeps it.
- **D5. An existing virtual host.** (A) Left as it is, whatever its description or tags (recommended). (B) A different description or tags is a conflict. Recommendation A: `/` always exists on 4.x with its own settings and a conflict on it would block every access apply.
Already decided, no question: P2 users with hashes are included, P10 broker-level actions exempt from V1 and in their own file applied first, P12 the algorithm allow-list and the manual step, P13 owner-only file, administrator tag plus Full control, conflicts never overwrite, no MCP tool, accepted risks of P2 (credential-equivalent file, old passwords come back alive, half-way failure leaves some created and the rerun is a no-op). Technical, decided by the architect: tags and permission patterns are carried verbatim; permissions of a user that is not declared are left out and listed; `description`/`defaultQueueType` of a vhost go into `declareVhost` only when the export has them (S-K).
