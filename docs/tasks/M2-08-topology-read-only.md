### The graph (T2)
Owner chose a graph for bindings. A graph of exchanges, queues and bindings has no mockup and no existing component, so it is a design, a layout rule and a drawing approach. Nothing is added to the build now.

Architect's technical rulings (no owner input): (1) the graph model is a pure function in core, `bindingGraph(exchanges, queues, bindings, focus, limits): BindingGraph` (nodes: exchange, queue; edges: binding with routing key and destination type; the default exchange and its implicit bindings are NOT in the input unless the user switches them on); (2) the layout is a pure function `layout(graph): Positioned` in core, no Compose, testable with plain assertions (left-to-right layers: source exchanges, exchange-to-exchange chains by depth, then queues; ordering inside a layer by name to be stable between refreshes; no crossing minimisation beyond a stable sort); (3) the view draws nodes as ordinary focusable composables positioned by the layout (so keyboard, focus order and accessibility semantics come with them) and edges on one Canvas behind them; (4) scale limits are part of the model, not of the drawing: the graph never shows the default exchange by default, never more than 60 nodes (constant, named), and offers a focus: a chosen exchange or queue with its neighbours to depth 2, or the filtered subset; when a view would exceed the cap it draws nothing partial but says "N more bindings; choose an exchange or narrow the filter" (same spirit as "a partial number is never shown"); 1000 queues bound only to the default exchange therefore never reach the drawing; (5) edge labels are the routing key, ellipsised with the full text in a tooltip and in the table; (6) a refresh keeps positions where the node set is unchanged (stable layout), so the graph does not jump every 5 s.

Tests: BDD stays plain text (scenarios below, run against the core model); unit tests on the model builder (focus, depth, cap, default exchange off) and on the layout (layers, order, no overlap, stable across refresh); UI tests on the node composables by test tag (focus, keyboard, text, one node per exchange and queue in the cap); two screenshot tests (a small graph, the "too many, narrow it" state).

Accessibility: nodes are focusable composables with a content description ("exchange events, topic, 2 bindings"), Tab/arrow moves through them in layer order, Enter selects (shows the node's bindings in the side sheet); the table is the complete fallback and stays one switch away.

## Goal
A connected user opens Topology in the drawer and sees, for the connection's virtual host (and, through a switch, any other virtual host the user may see), the quorum queues with their statistics, the exchanges and the bindings, refreshed like the stream list, with the reason when the screen is locked; nothing on the screen changes the broker or touches a queue's messages.

## Why
Spec "Goals and scope" (quorum queue topology and statistics), "Screens and UX" (Topology and queues), "Connection lifecycle" (D2 stale rows, D3 refresh only while shown), "Topology migrations and permission guardrails" (what the screen says when locked), "Management API facts". Scenarios: `09_topology_queues.feature` (the @M2 ones) and the three `@needs-M2` scenarios in `02_permission_check.feature`. Rule protected: queue messages are never read, got or purged; topology changes stay M5.

## Design notes
Reuse, do not copy:
- **Gateway.** A new core interface `TopologyCatalog` (package `dev.caerbannog.core.topology`), not new methods on `StreamCatalog` (that interface is stream-specific and the two have different failure shapes). Methods: `queues(vhost, page)`, `exchanges(vhost)`, `bindings(vhost)`, `queueDetail(vhost, name)`; all return the existing `CatalogResult<T>` (`NotAuthorised`, `NotFound`, `Unreachable`, `BadPaging`; no `PluginMissing` here, topology needs no plugin). No method can read a message: that is the type-level half of the safety rule; the guard test is the other half. `data-rabbit`: `ManagementTopologyCatalog` next to `ManagementStreamCatalog`, built on the same `ManagementHttp`, `ManagementRequests` (queues URL with `page`, `page_size` 500 and `columns`; `exchanges` and `bindings` already exist from M2-07) and `ManagementJson`. Fake `FakeTopologyCatalog` in `core-testing`, like `FakeStreamCatalog`.
- **Source.** `StreamSource(catalog, offsets, vhost)` gets a fourth member `topology: TopologyCatalog` (name kept; a rename is not worth the churn). `GuardedCatalog` gets a twin `GuardedTopology` (same proxy pattern, `Unreachable` when the connection is superseded). The composition root in `desktopApp` builds both from the same held connection.
- **Refresh and stale.** `TopologyViewModel` implements `RefreshTarget` and drives `RefreshLoop` (it is `internal` in core; the view model lives in the same module). Same `RefreshInterval` and `UpdatedAge`; D2 comes from `RefreshLoop.ask` (an unreachable broker keeps the rows and marks them stale). Do NOT edit `RefreshLoop`; if it needs a change, stop and ask the architect.
- **What loads when.** The queue list loads every tick (paged read over all pages of `GET /api/queues/{vhost}` as the stream list does, queues of type `stream` dropped in core, `quorum` and "other" split by `type`). Exchanges load only while the Exchanges tab is shown; bindings load while the Bindings tab is shown or a queue is selected (the queue's bindings are the vhost's bindings filtered by `destination`; no per-queue call). Reason: `GET /api/bindings/{vhost}` grows with the queue count (about 146 KB at 1000 queues in M2-07, mostly default-exchange rows), so it should not run for a user who only looks at queues.
- **Quorum fields.** Parsed fields are exactly those the spike S-A confirms; the model carries `readyMessages`, `unackedMessages` and `consumers` as nullable until S-A says otherwise, a cell of null reads "n/a" like the stream list (never 0). `membersOnline` is `online.size` of `members.size`, flagged when smaller (checked against the broker's own `online` list, never inferred from names). Policy comes from `columns=policy` on the list if S-A shows it is returned, else from `queueDetail` on selection.
- **Banner and texts.** Wording lives in core (`TopologyTexts`, like `permissionBanner`), asserted by Cucumber and Compose tests alike. The banner reads the session's permission result (`PermissionCheckResult`: `Checked`, `DeclaredByUser`, `Unreadable`) and the profile's `topologyControlLevel` (T5). The three `02` texts: no configure: "Topology is locked on this connection. The permission check found no configure permission for <user> on virtual host <vhost>, so queues, exchanges and bindings are read-only." (mockup wording); declared, not confirmed: "The broker could not confirm the permissions and still enforces its own." (the existing `DECLARED_NOT_CONFIRMED` string is reused, not duplicated). The management-tag message is new: "This user cannot read topology. Ask for the management tag." (queue and exchange lists need any management tag; verified: a no-tag user gets 401 `Not management user`, S3, "Management API facts"; the stream list's "monitoring" text does not apply here because topology needs no cross-connection view).
- **No write control.** There is no `TopologyEvents` method that changes anything; the UI has no node for edit, delete, bind, browse, get, consume or purge. UI tests assert the absence by test tag and by text.
- **UI.** `ui/.../topology/TopologyScreen.kt` and `TopologyTables.kt`, reusing `AppFrame`, the table, chip and tab styles of the stream list. No Compose import in core; no broker type in ui.

Fakes vs real: all `@fake-broker` scenarios use `FakeTopologyCatalog` and `FakeStreamCatalog`; only the 08a field spike and `brokerTest` use a real broker.
