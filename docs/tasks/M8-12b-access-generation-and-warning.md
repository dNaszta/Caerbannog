# Access migration generation, the lists and the secret-file warning

Milestone: M8    Depends on: M8-12a, M8-12c (both merged, main `1418028`), M8-06b (Generate); owner decisions D1 to D5 final (2026-11-11), D6 below    Size: M (not split)

LEAN (owner, 2026-11-11): one access file, two short lists, one warning. Nothing else.

## Goal
"Generate" in the Migrate from 3.x review also writes ONE access migration (when the export holds access data), numbered before the topology files, lists what was not migrated and which permissions were left out, writes the file owner-only and shows the approved secret-file warning (D3).

## What exists now (checked against main `1418028`)
The four actions, codecs, `redactedRaw`, the runner rules and the executor (12a, 12c); `AccessRules` findings (declare vhost/user/permissions/topic permissions as Info, `guest` Warning, blockers for a missing or unsupported algorithm, info for a user without a hash); `MigrationGenerator.generate` writes topology files only and adds a per-finding note `ACCESS_NOTE` ("Handled by the access migration (not part of this generation)") for every Access finding; `files()` numbers one file per vhost from `highest + 1`; the result panel `migrate3x-result` shows files, `leftOut`, `notes`, `vhostHint`; the save loop writes `generated.migrations` in order through `repository.importFile`; the export loop uses `ReportFileSaver.save(name, text)`; `FolderMigrationFileRepository.writeOrInvalid` writes with `ownerOnly = false`.

## Scope
In:
1. **`AccessGenerator`** (core, pure, `internal object`, next to `MigrationGenerator`; input `DefinitionsDocument`, `GenerationRequest`; output `AccessGeneration(file: MigrationFile?, notMigrated: List<NotMigratedUser>, leftOutPermissions: List<LeftOutPermission>, summary: AccessSummary?)`):
   - `declareVhost` for every virtual host EXCEPT `/` (D5), carrying only the settings the export has (`description` not empty, `tags` not empty, `default queue type` present); `declareUser` for every user that has a hash with an allow-listed algorithm and is not `guest`, tags verbatim, hash passed through (`SecretValue`); `setPermissions` and `setTopicPermissions` for those users only, patterns verbatim, and only for virtual hosts that are declared in the export or are `/`; order: vhosts, users, permissions, topic permissions (each sorted by name for a deterministic file).
   - `NotMigratedUser(name, reason)` with `NotMigratedReason`: `Guest` (D2), `UnsupportedAlgorithm(algorithm)` and `NoAlgorithm` (blockers, P12: "set a new password"), `NoPasswordHash` (external authentication; the app never invents a password). `LeftOutPermission(user, vhost)` for every permission or topic permission of a user that is not declared (one row per user and vhost, topic permissions of the same pair folded in).
   - `file == null` (nothing to write) when the document has no virtual host other than `/`, no declarable user and no permission: then no access file, no lists except `notMigrated` (a document with only `guest` still lists it). A per-vhost export (`DefinitionsOrigin.SingleVirtualHost`) gives no access data and no lists; its existing note stays.
   - The file's description: "Access migrated from RabbitMQ 3.x <source>" (same style as the topology files).
2. **`MigrationGenerator.generate`**: calls `AccessGenerator`; the access file becomes the FIRST entry of `Generated.migrations` and takes the first free number, the topology files follow (`files()` takes a start offset: access index 0 when present, topology `index + 1`); `GeneratedMigration` gets `val access: Boolean = false` (its `vhost` is the empty string; the panel shows "access"). `GenerationResult.Generated` gets `notMigrated: List<NotMigratedUser>`, `leftOutPermissions: List<LeftOutPermission>`, `access: AccessSummary?` (counts: virtual hosts, users, permissions, topic permissions; never a hash). The per-finding `ACCESS_NOTE` is REMOVED (the access file is part of the generation now) and the note "The default virtual host / already exists on 4.x and is not changed" is added when the export has `/`. The version check (`LAST_VERSION`) covers the extra file. `ConversionReview` and the review items are untouched (D1).
3. **Result data** (`GenerationReportBuilder`, `GenerationReport`): new fields `accessLine: String?` ("Access: 1 virtual host, 4 users, 6 permissions, 1 topic permission"), `usersNotMigrated: List<LeftOutRow>`, `permissionsLeftOut: List<LeftOutRow>`, `secretWarning: String?` (the D3 text, set when any generated file holds a `declareUser`). `SavedFile.vhost` is "access" for the access file. Every name is escaped with `escapeForText`. Texts in `MigrateFromThreeTexts` (D6 wording below).
4. **Owner-only write**: `FolderMigrationFileRepository.writeOrInvalid` writes with `ownerOnly = true` when the migration holds a `declareUser` (import and update; every other file keeps `false`). `ReportFileSaver.save` gets a parameter `secret: Boolean = false`; the Swing saver creates the file owner-only where the system allows (POSIX permissions at creation, best effort elsewhere, P13) when `secret` is true; the export loop passes `secret = true` for the access file. POSIX tests: mode `600` of the access file saved to the folder and the default mode of a topology file.
5. **UI** (`ui/migrate3x`, panel `migrate3x-result`): the access line, the secret warning in the warning tone (`migrate3x-access-warning`, shown on Saved and on Exported results), the two lists (`migrate3x-result-users-not-migrated`, `migrate3x-result-permissions-left-out`), the access file card with the pill "access, all virtual hosts". Mockup section 10b of `docs/ux/Migrate3x.dc.html` (drawn in this step 1) is the design. Tags and texts of the existing panel stay.
6. Report and review lines already show name, tags, algorithm and "password hash hidden" (12a/M8-03); a test asserts no hash in the `ReviewState` and the `GenerationReport`.
Out: per-user skip (D1 = B would be a new task), accepting `guest`, password entry, applying (Migrations screen, 12a and 12c), any new scenario outside feature `18`.

## Design notes
- No `java.*` in core; the POSIX permission code is in `data-rabbit` / `desktopApp` only.
- `MigrateFromThreeViewModel`: no new field or event (the generation flow already carries `GenerationReport`); keep it as small as it is.
- The hash never goes through `SessionState`, logs or texts; `expose()` gets no new caller (the codec writer writes the file).
