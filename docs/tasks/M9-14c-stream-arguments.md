# M9-14c: declareStream carries the stream's retention and leader locator, end to end

Milestone: M9 (follow-up of M9-14, M9-14b)    Depends on: M9-14b (merged), M9-05b (merged), M9-00c and M9-14 spike results (measured); independent of M9-07b, M9-08, M9-10 (it touches `StepForms` by one rule, see Scope)    Size: M (about 3 days: half a day of live rows first, then core, then data-rabbit; the cut rule for `M9-14d` is in "Order and split")

## Goal
A `declareStream` action can carry the settings `x-max-age`, `x-max-length-bytes`, `x-stream-max-segment-size-bytes` and `x-queue-leader-locator`. A migration file with them is parsed, applied (the stream is created with them), shown in the dry run and compared by the check; and the topology export writes them instead of naming them as "left out".

## Why
Owner decision O16 (2026-11-17, item 3: "do it"): "export stream retention and the leader locator". Spec A5 ("Growing `declareStream` with retention arguments is left for later") is now done for files and the export; the planner's stream form keeps writing a policy for retention (A5, Q4, unchanged). M9-14 review item 4 and the note of M9-14b ("Not in this task: the stream's retention and leader locator wait for `declareStream` arguments") named this follow-up. Measured facts it rests on: a stream the product makes carries `x-queue-leader-locator: balanced`, a stream's retention set by ARGUMENT is in its `arguments` and set by POLICY is not (M9-00c S-F1d, `docs/tasks/M9-00c-spike-results.md`), `x-max-age` is text and the other two retention keys are numbers (M9-14 E1), a super stream's partitions made by the CLI carry `balanced` (M9-14 E5, surprise 6).

## Scope
In (read against the real code on 2026-11-17):
- Model, `core`: `MigrationAction.DeclareStream` gets `arguments: Map<String, ArgumentValue> = emptyMap()` (same type as `DeclareQueue`; `description` unchanged, `detail` = the existing `argumentsDetail(arguments)` like a binding, so the dry run and the step list show "x-max-age=7D, x-queue-leader-locator=balanced" (key=value, as `MigrationTypedValuesTest` pins it)). `NamedActionCodecs.declareStreamCodec` (a `namedCodec` today) becomes a codec of its own like `declareQueueCodec`: reads `arguments` with `entry.typedEntries("arguments")`, refuses with `ARGUMENTS_INVALID` when malformed, and writes the key only when the map is not empty (`out.putTyped("arguments", ...)` already omits an empty one: pin it by a test). Backward compatible by construction: a file without `arguments` parses to the same action and is written back byte for byte (A2); `RerunSafety` and the checksum are unaffected (the action's JSON changes only when arguments exist).
- Parser rule, closed set (architect's decision, technical): the accepted keys are exactly the four above; any other key is refused with a fixed reason (`x-queue-type` is the `type`, never an argument, as for a queue; `x-dead-letter-exchange` is refused by the broker anyway, M9-00b S-D1). Value rules (CONFIRMED and tightened after step 2a: the exact table is in "Step 2a: rows confirmed", Decision 2): `x-max-age` text `[1-9][0-9]{0,8}[YMDhms]`; the two byte keys whole numbers above 0; `x-queue-leader-locator` one of `balanced`, `client-local`, `random`, `least-leaders` (S-14c-2). A stream setting the model refuses stays what the export names as "other settings" (below). ONE pure object `StreamSettingRules` in `core.migrations` (architect's decision, technical) holds the four keys, the value rules and the refusal reasons; the parser codec, the `StreamSettings` builder and `TopologyExport.writtenSettings` all call it, so a file the export writes is always a file the parser accepts: a broker value the rules refuse (a locator value the live rows do not accept, a retention text that is not `[0-9]+[YMDhms]`) is NOT written and is named as "other settings" of that stream, like an argument that cannot be typed (M9-14b step 2.5). The export never writes a file the parser then refuses.
- Executor, `data-rabbit`: the stream is still created by the stream manager (stream protocol, TLS per profile, unchanged transport and path allow-list; no new HTTP request, no `PUT /api/queues` for a stream). `core.streams.StreamManager.createStream(vhost, name)` gains the settings: recommended `createStream(vhost, name, settings: StreamSettings = StreamSettings.NONE)` with `StreamSettings(maxAge: String?, maxLengthBytes: Long?, segmentSizeBytes: Long?, leaderLocator: String?)` built by one pure function from the action's `arguments` (no primitive map crossing into `RabbitMqStreamManager`); `RabbitMqStreamManager` is the one place that maps them to the Java client's creator. EVERY implementer takes the 3-parameter signature (a default on the interface does not spare an override): `FakeStreamManager`, the fake broker's manager, `UnavailableStreamManager`, `RabbitMqStreamManager`, and `GuardedStreamManager` in `StreamSource.kt`, which MUST FORWARD `settings` (finding 1 of step 2b: `inner.createStream(vhost, name)` still compiles through the default and would silently drop the settings of every stream created through a real connection). The stream-management screen call site (`StreamManagementViewModel`, `createStream(vhost, name)`) stays on the default on purpose: its dialog creates plain streams (Out). KEEP the text of `x-max-age` as typed ("7D"): the Java client's `maxAge(Duration)` would turn it into seconds; MEASURED (S-14c-1): the raw route `StreamCreator.argument(String, String)` keeps "7D" but takes the stream protocol names (`max-age`, ..., never `x-`); the seam is decided in "Step 2a: rows confirmed", Decision 1.
- Idempotence and conflicts (architect's decision, technical, fixed now so it does not wait for S-14c-3): a `DeclareStream` WITH settings is read first, like a policy (`declarePolicy`): `GET /api/queues/{vhost}/{name}` through the executor's own `ResourceReader` (an allowed GET, no new path): 404 = create through the stream manager, then `ReadBack.verify`; 200 and `DeclaredResourceMatcher.matches` = `Success` with NO create; 200 and not = `ExecutorReasons.conflict(action)` ("exists with different settings") with NO create; an unreadable answer = `ExecutorReasons.forReply`. A step WITHOUT settings keeps today's path unchanged (create, idempotent, read back), so every old file and every existing executor test behaves as before. Safety net for the race (the stream appears between the read and the create): `Refused` from the manager is decided by FACTS, like `explainBadRequest`: one more read, 200 and matches = `Success`, 200 and not = `conflict`, otherwise `REFUSED`; never by the broker's text or code (refined after 2a). The apply never alters or deletes a stream. Row S-14c-3 does not change this design; it decides what the fake broker must answer (below) and whether the race net is ever reached.
- `DeclaredResourceMatcher` (shared by the read-back, the executor's pre-read and the check): `DeclareStream` today is `type == "stream"` only; it now also requires every DECLARED setting to be on the broker with the same typed value (the existing `argumentsContained`, `TypedJson.equal`) and nothing more: settings the broker added (`balanced` on a stream whose step declares only `x-max-age`) are ignored, a step with no settings matches any stream as today.
- Fakes pinned to facts (new, found by reading the code): `FakeManagementBroker.streamManager()` (core-testing) makes a stream with no settings and treats a repeat as `Success`; it must keep the measured answers and gain settings: it stores the declared settings as the stream's `arguments` (with `x-queue-leader-locator: balanced` added when none is declared, S-G3), and its answer to a repeat with other settings is whatever S-14c-3 measured, stated as new rows of `DeclareEquivalenceTable.streamAnswers` (`stream.create.again-other-retention`, `stream.create.again-subset`, `stream.create.again-other-locator`) that `RealBrokerM9SpikeDeclareEquivalenceTest`-style live checks and the fake both assert (the fake is never ahead of the broker).

### Decision 2: `StreamSettingRules` (one object in `core.migrations`; parser, `StreamSettings` builder and export all call it)
The existing Retention column code (`core.streams.RetentionDisplay`) defines no input shape, it only shows the broker's text (`7D`, `90m`, `1Y`, seconds), so the rule is new and is ours alone (S-14c-6). Units are those the RabbitMQ stream documentation names (Y, M, D, h, m, s). A value is accepted only if it is a text or number of the right JSON type; the rule returns a typed result with the fixed reason, never an exception. Reasons reuse the wording of the outline in `10` (written 2026-11-17, owner wording still to be approved under Q-14c-2), with two changes listed under "New wording" below.

| Key | JSON type | Rule | Refusal reason (fixed text) |
| --- | --- | --- | --- |
| `x-max-age` | text | `[1-9][0-9]{0,8}` followed by exactly one of `Y M D h m s` (case-sensitive: `7d`, `7W`, `P7D`, `604800`, `0s`, empty and `7 D` are refused; `604800s` is accepted: it is the broker's own shown form) | `stream setting "x-max-age" must be text such as 7D` |
| `x-max-length-bytes` | number | a whole JSON number, at least 1, at most `Long.MAX_VALUE` (a text, a decimal, 0, a negative are refused) | `stream setting "x-max-length-bytes" must be a whole number above 0` |
| `x-stream-max-segment-size-bytes` | number | the same rule (the broker's own bound of 3,000,000,000 is NOT checked: apply-time refusal) | `stream setting "x-stream-max-segment-size-bytes" must be a whole number above 0` |
| `x-queue-leader-locator` | text | exactly one of `balanced`, `client-local`, `random`, `least-leaders` (case-sensitive) | `stream setting "x-queue-leader-locator" must be balanced, client-local, random or least-leaders` |
| `x-queue-type`, `x-dead-letter-exchange`, `x-initial-cluster-size` and any other key | any | refused | `stream setting "<key>" is not supported` (CHANGED at step 2b gate: the key is printed only when `echoableName(key)` allows it; otherwise the reason is `stream setting is not supported`, see "Step 2b: contract confirmed") |
