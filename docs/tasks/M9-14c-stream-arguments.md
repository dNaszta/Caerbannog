# M9-14c: declareStream carries the stream's retention and leader locator, end to end

Milestone: M9 (follow-up of M9-14, M9-14b)    Depends on: M9-14b (merged), M9-05b (merged), M9-00c and M9-14 spike results (measured); independent of M9-07b, M9-08, M9-10 (it touches `StepForms` by one rule, see Scope)    Size: M (about 3 days: half a day of live rows first, then core, then data-rabbit; if step 3 passes its third day, the export part is cut out as `M9-14d`)

## Goal
A `declareStream` action can carry the settings `x-max-age`, `x-max-length-bytes`, `x-stream-max-segment-size-bytes` and `x-queue-leader-locator`. A migration file with them is parsed, applied (the stream is created with them), shown in the dry run and compared by the check; and the topology export writes them instead of naming them as "left out".

## Why
Owner decision O16 (2026-11-17, item 3: "do it"): "export stream retention and the leader locator". Spec A5 ("Growing `declareStream` with retention arguments is left for later") is now done for files and the export; the planner's stream form keeps writing a policy for retention (A5, Q4, unchanged). M9-14 review item 4 and the note of M9-14b ("Not in this task: the stream's retention and leader locator wait for `declareStream` arguments") named this follow-up. Measured facts it rests on: a stream the product makes carries `x-queue-leader-locator: balanced`, a stream's retention set by ARGUMENT is in its `arguments` and set by POLICY is not (M9-00c S-F1d, `docs/tasks/M9-00c-spike-results.md`), `x-max-age` is text and the other two retention keys are numbers (M9-14 E1), a super stream's partitions made by the CLI carry `balanced` (M9-14 E5, surprise 6).

## Scope
In (read against the real code on 2026-11-17):
- Model, `core`: `MigrationAction.DeclareStream` gets `arguments: Map<String, ArgumentValue> = emptyMap()` (same type as `DeclareQueue`; `description` unchanged, `detail` = the existing `argumentsDetail(arguments)` like a binding, so the dry run and the step list show "x-max-age 7D, ..."). `NamedActionCodecs.declareStreamCodec` (a `namedCodec` today) becomes a codec of its own like `declareQueueCodec`: reads `arguments` with `entry.typedEntries("arguments")`, refuses with `ARGUMENTS_INVALID` when malformed, and writes the key only when the map is not empty (`out.putTyped("arguments", ...)` already omits an empty one: pin it by a test). Backward compatible by construction: a file without `arguments` parses to the same action and is written back byte for byte (A2); `RerunSafety` and the checksum are unaffected (the action's JSON changes only when arguments exist).
- Parser rule, closed set (architect's decision, technical): the accepted keys are exactly the four above; any other key is refused with a fixed reason (`x-queue-type` is the `type`, never an argument, as for a queue; `x-dead-letter-exchange` is refused by the broker anyway, M9-00b S-D1). Value rules: `x-max-age` text matching `[0-9]+[YMDhms]`; the two byte keys whole non-negative numbers; `x-queue-leader-locator` one of the values the live rows accept (step 0). A stream setting the model refuses stays what the export names as "other settings" (below).
- Executor, `data-rabbit`: the stream is still created by the stream manager (stream protocol, TLS per profile, unchanged transport and path allow-list; no new HTTP request, no `PUT /api/queues` for a stream). `core.streams.StreamManager.createStream(vhost, name)` gains the settings: recommended `createStream(vhost, name, settings: StreamSettings = StreamSettings.NONE)` with `StreamSettings(maxAge: String?, maxLengthBytes: Long?, segmentSizeBytes: Long?, leaderLocator: String?)` built by one pure function from the action's `arguments` (no primitive map crossing into `RabbitMqStreamManager`); `RabbitMqStreamManager` is the one place that maps them to the Java client's creator. The fakes (`FakeStreamManager` in `core-testing`, `UnavailableStreamManager`, `StreamSource`'s guard wrapper) and the stream-management screen call site keep compiling through the default. KEEP the text of `x-max-age` as typed ("7D"): the Java client's `maxAge(Duration)` would turn it into seconds; whether the raw argument route (`StreamCreator.argument`) keeps "7D" is a live row (step 0).
- Idempotence and conflicts: apply stays "created, or the same, or a conflict, never deleted or recreated" (`streamOutcome`, `ReadBack`). Today `DeclaredResourceMatcher` judges a stream by `type == "stream"` only; it now also requires every DECLARED setting to be on the broker with the same typed value (the existing `argumentsContained`, `TypedJson.equal`), nothing more: settings the broker added (`balanced` on a stream whose step declares only `x-max-age`) are ignored, a step with no settings matches any stream as today. A stream that exists with other settings: the create is `Success` or `Refused` depending on what the broker answers for the same name and other arguments (step 0, row S-14c-3); the typed outcome must end as `ExecutorReasons.conflict(action)` ("exists with different settings"), never as a generic refusal, decided by FACTS (a read after), never by the broker's text, like `explainBadRequest`.
- The check, `ManagementDeclareCheck.compared`: `DeclareStream` moves from the shared arm of the policies into its own: absent = `Absent`; present and `DeclaredResourceMatcher.matches` = `Same`; present and not = `Different`. What "Already there" compares for a stream: only the declared settings (table in the scenario outline "A stream is compared on the settings its step declares" in `20`). Retention set by a POLICY is not in `arguments` (S-F1d): a step that declares `x-max-age` against such a stream is `Different` with the existing text "Exists with different settings"; the check does not read `effective_policy_definition` (it would call "same" what the executor then cannot create; the apply and the check must agree). Whether `HonouredArgumentRule` rules 3 and 4 (M9-05b) also predict a repeated stream create (an argument on the broker that the step lacks) is NOT assumed: row S-14c-3 decides; if the broker refuses a repeat that differs only by an extra setting on the broker, the check predicts it like rule 3, otherwise it does not.
- Export, `core.migrations.TopologyExport`: `streams.map { DeclareStream(name, vhost, arguments = writtenSettings(it)) }`, where `writtenSettings` keeps the four keys with their typed values and drops `x-queue-type`. The note keeps only what still cannot be written: a stream argument that is none of the four keys (`other settings`, as M9-14b built it) and nothing else. Consequences to pin by tests: `RETENTION_WORD` and `LEADER_LOCATOR_WORD` and the "retention of stream X" strings go; the note of a stream with only the four keys is null, so "An export that loses nothing says nothing" now also holds for any stream and for a super stream (the "leader locator of super stream orders (3 partitions)" entry of M9-14b, open point 3 there, disappears); `superStreamNote` stays for "other settings of super stream X (N partitions)"; the completeness rule: a stream whose arguments the broker read could not be typed (`typedArgumentsComplete` false) keeps naming "other settings" (as today, M9-14b step 2.5: a refused stream argument is a note, not `NotWritable`). `TopologyExport` KDoc ("`declareStream` carries no arguments, so ...") is rewritten.
- The planner, `core.planner`: the stream FORM still writes a name only; retention stays a policy (A5, Q4, M9-08; the retention block of M9-08 is no longer waiting for S-F1, which is measured, but for `M9-08b`). One rule is required for no loss (A2): `StepForms.formOf(DeclareStream)` returns `null` when `arguments` is not empty, so an opened file's stream step with settings is shown read-only with its detail and written back unchanged (today the line `is DeclareStream -> StreamForm(name = action.name)` would DROP the settings on edit; its comment "A stream has no arguments here" is wrong after this task). `PlanCheck`, `PlanValidation`, the pair recognition (by name) and the review graph need no change (verify; one test each that a stream with settings is still a stream node and still part of a pair by its name).
- Live rows first (step 0, a `@broker` test class `RealBrokerM9StreamArgumentsTest`, results in `docs/tasks/M9-14c-spike-results.md`, assertions with a positive control each, no sleeps): S-14c-1 which keys the stream protocol accepts at creation and what `arguments` the management API then shows for each (and whether `x-max-age` stays "7D" or becomes seconds); S-14c-2 which `x-queue-leader-locator` values are accepted and shown (`balanced` and `client-local` expected, others unmeasured: do not guess); S-14c-3 what creating a stream that exists answers with the same settings, with another retention, with only a subset of the broker's settings (`balanced` extra on the broker) and with a different locator; S-14c-4 both retention by argument and a policy on one stream (the precedence question of `M9-08b`: measure once, give both tasks the answer); S-14c-5 the default leader locator of a stream made with no locator (balanced on 4.4.0, already measured; add the assertion that a stream made WITH `balanced` and one made without it show the same `arguments`, which is what makes open point 1 below safe).
Out: any setting beyond the four keys (initial cluster size, filter size, replicas, `x-stream-partition-order`); retention in the planner's stream form (stays M9-08, a policy); editing the retention of an existing stream (the app never alters a stream: a changed retention is a conflict, the owner changes it by a policy or by hand); the stream manager screen "Create stream" dialog (a separate UX decision, not asked); the 3.x migration generator (`MigrationGenerator` still builds `DeclareStream(name, vhost)`; carrying the settings of a 3.13 stream is a follow-up only if the owner asks: record, do not build); a new MCP tool.

## Design notes
Modules: `core` holds the model, the parser rules, the export and the pure `StreamSettings` builder; `data-rabbit` is the only module that knows the stream client and the management JSON; no `java.*` in `core`, no new dependency. Boundaries kept: the executor is still the only writer, the stream manager is still the only creator of streams; the check is still GET only (no new request: `GET /api/queues/{vhost}/{name}` is the read it already makes for a stream); no read path for queue messages is touched. Safety: creating a stream with settings is a topology change and goes through the same dry run (level, configure permission, V1 virtual host) and the same TLS rule (D9a) as today; the stream protocol connection is made by the existing `StreamEnvironments` for the connection's own profile. The planner's dry run text for a stream step gains the detail line only. `description` of the action stays "Declare stream NAME" so every existing label, graph node and test of the planner is unchanged.

The migration file, the executor, the export and the check are not exposed by any MCP tool (`caerbannog_analyze_*`, `caerbannog_list_shovels`, list and read tools only; no tool applies or exports a migration, and the spec forbids MCP tools that change topology for the planner, O6). ## Open points
- PRODUCT QUESTION for the owner (Q-14c-1, the leader locator in an export): a stream the product or the CLI made always carries `x-queue-leader-locator: balanced`, so every exported stream (and every partition of a super stream) will now hold `"arguments": {"x-queue-leader-locator": "balanced"}`. Options: (a) write it always (faithful and literal: "export the leader locator"; the file says what the broker had; a little noise in every stream step; dry run shows it); (b) leave it out when it is `balanced` and write it only when it differs (smaller files, the file says only what someone chose; relies on the measured fact that a stream made with no locator gets `balanced`, pinned by S-14c-5, on 4.4.0 only). Recommendation: (a); explicit beats implicit in a file that is meant to reproduce a broker, and (b) hides a broker default that may differ on another 4.x. Until answered: build (a). The choice is one function (`writtenSettings`) and two scenarios ("An export writes ..." and the super stream one), cheap to change.
- "Already there" for a stream whose retention is set by a policy and whose step declares it as an argument is `Different` (above). If the owner finds that surprising, the alternative is to read `effective_policy_definition` too; not recommended (the apply could not create it). No text is new: the existing "Exists with different settings" is reused.
- Open facts, measured in step 0 and recorded in the spec by the architect at step 3: S-14c-1 to S-14c-5 (nothing above is asserted about the stream protocol's argument names, the text of `x-max-age`, the accepted locator values or the behaviour of a repeated create with other settings).
