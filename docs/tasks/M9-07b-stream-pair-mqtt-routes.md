# M9-07b: The optional MQTT routes of a stream pair (the owner's request and answer flow)

Milestone: M9    Depends on: M9-07 (the plain pair), M9-10 (the MQTT route form and its translation), M9-00a (S-A5 to S-A8, for the texts and the note), M9-12 (for the "recognised again" scenario only)    Size: S

PLANNED 2026-11-15. Brief confirmed against the code on main 1f469607 on 2026-11-17 (see "Decisions of step 1"); tests written, contract confirmed at the step 2 gate (see "Step 2: contract confirmed"); not built. Cut out of `M9-07` on 2026-11-15 so that the plain stream pair can be built without the MQTT route step; this task adds two ticks that call the form of `M9-10`, and one note in the graph.

## Goal
In the stream form, with "Also create its response stream (DLN)" ticked, two more optional ticks, both off by default, each add one ordinary MQTT route: "Answers arrive over MQTT" into the response stream, and "Requests are also recorded from an MQTT topic" into the request stream. The wizard summary and the review graph say, in one short sentence, that the owner's own service turns a request into an MQTT message and that the planner does not plan that.

## Why
Owner decision O13 (Q3 revised). The owner's words: "i have several iot devices, i can request them through eg. started on stream, iot device gets mqtt message, answers with mqtt, which is processed through stream", and "header can contains destination id, devices answer on a fixed topic with their id in it, like devices/<id>/answer - correlation id". The flow: a request is a message in the request stream with the destination device id in a header; the owner's service (not planned by the app) turns it into an MQTT message for the device; the device answers on `devices/<id>/answer`; the answer must land in the response stream and be processed from there; request and answer are matched by a correlation id in the message, which the planner never touches. The first idea (routing on the request side by default) had the MQTT route on the wrong side. Spec "Topology planner (M9)", "Streams and the response stream", A14.

## Scope
In:
- `core.planner`: `StreamForm` (from `M9-07`) gains `answersTopic: String?` and `requestsTopic: String?`; null means the tick is off. The ticks exist only while `withResponse` is true; clearing the pair clears both. Each given filter is checked by the same function as the MQTT route form (`MqttTopicTranslation`, `M9-10`), with the same fixed texts. `actions`: the two streams first, then the answers route (`MqttRouteForm(answersTopic, <response stream name>, stream)` actions), then the requests route (`MqttRouteForm(requestsTopic, <stream name>, stream)` actions). Nothing else: no exchange, no policy, no marker (A1, A14).
- The text of the summary under the step list when an answers route is part of it, and of the graph note, is one constant: `PlannerTexts.SERVICE_NOT_PLANNED = "Your own service turns a request into an MQTT message; the planner does not plan that."`
- The note in the graph: `planGraphNotes(plan): List<PlanGraphNote>` (one argument, see "Step 2: contract confirmed"), a pure function over the actions (A10, A11): for every MQTT route into a stream that is recognised as a response stream, one note between the request stream and `amq.topic` (once per request stream, however many routes). So the note is also drawn for a pair that was typed by hand or reopened from a file. It goes into the `notes` field that `M9-04` added to `PlanGraph`. A route into a stream that is not a response stream draws no note.
- `ui`: two checkboxes with a topic field each in `StreamFormView` (placeholder of the answers field `devices/+/answer`, the owner's example; the requests field has none), the note drawn by `PlanReviewGraph` as a dashed rounded box with no edge, no click and no focus action beyond reading it. Test tags: `planForm:answersOverMqtt`, `planForm:answersTopic`, `planForm:requestsOverMqtt`, `planForm:requestsTopic`, `planGraphNote:<index>`.

Out: any bridge from a stream to an MQTT message; reading or writing a correlation id (the test message of `M9-10` is the only place the planner pre-fills one, and the only place that warns about it: owner decision O16, 2026-11-17, the Publish MQTT dialog shows a warning that the service must read and write the application property `correlation-id`; the pair's tick and graph note say nothing about it); retention (`M9-08`); an exchange or a routing key of the owner's own choice for the pair; MQTT 5 settings of a route.

## Decisions of step 1 (architect, 2026-11-17, checked against the code on main 1f469607)

Technical, decided here:
1. **No default filter.** A tick that is switched on starts with an EMPTY filter (`""`, null = off), so the form says "Enter a topic filter" until the owner types one (the outline row with an empty filter needs exactly that). The answers field shows `devices/+/answer` as a placeholder only (the owner's example); the requests field has no placeholder. No name-derived suggestion: a topic belongs to the owner's devices, not to the stream name, and a guessed filter that is applied silently would route traffic nobody asked for. The field is the filter itself and is editable; under it the existing `PlannerTexts.mqttRouteSaves(key)` line shows the key it is saved as (the mockup has it), while the filter is accepted.
2. **Reuse, not copy.** `StreamForm.actions` builds each route by calling `MqttRouteForm(filter, <destination>, MqttDestinationKind.Stream).actions(ctx)`; the filter check is `MqttTopicTranslation.toBindingKey` with `PlannerTexts.mqttRefusal`, reported under the stream form's own fields `answersTopic` and `requestsTopic` (not `filter`). Only the filter problem of the route form is taken over: the destination is the stream or response name, which the stream form already checks, so no second message for one mistake.
3. **Clearing.** A pure `StreamForm` function sets the pair on or off and clears both ticks when it goes off (`withResponse = false, answersTopic = null, requestsTopic = null`); `problems`, `actions` and `hints` also ignore the two fields while `withResponse` is false, so a stale value can never produce a step. The ticks are drawn only when adding (`editingStepId == null`), like the pair tick. `StepForms.formOf` is unchanged: a reopened stream is an ordinary `StreamForm(name)` and its route an ordinary `MqttRouteForm` (A1, A10, A14).
4. **The shared rule of the note.** One pure function decides "an MQTT route leads into a response stream", over a list of actions: `PlanPairs` gets a second entry point over a list of `DeclareStream` names (the existing `responseOf(plan)` calls it), `MqttRoutes.routeOf` recognises the route. `planGraphNotes(plan)` (graph) and the wizard summary note both use it, so the summary sentence and the graph note can never disagree. A route into the request stream, or into a stream that is not a response stream, draws and says nothing.
5. **The summary sentence.** `WizardState.Summary` gets `note: String?`, filled by the view model through that pure rule over the summary's actions (`PlannerTexts.SERVICE_NOT_PLANNED` when an answers route is part of it, otherwise null); `SummaryPage` draws it under the list (tag `planWizard:summaryNote`). The field is neutral on purpose: `M9-09` (the dead-lettering sentence of the same place) reuses it and must not add a second one.
6. **The graph note.** `PlanGraphNote(sourceId = "q:<request>", targetId = "e:amq.topic", text = SERVICE_NOT_PLANNED)`, one per request stream, in plan order. The canvas has no drawing for it yet (only `PlanLink` labels): `BindingGraphCanvas` places it at the midpoint of the two node boxes as a dashed rounded box, with no edge, no click and no focus action, text readable by the screen reader. This drawing is the one real risk of the task (layout); if two nodes of the pair sit in the same layer, the note goes beside the request node on the side of `amq.topic`. No change to the Topology screen graph (it passes no notes).
7. **The MQTT exchange assumption.** While either tick is on, the stream form shows the existing `PlannerTexts.MQTT_EXCHANGE_ASSUMPTION` once under the ticks (tag `planForm:mqttAssumption`, as in the route form): the route is an MQTT route and the app cannot read the broker's MQTT exchange (S-B1); leaving it out would be a silent claim. No new text.
8. **The M9-12 scenario.** "A saved pair with its answers route is recognised again": the Given "a pending migration ... that declares the streams ... and binds ..." is a new stand-in in `PlannerStreamSteps` that calls the existing `PendingStandIn.put`, the When `I choose "Edit steps" for "0005"` reuses `PendingStandIn.open`; M9-12 replaces `PendingStandIn` and the Given, not the Thens. The Thens (the step shown as the response stream, the route listed with its words, the note) are real: they run against the real planner screen. Mark the Given with the same "stand-in until M9-12" comment as M9-07 and M9-10.
9. **The live scenario.** `RealBrokerPlannerIotRouteTest` does not exist yet (the BDD README names it); it is modelled on `RealBrokerPlannerMqttRouteTest` (real runner, real plugin container, bounded polling, counts only, a positive control). Its content is the scenario "A device answer published over MQTT lands in the response stream, with its correlation id where the processing can read it": plan = the two streams and the answers route `devices/+/answer`; publish as `d42` to `devices/d42/answer` with the MQTT 5 user property `correlation-id` = `c-1`; the response stream holds one message more, the request stream none; the stream message has the APPLICATION property `correlation-id` = `c-1` and the standard AMQP `correlation-id` is empty (S-A6). The test publishes over MQTT; it reads the streams through the same short-lived unnamed-consumer read the other live tests use, never a queue.
10. **Stays one task.** Size S to M (core: ticks and `planGraphNotes`, half a day each; ui: two fields, one drawing; live test: half a day). Splitting would leave a half-offered tick or a note nobody can see. If the canvas drawing grows past a day, the senior developer says so at step 3 and the architect cuts the drawing into `M9-07d`; nothing else moves.
11. **Runners.** No feature file changed in step 1. `@m9-07b` is not in the filter of `RunTopologyPlannerAcceptanceTest` (it lists `@m9-01..@m9-07` and `@m9-10`); the test developer adds `@m9-07b` in step 2, keeping `and not @needs-decision`. ## Step 2: contract confirmed (architect, 2026-11-17, gate between step 2 and step 3)

The tests are the exact API spec. Confirmed as written (the senior developer follows them, not the wording of "Scope"):

1. **`StreamForm`**: `StreamForm(name, withResponse = false, responseName = null, answersTopic: String? = null, requestsTopic: String? = null)`. Model value: `null` = tick off, `""` = tick on with an empty filter (the form then says "Enter a topic filter"). The text field shows the model value as typed, so after a tick is switched on the model holds `""` and the field text is `""`: there is no conflict. `withPair(on)`: off clears both ticks and keeps the typed `responseName`; on starts both ticks null (a tick that was on and a pair switched on again with `withPair(true)` keeps what it has). `problems` order: name, response, then `answersTopic`, then `requestsTopic`; a tick problem is reported next to a name problem (two mistakes, two messages), a bad name or response name adds no tick message of its own. A route's destination is the effective response name (answers) and the stream name (requests), each exactly `MqttRouteForm(filter, dest, Stream).actions(ctx)`. `problems`, `actions`, `hints` ignore both fields while `withResponse` is false.
2. **Shared rule**: `PlanPairs.responseIndexes(streamNames: List<String>): Map<Int, Int>` (response index to request index; `responseOf(plan)` is built on it and must agree) and `PlanPairs.requestsAnsweredOverMqtt(actions: List<MigrationAction>): List<String>` (each request stream once, in the declaration order of the request streams; only `DeclareStream` counts, `MqttRoutes.routeOf` recognises the route, a route into the request stream or a non-response stream says nothing).
3. **`planGraphNotes(plan: TopologyPlan): List<PlanGraphNote>` takes ONE argument.** The brief's "Scope" said `(plan, known)`; the test developer fixed `(plan)` and that is right: a pair is recognised in the plan only (A11), the same way `PlanPairs.responseOf(plan)` does it, and a note about a service for steps the plan does not contain would be a claim about the broker that the app cannot make (`known` is also null while the broker is read). `planPreview(...).notes` equals it; the note is `PlanGraphNote("q:<request>", "e:amq.topic", PlannerTexts.SERVICE_NOT_PLANNED)`, in the order of `requestsAnsweredOverMqtt`. The brief's "Scope" line is corrected above.
4. **`WizardState.Summary.note: String? = null`** (neutral name for M9-09), filled with `SERVICE_NOT_PLANNED` by the view model when the shared rule finds an answers route among the summary's own actions.
5. **UI tags** beyond the five of the brief are confirmed: `planForm:answersSubline`, `planForm:requestsSubline`, `planForm:answersKey`, `planForm:requestsKey` (`mqttRouteSaves(key)` only while that filter is accepted), `planForm:error:answersTopic|requestsTopic`, `planForm:answersOverMqtt`, `planForm:requestsOverMqtt`, `planForm:mqttAssumption` (exactly once while either tick is on), `planWizard:summaryNote`, `planGraphNote:<index>` (0-based; no click, long-click, set-text or focus action; no edge; text readable). The answers placeholder `devices/+/answer` shows while the field is focused and empty and is never the value; the requests field has none.
6. **Changes to existing tests and steps are acceptable**: runner filter gains `@m9-07b` (still `and not @needs-decision`); `PlannerDriver.removeByTitle` also matches the planner's step title (the route has no `description` that reads like its step title); `PlannerSteps.formSays` one more hook (no-op unless a tick is on); `PlannerStreamSteps.summarySays` takes the `SERVICE_NOT_PLANNED` sentence; `StreamFormUiTest` asserts the real tags. `PlannerMqttSteps.plannerListsOne` now means "among the steps": accepted, because the M9-10 scenario that uses it has one step in its plan, so it asserts the same thing there; the test developer keeps the comment that says so.

### Decisions of the gate

- **3a, the note layout (the real risk): keep `PlanReviewGraphNoteUiTest` strict.** Reason: the sentence of the note says WHERE the owner's service sits, so a box that floats elsewhere says nothing; the geometry is satisfiable. How, from the real layout (`buildBindingGraph`): `amq.topic` is in layer 0, the request stream and the response stream are both in layer 1 (a node with no binding defaults to layer 1) and `LAYER_SPACING` is 140 dp, so the free band between the two columns is 140 dp wide and the first row of both nodes has its centre at y = 48. A box of 220 x ~60 dp (the sentence in `labelSmall`, wrapping to at most three lines, 8 dp padding) does not fit that band, and a 140 dp box wraps to five lines and runs into the key pill (which starts at about y = 72). So: (i) the box has a fixed width (`NOTE_WIDTH` = 220 dp) and wraps; (ii) on the plan path only, and only when `plan.notes` is not empty, the canvas widens the gap between the two columns that hold the note's two nodes to `NOTE_WIDTH + 2 * 12` by shifting the nodes of the later columns and their edges with the same mapping the canvas already uses for `shift` (nodes and `fromX`, `toX`, `labelX` of the edges); (iii) the box is centred on the middle of the free band and placed at the top of the pair's first row (about y = 4, below it the first label block starts at about y = 72), so its centre is inside the 24 px slack of the two node centres, it sits on no node and on no pill; it is drawn under the nodes and the labels and may cross the line of the edge (the test does not look at lines and a note that hides part of a curve is acceptable; a position that avoids the line is nicer, not required); (iv) a pure function `placeNotes(nodes, labelRects, notes)` returns the rectangles, so the geometry has a plain unit test and a second note takes the nearest free slot (the two-pair test only requires that notes do not overlap each other); (v) if the two nodes of a note are in the SAME column (an exchange bound to `amq.topic` puts it in layer 1 next to the streams), the canvas inserts a vertical gap of `NOTE_HEIGHT + 16` between them by shifting the nodes below the upper one and their edges, and the box sits in that gap. The Topology path (`plan == null`) never computes any of this: its twelve screenshot hashes (BEFORE list in "Status") must be identical after the build, and a plan graph with no note must also be identical to today's (the planner screenshots, if any, and the existing `PlanReviewGraph*UiTest` classes). The canvas file is already 500 lines: put the note drawing and `placeNotes` in a new file (`PlanGraphNotes.kt` in `ui/planner/` or beside the canvas) and keep the canvas change to the hook.
- **3b, the route in the summary: "to stream ..." through the context, not through the form.** Reason: the summary and the plan list both call `PlannerState.wordsOf(action)`, which finds the kind of a route's destination from the plan's `DeclareStream` steps; the summary's own actions are not in the plan yet, so the kind is unknown there. Passing the kind from the form would fix only the stream pair and would leave the next form that adds a route and its stream without it. Instead `wordsOf` gets a second, defaulted parameter: `PlannerState.wordsOf(action, alongside: List<MigrationAction> = emptyList())`, which gives `MqttRoutes.words` the plan's actions plus `alongside`; `PlannerScreen` passes the actions of the summary while the wizard is on its summary page (`{ a -> state.wordsOf(a, (state.wizard as? WizardState.Summary)?.actions.orEmpty()) }`), so `SummaryPage` and `PlanWizardDialog` keep their signatures. Result: the summary reads "MQTT route devices/+/answer to stream device-commands-dln", the same words as the list after "Add to plan". The test developer adds the test named below (the existing glue does not pin the old words: nothing in the repo asserts a summary line without "stream").
- **3c, a single MQTT route form into an already planned response stream: no summary sentence, graph note after Add. Intended for this task.** The sentence belongs to the pair's tick (the owner decides there that answers come over MQTT); the route form of M9-10 is a plain route and the owner who adds one by hand into his own response stream gets the graph note, which is where the sentence matters most. Making the summary agree would need the rule to run over the plan plus the summary and then to tell "this summary adds a route into a response stream" from "the plan already had one", which is a second rule for a case no scenario asks for. The shared rule is the same one in both places, so they cannot disagree about what a note is; they differ only in how much of the plan the summary looks at. Recorded here so M9-09 (which reuses `Summary.note`) knows. A test pins it (below), so a later change is deliberate.
- **3d, two pairs: notes in declaration order of the request streams: fine** (`PlanGraphNotesTest` pins it).
