# M9-07b: The optional MQTT routes of a stream pair (the owner's request and answer flow)

Milestone: M9    Depends on: M9-07 (the plain pair), M9-10 (the MQTT route form and its translation), M9-00a (S-A5 to S-A8, for the texts and the note), M9-12 (for the "recognised again" scenario only)    Size: S

PLANNED 2026-11-15. Brief confirmed against the code on main 1f469607 on 2026-11-17 (see "Decisions of step 1"); not built. Cut out of `M9-07` on 2026-11-15 so that the plain stream pair can be built without the MQTT route step; this task adds two ticks that call the form of `M9-10`, and one note in the graph.

## Goal
In the stream form, with "Also create its response stream (DLN)" ticked, two more optional ticks, both off by default, each add one ordinary MQTT route: "Answers arrive over MQTT" into the response stream, and "Requests are also recorded from an MQTT topic" into the request stream. The wizard summary and the review graph say, in one short sentence, that the owner's own service turns a request into an MQTT message and that the planner does not plan that.

## Why
Owner decision O13 (Q3 revised). The owner's words: "i have several iot devices, i can request them through eg. started on stream, iot device gets mqtt message, answers with mqtt, which is processed through stream", and "header can contains destination id, devices answer on a fixed topic with their id in it, like devices/<id>/answer - correlation id". The flow: a request is a message in the request stream with the destination device id in a header; the owner's service (not planned by the app) turns it into an MQTT message for the device; the device answers on `devices/<id>/answer`; the answer must land in the response stream and be processed from there; request and answer are matched by a correlation id in the message, which the planner never touches. The first idea (routing on the request side by default) had the MQTT route on the wrong side. Spec "Topology planner (M9)", "Streams and the response stream", A14.

## Scope
In:
- `core.planner`: `StreamForm` (from `M9-07`) gains `answersTopic: String?` and `requestsTopic: String?`; null means the tick is off. The ticks exist only while `withResponse` is true; clearing the pair clears both. Each given filter is checked by the same function as the MQTT route form (`MqttTopicTranslation`, `M9-10`), with the same fixed texts. `actions`: the two streams first, then the answers route (`MqttRouteForm(answersTopic, <response stream name>, stream)` actions), then the requests route (`MqttRouteForm(requestsTopic, <stream name>, stream)` actions). Nothing else: no exchange, no policy, no marker (A1, A14).
- The text of the summary under the step list when an answers route is part of it, and of the graph note, is one constant: `PlannerTexts.SERVICE_NOT_PLANNED = "Your own service turns a request into an MQTT message; the planner does not plan that."`
- The note in the graph: `planGraphNotes(plan, known): List<PlanGraphNote>`, a pure function over the actions (A10, A11): for every MQTT route into a stream that is recognised as a response stream, one note between the request stream and `amq.topic` (once per request stream, however many routes). So the note is also drawn for a pair that was typed by hand or reopened from a file. It goes into the `notes` field that `M9-04` added to `PlanGraph`. A route into a stream that is not a response stream draws no note.
- `ui`: two checkboxes with a topic field each in `StreamFormView` (placeholder of the answers field `devices/+/answer`, the owner's example; the requests field has none), the note drawn by `PlanReviewGraph` as a dashed rounded box with no edge, no click and no focus action beyond reading it. Test tags: `planForm:answersOverMqtt`, `planForm:answersTopic`, `planForm:requestsOverMqtt`, `planForm:requestsTopic`, `planGraphNote:<index>`.

Out: any bridge from a stream to an MQTT message; reading or writing a correlation id (the test message of `M9-10` is the only place the planner pre-fills one, and the only place that warns about it: owner decision O16, 2026-11-17, the Publish MQTT dialog shows a warning that the service must read and write the application property `correlation-id`; the pair's tick and graph note say nothing about it); retention (`M9-08`); an exchange or a routing key of the owner's own choice for the pair; MQTT 5 settings of a route.

## Design notes
Everything here is built from parts that exist after `M9-07` and `M9-10`: two `declareStream` steps and ordinary `declareBinding` steps on `amq.topic`. After "Add to plan" nothing remembers that the steps belong together, so each can be edited or removed (A1); a reopened file shows the recognised pair (A11) and the recognised routes (A10) and the note follows from them. The note is not a step, not an edge and not stored. Where the broker is faked: `FakeTopologyCatalog` for `KnownTopology`; real in the live test. No MCP and no new request: the apply is the existing runner and executor.

## Decisions of step 1 (architect, 2026-11-17, checked against the code on main 1f469607)

Technical, decided here:
1. **No default filter.** A tick that is switched on starts with an EMPTY filter (`""`, null = off), so the form says "Enter a topic filter" until the owner types one (the outline row with an empty filter needs exactly that). The answers field shows `devices/+/answer` as a placeholder only (the owner's example); the requests field has no placeholder. No name-derived suggestion: a topic belongs to the owner's devices, not to the stream name, and a guessed filter that is applied silently would route traffic nobody asked for. The field is the filter itself and is editable; under it the existing `PlannerTexts.mqttRouteSaves(key)` line shows the key it is saved as (the mockup has it), while the filter is accepted.
2. **Reuse, not copy.** `StreamForm.actions` builds each route by calling `MqttRouteForm(filter, <destination>, MqttDestinationKind.Stream).actions(ctx)`; the filter check is `MqttTopicTranslation.toBindingKey` with `PlannerTexts.mqttRefusal`, reported under the stream form's own fields `answersTopic` and `requestsTopic` (not `filter`). Only the filter problem of the route form is taken over: the destination is the stream or response name, which the stream form already checks, so no second message for one mistake.
3. **Clearing.** A pure `StreamForm` function sets the pair on or off and clears both ticks when it goes off (`withResponse = false, answersTopic = null, requestsTopic = null`); `problems`, `actions` and `hints` also ignore the two fields while `withResponse` is false, so a stale value can never produce a step. The ticks are drawn only when adding (`editingStepId == null`), like the pair tick. `StepForms.formOf` is unchanged: a reopened stream is an ordinary `StreamForm(name)` and its route an ordinary `MqttRouteForm` (A1, A10, A14).
4. **The shared rule of the note.** One pure function decides "an MQTT route leads into a response stream", over a list of actions: `PlanPairs` gets a second entry point over a list of `DeclareStream` names (the existing `responseOf(plan)` calls it), `MqttRoutes.routeOf` recognises the route. `planGraphNotes(plan)` (graph) and the wizard summary note both use it, so the summary sentence and the graph note can never disagree. A route into the request stream, or into a stream that is not a response stream, draws and says nothing.
5. **The summary sentence.** `WizardState.Summary` gets `note: String?`, filled by the view model through that pure rule over the summary's actions (`PlannerTexts.SERVICE_NOT_PLANNED` when an answers route is part of it, otherwise null); `SummaryPage` draws it under the list (tag `planWizard:summaryNote`). The field is neutral on purpose: `M9-09` (the dead-lettering sentence of the same place) reuses it and must not add a second one.
6. **The graph note.** `PlanGraphNote(sourceId = "q:<request>", targetId = "e:amq.topic", text = SERVICE_NOT_PLANNED)`, one per request stream, in plan order. The canvas has no drawing for it yet (only `PlanLink` labels): `BindingGraphCanvas` places it at the midpoint of the two node boxes as a dashed rounded box, with no edge, no click and no focus action, text readable by the screen reader. This drawing is the one real risk of the task (layout); if two nodes of the pair sit in the same layer, the note goes beside the request node on the side of `amq.topic`. No change to the Topology screen graph (it passes no notes).
7. **The MQTT exchange assumption.** While either tick is on, the stream form shows the existing `PlannerTexts.MQTT_EXCHANGE_ASSUMPTION` once under the ticks (tag `planForm:mqttAssumption`, as in the route form): the route is an MQTT route and the app cannot read the broker's MQTT exchange (S-B1); leaving it out would be a silent claim. No new text.
8. **The M9-12 scenario.** "A saved pair with its answers route is recognised again": the Given "a pending migration ... that declares the streams ... and binds ..." is a new stand-in in `PlannerStreamSteps` that calls the existing `PendingStandIn.put`, the When `I choose "Edit steps" for "0005"` reuses `PendingStandIn.open`; M9-12 replaces `PendingStandIn` and the Given, not the Thens. The Thens (the step shown as the response stream, the route listed with its words, the note) are real: they run against the real planner screen. Mark the Given with the same "stand-in until M9-12" comment as M9-07 and M9-10.
9. **The live scenario.** `RealBrokerPlannerIotRouteTest` does not exist yet (the BDD README names it); it is modelled on `RealBrokerPlannerMqttRouteTest` (real runner, real plugin container, bounded polling, counts only, a positive control). Its content is the scenario "A device answer published over MQTT lands in the response stream, with its correlation id where the processing can read it": plan = the two streams and the answers route `devices/+/answer`; publish as `d42` to `devices/d42/answer` with the MQTT 5 user property `correlation-id` = `c-1`; the response stream holds one message more, the request stream none; the stream message has the APPLICATION property `correlation-id` = `c-1` and the standard AMQP `correlation-id` is empty (S-A6). The test publishes over MQTT; it reads the streams through the same short-lived unnamed-consumer read the other live tests use, never a queue.
10. **Stays one task.** Size S to M (core: ticks and `planGraphNotes`, half a day each; ui: two fields, one drawing; live test: half a day). Splitting would leave a half-offered tick or a note nobody can see. If the canvas drawing grows past a day, the senior developer says so at step 3 and the architect cuts the drawing into `M9-07d`; nothing else moves.
11. **Runners.** No feature file changed in step 1. `@m9-07b` is not in the filter of `RunTopologyPlannerAcceptanceTest` (it lists `@m9-01..@m9-07` and `@m9-10`); the test developer adds `@m9-07b` in step 2, keeping `and not @needs-decision`. The two other runners that could see the file (`RunStreamListAcceptanceTest`, `RunMcpAcceptanceTest`) select other features; no scenario of this task lacks steps in any runner today.
