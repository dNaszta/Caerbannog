# Mini-spike: stream client facts for M2-03 (stats permissions, read-only proof, TLS, failures)

Milestone: M2    Depends on: M2-02 (merged), M2-01b (merged); decisions D5 (b), D7 (a) taken    Size: S

Branch: `m2-03a-stream-stats-permissions` from `main` (4d45b7c or later). Needs Docker. First step of M2-03 and a branch of its own (the findings change the M2-03 brief, so they are merged before M2-03 starts). Owner: test developer. Confirmed by the architect 2026-11-04 against the current code.

## Goal
We know, on a real RabbitMQ 4 broker over TLS, with the official stream client 1.12.0: (1) whether `Environment.queryStreamStats(stream)` works for `administrator`, `monitoring`, `management` and no-tag users, on a stream they have permission on and on one they do not, and the exact failure each time; (2) that the call writes nothing; (3) how the client can trust the profile CA without verifying the host name (D7); (4) what a failed credentials attempt looks like for the stream client and for the management API; (5) how the client fails and how long it blocks when the stream port is unreachable. Each answer is a passing assertion or a recorded exact value, so M2-03 can build `StreamOffsets` and `Failed(reason)` without guessing.

## Why
Decision D5 (b): the M2 list shows first offset for every visible row, from `queryStreamStats` only. `docs/spec.md` "Management API facts" (S3 says: not tested whether a user without the management tag can use the stream protocol) and the open question "Can a user without the management tag...". D7 (a): CA honoured, host name not verified, same as the M1 probe (`TlsSupport.buildSslContext` plus `permissiveSslParameters`). `docs/tasks/M2-03-stream-gateway.md` "Connection model" needs the exact Failed reasons and the unavailable path.

## Scope
In: `@broker` tests in `data-rabbit` (tag `broker`, run by `:data-rabbit:brokerTest`), in a new class `StreamClientSpikeTest` that reuses the container recipe of `StreamManagementApiSpikeTest` (`rabbitmq:4-management`, `tls/rabbitmq.conf`, `tls/ca.pem`, `server.pem`, `server.key`, plugins `rabbitmq_stream` and `rabbitmq_stream_management`, port 5551 exposed) and the same throwaway users (`spike-mon` monitoring, `spike-mgmt` management, `spike-plain` no tag; permissions `^spike-allowed-.*` on `/`). Copy the small plumbing you need (container, `ctl`, `awaitUntil`, management GET helper); do not refactor the existing spike class and do not change its assertions. The existing test class may stay as is; a shared helper file is allowed only if it changes no existing line.

1. **Stats matrix.** For admin, `spike-mon`, `spike-mgmt`, `spike-plain`: create `spike-allowed-<id>` (declared by admin, a few messages published by admin) and `spike-private-<id>` (no permission for the three users). Call `queryStreamStats` on both. Assert the success (`firstOffset`, `committedChunkId` types, not only "no exception") or record and assert the exact exception class, and its message, for each denied or failed cell. Also record at which step a no-tag or wrong-password user fails: at `Environment.build()` (locator connect) or at the first call.
2. **Writes nothing.** Before and after the calls: management `messages` of the stream and `GET /api/stream/.../tracking` (`tracking.offsets`/writer entries; use the endpoint the M2-02 spike used) are unchanged. The check must be able to fail: use value-based bounded polling after the call (stats lag up to 5 s) and assert equality with the before values. Create the Environment with no named consumer anywhere (a named consumer with default tracking writes a chunk, see M2-02c and spec "Browsing").
3. **TLS with the profile CA, no host name verification.** Build the `Environment` with a trust store holding only `tls/ca.pem` (not `InsecureTrustManagerFactory`; the M2-02 spike used trust-all, the product must not). Find and record the exact API in stream-client 1.12.0 that turns host name verification off while the CA is still checked: the `Environment` builder `tls()` configuration (candidates to verify in the jar, do not trust this list: a hostname-verification switch on the TLS configuration, `sslContext(io.netty.handler.ssl.SslContext)`, a `sslEngine` or `SslHandler` customisation hook), and any dependency or flag needed. Prove three things with tests: (a) CA only and a host name that is NOT in the certificate (the fixture cert has SAN `localhost` and `127.0.0.1`; connect through another name or address that reaches the same published port, for example the host's own address or `127.0.0.2`/`[::1]` if the Docker mapping allows it, and record which one worked on this machine) succeeds with verification off; (b) the same with verification on fails and the exception class and message are recorded (the control that makes (a) meaningful); (c) a wrong CA (a different self-signed cert, generate it in the test or use `certs/valid-certificate.pem` if it is not the broker's CA) is refused even with verification off, so "off" does not mean trust-all. If the client cannot skip host name verification, STOP that part and say so clearly in Status: the product owner must then choose between verifying the host name on the stream path only, or a per-profile switch earlier than M5 (`M5-verify-host-name`). Do not work around it with trust-all.
4. **Failed credentials.** Record exact exception class and message for the stream client with a wrong password and with the no-tag user, and the HTTP status and body of the management API for a wrong password (`401`, body text) versus the no-tag user (`401 Not management user`, already in `fixtures/m2-02/non-admin-no-tag-401.json`). State whether the two management 401 bodies differ enough for M2-03 to tell "credentials refused" from "not a management user" (the spec says a 401 cannot tell them apart on the permissions endpoint; re-check here for `/api/whoami`). Make sure no recorded text contains the password.
5. **Unreachable stream port.** Against a host and port where nothing listens (a port you bound and closed, so the refusal is immediate and deterministic) record: exception class and message, whether it throws at `Environment.build()` or at the first call, how long it blocks (milliseconds, rough), and whether the Environment builder has a connect or RPC timeout setting and its default. A non-routable address (timeout case) is optional: run it only if it is bounded by a short explicit timeout you set, and never make the suite depend on it.
6. **One Environment, many calls, cost.** One `Environment` serves several `queryStreamStats` calls (also from several threads, say 4 in parallel, 20 calls); record rough time of the first and of the following calls and whether the Environment reconnects its locator by itself after the broker closes the connection (stop/restart is not needed; closing the connection through the management API `DELETE /api/connections/{name}` is enough and optional).
Out: production code, UI, any change to `docs/spec.md` or other briefs (the architect does that from Status), new dependency (stream-client 1.12.0 test scope is already approved; Netty comes with it; anything else needs a stop and a question), real keychain, any change to the product decisions, browsing or consuming messages, named consumers, publishing from the non-admin users.

## Status
Done 2026-11-04 by the test developer, branch `m2-03a-stream-stats-permissions`. Test class `data-rabbit/src/test/kotlin/dev/caerbannog/datarabbit/StreamClientSpikeTest.kt` (14 `@broker` tests, all passing; `./gradlew :data-rabbit:brokerTest --tests '*StreamClientSpikeTest*' --rerun-tasks` green twice in a row, about 73 s each; `:data-rabbit:test` green, about 1 s, the new class is excluded by the `broker` tag). No production code, no new dependency, nothing outside `data-rabbit/src/test`. Validation of the assertions: the first run asserted a deliberately wrong expectation ("DISCOVERY") so the real values showed in the failure message; they were then turned into class + message-fragment assertions. The read-only test carries its own control (one extra publish must show up as exactly 4 messages and exactly 1 new writer).

Broker: RabbitMQ 4.4.0, Erlang 29.1.2 (`/api/overview`, image `rabbitmq:4-management`, a floating tag). Stream client 1.12.0, Netty 4.2.19.Final (test classpath). Admin user of the container image is `guest`.

Item 1, stats matrix (CA-only trust, no host name check, no named consumer; 3 messages = chunk offsets 0..2):
- admin on allowed and on private: `StreamStats` with `firstOffset()` = 0, `committedChunkId()` = 2, `committedOffset()` = 2 (all `long`).
- `spike-mon` (monitoring), `spike-mgmt` (management), `spike-plain` (no tag), permission `^spike-allowed-.*` configure/write/read: allowed stream gives the same stats as admin (first 0, chunk id 2). Read permission on the stream is enough; no tag is needed, a no-tag user can call `queryStreamStats` (this answers the open question and S3a's "can a user without the management tag use the stream protocol": yes).
- The same three users on the private stream: exact class `com.rabbitmq.stream.StreamException`, message `Error while querying stream stats: 16 (ACCESS_REFUSED).`, thrown at the call, not at `Environment.build()`. The Environment stays usable after the refusal (next call on the allowed stream works).
- `Environment.build()` succeeded for all four users (authentication only checks the password); a no-tag user does NOT fail at build or at the first call on a permitted stream.
- Stream that does not exist (admin and spike-plain, name inside the permitted pattern): `com.rabbitmq.stream.StreamDoesNotExistException`, message `Stream <name>  does not exist` (two spaces in 1.12.0, assert on "does not exist"). Different from ACCESS_REFUSED, so M2-03 can tell "gone" from "denied".
- EMPTY stream (declared, no message): the call returns but `firstOffset()` throws `com.rabbitmq.stream.NoOffsetException`, message `No first offset for stream <name>`. M2-03 must treat this as "no first offset" (empty), not as Failed. Note `StreamStats` is lazy about it: the exception comes from the accessor, so the gateway must call `firstOffset()` inside its try.
- `committedChunkId` and `committedOffset` are the last chunk's id and its first offset; `committedChunkId` is not the message count.

Item 2, writes nothing: 4 users x 5 calls = 20 calls on one stream, then `messages` (management) and `/api/stream/%2F/<name>/tracking` equal the values before; `tracking.offsets` stays empty, no consumer, no stream publisher. Control inside the test: one more publish raises `messages` to exactly 4 and adds exactly one writer, so a stats-call write would have been seen. Fact for fixtures: publishing through the management API (AMQP 0.9.1) leaves one `tracking.writers` entry per publish (3 publishes: 3 writers), so "writers empty" is not a valid baseline after management publishes; compare before/after instead. `messages` is absent from `/api/queues/...` until the first stats tick on a brand new stream (a `null` field, guard it in parsers).

Item 3, TLS, profile CA, no host name verification (NO STOP, no product decision needed):
- API: `Environment.builder().tls().sslContext(io.netty.handler.ssl.SslContext)` (also `trustEverything()`, which must not be used). Build the context with `SslContextBuilder.forClient().trustManager(<TrustManagerFactory over a KeyStore holding only the profile CA>).endpointIdentificationAlgorithm(null).build()`. `SslContextBuilder.endpointIdentificationAlgorithm(String)` is the switch: `"HTTPS"` verifies the names, `null` switches the name check off while the chain is still checked. No extra dependency (Netty comes with the client); the client calls `SslContext.newHandler(alloc, host, port)`.
- WARNING: with Netty 4.2.19 the DEFAULT (method not called) VERIFIES the host name (asserted: failure `javax.net.ssl.SSLHandshakeException: No subject alternative names matching IP address ...`). So the product must call `endpointIdentificationAlgorithm(null)` explicitly, and the Netty version matters (4.1 defaulted to off). A test pins it.
- (a) CA only, name not in the certificate (SAN `localhost`, `127.0.0.1`), verification off: succeeds. The name that worked on this machine (macOS, Docker Desktop) is the host's own LAN address (site-local IPv4, 192.168.1.195 here) on the published port; `127.0.0.2` does not reach the container here (connect timeout). The test discovers the LAN address itself and is skipped with a stated gap (`assumeTrue`) on a machine without one.
- (b) Same host with `"HTTPS"`: fails at `Environment.build()` with `com.rabbitmq.stream.StreamException` (message null) caused by `javax.net.ssl.SSLHandshakeException: No subject alternative names matching IP address <ip> found`. Control: with verification ON the names `localhost` and `127.0.0.1` succeed.
- (c) Wrong CA (a different self-signed cert with the same SAN, made with the JDK `keytool` in the test): refused at build with verification off and on: `com.rabbitmq.stream.StreamException` caused by `javax.net.ssl.SSLHandshakeException: PKIX path building failed: ... unable to find valid certification path to requested target`. So "off" is not trust-all.
- Gap: (a)/(b) rely on a second reachable name; on a machine without one they are skipped (not red). The (b)-style control with SAN names plus (c) still run.

Item 4, failed credentials:
- Stream client, wrong password: fails at `Environment.build()` with `com.rabbitmq.stream.AuthenticationFailureException`, message `Unexpected response code during authentication: 8 (AUTHENTICATION_FAILURE)`; an unknown user gives the identical message. No password in the exception chain (asserted). No-tag user: no failure (see item 1).
- Management `GET /api/whoami` and `GET /api/overview`, same bodies on both: no-tag user with the right password: `401 {"error":"not_authorised","reason":"Not management user"}`; wrong password or unknown user: `401 {"error":"not_authorized","reason":"Not_Authorized"}` (note the spelling: British "authorised" vs American "authorized"). They DIFFER, so M2-03 can tell "credentials refused" from "not a management user" on `/api/whoami` and `/api/overview` (monitoring and management users get 200 on `/api/whoami`). The spec's "a 401 cannot be told apart" holds only for the permissions endpoint (body `Access refused.`); re-check there if M1's logic depends on it. Password never echoed.

Item 5, unreachable stream port:
- Closed port (bound then closed, `127.0.0.1`): throws at `Environment.build()` (not deferred): `com.rabbitmq.stream.impl.ConnectionStreamException` (package-private class, match by name, subclass of `StreamException`), message `Error while creating stream connection to 127.0.0.1:<port>`, cause `io.netty.channel.AbstractChannel$AnnotatedConnectException: Connection refused: /127.0.0.1:<port>` / `java.net.ConnectException: Connection refused`. Blocks about 1.05 to 1.09 s although the refusal is immediate (the client waits about one second before giving up; assertion bound 10 s).
- Timeouts: `rpcTimeout(Duration)` on the builder, default 10 s (`Client.DEFAULT_RPC_TIMEOUT`). There is no connect-timeout setting on the builder; the connect timeout is Netty's default 30000 ms (seen: `io.netty.channel.ConnectTimeoutException: connection timed out after 30000 ms: /127.0.0.2:<port>` wrapped in `com.rabbitmq.stream.impl.TimeoutStreamException: Error while creating stream connection to ...`). It can be set with `.netty().bootstrapCustomizer { it.option(ChannelOption.CONNECT_TIMEOUT_MILLIS, n) }`: with 1000 ms against 10.255.255.1 the build throws `TimeoutStreamException` after about 2.06 to 2.08 s (about twice the timeout: one retry). M2-03 must set an explicit connect timeout, or a bare unreachable host blocks `Environment.build()` for 30 s or more.

Item 6, one Environment: build (locator connect plus TLS) 17 to 32 ms; 20 sequential `queryStreamStats` calls 0.45 to 2.0 ms each (first call not slower than the rest, the connect is in build); 20 calls from 4 threads in 4 to 7 ms total, all correct. After the broker closed the Environment's connection (`DELETE /api/connections/{name}`, 204, waited until it vanished) the same Environment answered again by itself and the management list shows a NEW connection (name `rabbitmq-stream-locator-0`), so the locator reconnects on demand without the caller doing anything. The management connection list lags the connect by a stats tick: poll it.

For the product owner: no decision needed. D7 (a) is implementable as decided (profile CA, host name not verified) with `endpointIdentificationAlgorithm(null)`; the M5 per-profile switch can later pass `"HTTPS"`. Not run: keychainTest, desktopApp, any non-admin publish or consumer.
