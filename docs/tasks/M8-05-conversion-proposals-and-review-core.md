# Conversion review and migration generation (pure core)

Milestone: M8    Depends on: M8-01, M8-03, M8-04 (all merged); the apply path is the existing M5-08 runner, executor and folder    Size: M (cut down from L)

## Goal
A pure `core` review lets each topology item of an analysed 3.x definitions file be accepted (default or chosen alternatives, with the ordering tick where needed), skipped or replaced by the user's own actions, and then generates ONE ordinary topology migration per source virtual host that the existing folder repository, runner and executor apply. Generation sends nothing, writes nothing, never emits a delete, never touches 3.x, and no secret can enter the result.

## Why
Spec decision 2 and "Review and the generated migration". M8-03 produces the report, M8-04 widened the migration format, M5-08 applies it for real. This task is the missing middle.

## Scope (cut to the essential; what is deferred is listed at the end)
In (`core`, package `dev.caerbannog.core.migrate3x`, `commonMain`, pure, no I/O, no clock, no new dependency):
1. **Review items.** `data class ReviewItem(kind: ItemKind, vhost: String?, name: String?)` (public; bindings are named `source->destination:routingKey`). An item NEEDS A DECISION when it is a queue, exchange, policy or operator policy (bindings never need one) with at least one finding of severity `Blocker` or `Warning`, scope `Always`, and class `Incompatibility` or `BehaviourChange`. Findings of class `MessageLoss`, `NotCovered`, `ClientCheck` and `Access` and every `Info` finding never block and never need a decision (message loss is informational for a conversion: S-N; access is `M8-12`). Every other item is compatible and is written as it is.
2. **Decisions.** `sealed interface ItemDecision`: `Accept(chosen: Map<String, Int> = emptyMap(), acknowledged: Set<Acknowledgement> = emptySet())` (`chosen` maps a finding id to the index in `[proposal] + alternatives`, 0 = the default); `Skip`; `Replace(actions: List<MigrationAction>)` (the user's own actions for this item, they replace the generated ones, validated by the parser at generation).
   Rules of `Accept`: the chosen proposal of every decision-driving finding is applied (below); it is REFUSED (`DecisionRefusal.ManualNeeded(findingIds)`) while a `Blocker` finding with scope `Always` has a chosen proposal that is `Manual` or `None` (no automatic fix: the non-durable queue until the alternative `MakeDurable` is chosen; after `MakeDurable` only `durable = true` changes, every other flag stays as in the source); it is REFUSED (`DecisionRefusal.TickMissing(missing)`) when a chosen proposal carries an `Acknowledgement` that is not in `acknowledged` (P15: classic to quorum needs "Ordering by priority may change"; keeping a classic queue needs none). A `Warning` with a `Manual` default does not refuse `Accept`: the item is declared as in the source. This covers a plugin exchange type and an UNKNOWN QUEUE TYPE (`queue-type-unknown` is a `Warning`, M8-03): the queue is declared with `type` = the type name as written in the source, no `x-queue-type` argument, no other change (the parser accepts any type string; the runner's read-back and the broker decide). `Replace` is refused (`DecisionRefusal.ReplaceHasDelete`) when any of its actions is a `Delete*` action (`DeleteQueue`, `DeleteExchange`, `DeleteBinding`, `DeleteStream`, `DeletePolicy`): a generated migration never deletes, also not at the user's hand. It is checked at `decide`, so the map never holds one; generation re-checks and a delete found there is a bug that fails loudly.
3. **`ConversionReview`** (a small single-threaded state holder, created by `ConversionReview.start(document: DefinitionsDocument, report: CompatibilityReport)`; decisions live in one map keyed by `ReviewItem`, never one object per finding, so 60,000 queues are fine): `val items: List<ReviewItem>` (those that need a decision, in REPORT ORDER: walk `report.findings` in their order, keep the item of every finding that qualifies by the rule in 1 (kind, severity, scope, class), distinct, at its first QUALIFYING finding; an earlier non-qualifying finding places nothing. Items with an unwritable name, see below, are not in `items`), `val pending: List<ReviewItem>` (`items` minus the decided, same order), `fun decide(item, decision): DecisionResult` (`Decided` or `Refused(reason)`), `fun decisionOf(item)`, `fun generate(request: GenerationRequest): GenerationResult`. It keeps no reference to a `SecretValue` and its `toString` shows counts only.
4. **Generation (`MigrationGenerator`, pure).** `GenerationRequest(existingVersions: Set<String>, source: String)` (`source` is the report's connection or file label for the description). `GenerationResult`: `Incomplete(pending)` (nothing is produced; it never lists left-out items) or `Generated(migrations: List<GeneratedMigration>, skipped: List<SkippedItem>, notes: List<GenerationNote>)`. One `GeneratedMigration(vhost, file: MigrationFile)` per source virtual host that has at least one action, ordered by virtual host name (ordinal string order, so `/` first; independent of the document). Versions: let N = the highest existing version that is all digits (none = 0); the files get N+1, N+2, ... in that order, four digits, `0001` style. Gaps below N are NOT filled (the runner applies in order and history is per version: a file inserted below an applied one would be out of order); non-numeric existing versions are ignored; going past `9999` fails the generation loudly (`IllegalStateException`). Example: existing {0001, 0003} gives 0004, description "Migrated from RabbitMQ 3.x <source> vhost <name>", built with `MigrationParser.exportToJson` and read back with `MigrationParser.parse` (a result that does not parse is a bug: it fails the generation loudly). Per item, from the document and the accepted proposals:
   - **Queue:** `DeclareQueue` from the source (`name`, `durable`, `autoDelete`, typed arguments WITHOUT `x-queue-type`, `x-queue-version` never added; a source `x-queue-version` is kept only for a classic queue that stays classic and is 2; stream kind gives `DeclareStream`). Proposals applied in order: the type proposal of `classic-not-replicated` (`ConvertQueueType(Quorum)` sets `type = quorum`; `KeepClassic` keeps classic), then every accepted `RemoveArgument`, `SetArgument`, `ClearAutoDelete`, `MakeDurable` whose finding scope is `Always`, or `ConvertedToQuorum` only when the queue ends quorum, or `KeptClassic` only when it ends classic.
   - **Exchange:** `DeclareExchange` with durable, autoDelete, internal and typed arguments as in the source.
   - **Policy and operator policy:** `DeclarePolicy` or `DeclareOperatorPolicy` with pattern, apply-to, priority, typed definition minus every key of an accepted `DropPolicyKeys`; when no key is left the policy is NOT written and a note says it held only keys that 4.x rejects.
   - **Binding:** `DeclareBinding` with the destination type and typed arguments; a binding whose source or destination item is skipped, unwritable, or replaced by actions that do not declare the same name (and vhost) as the item, is left out and listed in `notes` (item = the binding, text names the end and says why); when the `Replace` declares the same name (a queue, stream or exchange of that name in the item's vhost) the binding stays.
   - **Order inside a file:** exchanges, queues (and streams), policies, operator policies, bindings; each group in DOCUMENT ORDER (the order of the lists in the parsed document). Determinism means: the same document and decisions give equal results; a document with shuffled lists is a different document and gives its own order. Nothing is sorted by name except the virtual host files above. `skipped` is in the same group and document order.
   - **Skipped and unwritable:** a skipped item is listed in `skipped` with `SkipReason.SkippedByUser`; an item of kind queue, exchange, policy or operator policy whose name is exactly `.` or `..` (the parser refuses it, M8-04) is UNWRITABLE: it is never a review item (not in `items`, not in `pending`, even when it would need a decision, e.g. a classic queue named `..`; `decide` on it is `Refused(NotAReviewItem)`), so it never blocks generation, and `generate` lists it in `skipped` with `SkipReason.NameCannotBeWritten` (never dropped silently). There is no "unknown kind" reason: items of other kinds (virtual host, user, permission, topic permission, parameter, global) are not topology, are not generated and are covered by the access notes. An unknown QUEUE TYPE is not unwritable (see Accept).
   - **Never:** a delete action, a Shovel, a user, vhost or permission action, a request of any kind. A 3.x broker is never involved (the input is the parsed document and the report).
5. **Single-vhost export (P17).** For `origin = SingleVirtualHost(name)` the topology migration uses the assigned name and a note says: "This file is an export of one virtual host and holds no users, virtual hosts or permissions; the virtual host \"<name>\" must already exist on the 4.x broker".
6. **Notes** (`GenerationNote`, plain fixed text): message-loss items (queue name, "uses the old classic queue index; a new 4.x broker with this migration and a Shovel is the recommended path"), left-out bindings, the mirroring-only policies, the single-vhost notice, and for every access finding (users, vhosts, permissions): "Handled by the access migration (not part of this generation)".
7. **Fakes and tests tooling** in `core-testing`: a small builder to make documents and reports (extends `DefinitionsDocuments`), a helper that accepts every default with the needed ticks.
Out (deferred): see the end.

## How a reviewed proposal becomes something the app applies
`GeneratedMigration.file.rawJson` is the text; the caller (the later review screen, `M8-06`) saves it with the existing `MigrationFileRepository.importFile(rawJson)` into the user's migrations folder; the Migrations screen lists it and the M5-08 runner and executor apply it action by action with the profile's level, permission, virtual host check, conflict rule and read-back. This task adds no apply code, no HTTP and no persistence.

## Design notes
Pure functions and one small mutable holder (`ConversionReview`) for the decision map; no coroutines, no `Flow`, no clock (the caller passes the existing versions). Reuse `MigrationAction`, `MigrationParser.exportToJson/parse`, `ArgumentValue`, the M8-03 `Finding`, `Proposal`, `Acknowledgement`, `ItemRef` (made public as `ReviewItem` here). The decision is per ITEM because several findings of one item combine into one declaration and the UI (M8-06) asks one question per item; the findings are the explanation and the source of the defaults and alternatives. The builder is the only place that knows how a `Proposal` changes an action (`Proposal.apply(action)` as a private function per type). The ordering tick is data, enforced here, shown by `M8-06`. Safety: no secret (nothing reads a `SecretValue`), no request, no delete, no Shovel, nothing is overwritten (the caller imports with the existing repository, which refuses an existing version), 3.x is read-only (this task has no broker access at all), the message-loss finding stays visible as a note.

## UX
None here (`M8-06`: one row per item with the findings, the default proposal, the alternatives, the tick, Skip, Replace).

## MCP
None. The point is a human decision per item (spec MCP evaluation); a generated migration is an ordinary file that the read-only migration MCP tools (`M5-09`) list and dry-run.

## Open points
1. `Replace(actions)` is validated only by the parser at generation (names, types, no Shovel because the format has none); the review does not check that the user's actions make sense on 4.x (the runner's read-back and conflict rule do).
2. The optional S-K choice (set the vhost `default_queue_type` to quorum instead of rewriting each queue) is NOT built: it needs a `declareVhost` action (`M8-12`).
3. The accepted default is "convert every classic queue without `x-max-priority`" (architect default 1 of `M8-03`, not vetoed by the owner).
4. Report size: decisions in one map keyed by `ReviewItem` (M8-03 note); the UI virtualises.
5. A 3.x entity named `.` or `..` is left out and listed; a name of three or more dots is written.

## Deferred (cut from the old brief)
- The ACCESS migration (vhosts, users, permissions, topic permissions, hash pass-through, lower version, `guest` skip, algorithm manual steps): `M8-12` (it needs its own actions and the `SecretValue` handling); here every access finding only produces the note "Handled by the access migration".
- The review UI and the file save button: `M8-06`. The MCP report tool: `M8-10`. The vhost default queue type option: with `M8-12`. A dry run that compares with the broker: idea after `M5-08c`.
- The dependency on `M8-12` is removed: this task no longer needs access actions.
