# Real migration execution, persistence and conflicts

Milestone: M5 (gap found in M8-04 step 1)    Depends on: M8-04 (the widened model and `MigrationRequests`), M5-07 (merged)    Size: L

## Goal
Applying a migration really changes the broker: each action is sent to the management API (or the stream client for streams), read back, and never overwrites an existing resource with other settings; migration files and the applied-versions history are kept on disk per machine and profile; the desktop app uses all of it with the profile's real topology control level and virtual host. The two `@broker` scenarios of `10` that were never implemented run against a real broker.

## Why
Finding of M8-04 step 1 (2026-11-09), by reading the code: `MigrationsWindowContent` in `desktopApp/.../Main.kt` wires a no-op executor (`execute` returns `Success`), `InMemoryMigrationFileRepository` and `InMemoryMigrationHistoryRepository`, and `ManagementHttp` has `get` and `post` only. M5-04 was accepted on its fake-broker scenarios; "Apply a migration to a real broker" and "Exported topology can be applied to an empty broker" have no test. Two guardrail gaps came with it: the desktop screen hard-codes `controlLevel = FULL_CONTROL` instead of the profile's `topologyControlLevel`, and `MigrationRunner.dryRun` never checks the action's virtual host against the connection's (spec decision V1). Without this task the generated migrations of M8 cannot be applied in the app.

## Scope
In:
1. **Write calls in `data-rabbit`.** `ManagementHttp` gets internal `put(url, body)` and `delete(url)` with the same transport rules (TLS per profile, D9a, no credential before the user chose the profile, error classification, a body of an error is never copied). Only the migration executor may call them: a source-grep guard test lists the callers and fails for any other. The executor never calls a path containing `/get`, `/contents` or `/purge` (the app never gets, consumes, acknowledges, rejects, deletes or purges queue messages; a test asserts the allow-list of paths).
2. **`ManagementTopologyMigrationExecutor`** (implements `TopologyMigrationExecutor`; built by the gateway for a 4.x connection, `HeldConnection.migrationExecutor` nullable and null for a 3.x source, which stays read-only):
   - Declare actions use `MigrationRequests.requestFor` from M8-04. Delete actions: `DELETE /api/queues|exchanges|policies|operator-policies/...`; a 404 is success (idempotent). `deleteBinding` uses the management "properties key" path (`~` for an empty routing key, escaped otherwise): the live test measures it; unverified until then. Streams (`declareStream`, `deleteStream`) go through the held connection's existing `StreamManager`, not through management.
   - **Conflict rule (never overwritten silently).** Queue and exchange: the broker answers 400 `PRECONDITION_FAILED` for an existing resource with other settings; that is `Failed("<name> exists with different settings")`, nothing is deleted or recreated. Policy and operator policy: a `PUT` replaces silently, so the executor first reads `GET /api/policies/{vhost}/{name}`; equal (pattern, apply-to, priority, every definition key with numeric comparison) is a no-op without a request; different is `Failed("<name> exists with different settings")` and the policy is untouched. Binding: a duplicate is a no-op.
   - **Read-back after each declare:** the resource is read with its detail `GET`; missing gives `Failed("<name> was not found after it was declared")`; for a queue the type, durability and every declared argument must match (numbers compare as numbers); one retry after a short delay (named constant, injectable for tests) for slow visibility. A 4.x import skipping a queue silently is exactly what this catches.
   - Errors map to a fixed reason text (never the response body, never a secret); a timeout or unreachable broker is `Failed` with a fixed reason.
3. **`core` runner.** `MigrationRunner.dryRun` and `applyPending` take the connection's virtual host and block (not allow) every action whose `vhost` differs, with the reason "The action belongs to virtual host <v>; this connection is for <c>" (spec V1; the broker-level access actions of `M8-12` are exempt as P10 decided). The control level and the configure permission checks stay as they are. The runner treats a `Failed` result as before: stop, do not record.
4. **Persistence (`data-rabbit`).** `JsonFileMigrationFileRepository`: the folder `~/.caerbannog/migrations/` (constructor parameter, default via `System.getProperty("user.home")` like `connections.json`), one file `<version>.json` per migration holding exactly the raw text (so the checksum is stable), written atomically (temp file plus atomic move, as `JsonFileAppSettings`), never rewritten unless the user edits or imports. `JsonFileMigrationHistoryRepository`: `~/.caerbannog/migration-history.json`, `{"schema":1,"profiles":{"<profile name>":{"<version>":"<checksum>"}}}`, atomic writes, read through `parseUntrustedJson` (limit 32). Unreadable behaviour follows `M1-13`: a history file that is corrupt or too deep blocks applying with a message naming the path and a fixed reason, the file is never overwritten or deleted without an explicit user action (the "start with an empty history" action renames it to `migration-history.json.unreadable-<timestamp>` after a confirmation, the same pattern as `M1-13`; applying a destructive migration twice must never be a side effect of a lost history). A migration file in the folder that is not a valid migration is listed as invalid with the reason and is never deleted or modified. File names are the validated version (letters, digits, `-`, `_` only), so a version cannot write outside the folder.
5. **Desktop wiring.** Replace the no-op executor and the in-memory repositories in `MigrationsWindowContent`/the composition root with the real ones; use the profile's real `topologyControlLevel` and the connection's virtual host; remove the hard-coded `FULL_CONTROL`. A 3.x connection has no executor and the screen stays blocked.
6. **Export reads every page.** `MigrationsViewModel.exportCurrentTopology` calls `topologyCatalog.queues(vhost, 1)` once (first page only); it reads all pages (until the catalog says there are no more) so a vhost with more queues than one page is exported completely.
7. **Live tests.** `RealBrokerM5MigrationTest` (`data-rabbit`, `@Tag("broker")`, Testcontainers 4.x like the other `RealBroker*` tests): the scenarios "Apply a migration to a real broker" and the gate scenario "Exported topology can be applied to an empty broker" (`@gate-M5`), plus conflict (queue with other arguments, policy with other settings), read-back, delete of an absent resource, binding delete with an empty and a non-empty routing key, an exchange-to-exchange binding, typed numbers on the wire, and idempotency (apply twice). Clean up everything it creates.
Out: new action kinds (`M8-12`), MCP tools (see MCP), down migrations or rollback, a UI to choose the folder, migration of history when a profile is renamed (open point), concurrent apply from two app instances.

## Design notes
Ports in `core` (`TopologyMigrationExecutor`, `MigrationFileRepository`, `MigrationHistoryRepository` already exist; the runner gets the connection vhost), adapters in `data-rabbit`, no Compose or network code in `ui`. One executor class per concern if it grows: `MigrationWriter` (requests and status mapping), `ConflictCheck` (policy compare), `ReadBack` (verify); the executor composes them. The runner keeps its single apply loop (no copy). Secrets: nothing in this format is secret until `M8-12`; the executor logs nothing and its failure texts are fixed. The topology change guard is layered: runner (level, permission, vhost) then executor (only a 4.x held connection has one).

## UX
`docs/ux/Migrations.dc.html` has no state for: applying (per-action progress), an action failed (which action, the fixed reason), a conflict (names the resource), a history file unreadable (path, reason, "Try again", "Show folder", "Start with an empty history" with a confirmation that names the new file name), an invalid file row. The architect adds those states at step 1b before the UI work (not drawn yet). Material 3, states: empty, loading, applying, blocked (permission, level, other virtual host), applied, modified, failed, conflict, history unreadable.

## Product decisions for the owner (options and my recommendation; nothing here blocks starting the fake-broker half)
1. **Half-applied failure** (the open `@needs-decision` in `10`). A: stop at the failing action, report which one and why, do not record the migration as applied; a rerun applies it again and the idempotent declares and the read-back make the finished actions no-ops (recommended; what the runner does now). B: record progress per action so a rerun starts after the last good one (more state, history format grows). C: roll back (needs down migrations, not in the format; not recommended).
2. **Where the migration files live.** A: a fixed folder `~/.caerbannog/migrations/` next to `connections.json` (recommended for v1; simple, per machine). B: a folder the user chooses (a setting; useful for a git repository). Either way the file content and checksum are the same.
3. **MCP** (existing discrepancy): A: read-only tools only (list, dry run), apply stays a human action in the app (recommended); B: also an apply tool with all guards; C: none. Decided in `M8-10`/by the owner; not needed to start this task.
