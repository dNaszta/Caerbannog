# Show stream message annotations that are lists or maps as readable text (`x-opt-deaths`)

Milestone: M3 (a defect found by the M9-00b spike; scheduled with M9)    Depends on: none    Size: S

OWNER APPROVED running it (2026-11-17, "goes on"); no open product question remains.

## Goal
A stream message that was dead-lettered into a stream shows `x-opt-deaths` (and any other annotation or property that is a list or a map) as readable text on the Messages screen, in "Copy properties", in the property filter and in the MCP stream message tools, never as `[Ljava.lang.Object;@1a2b3c`.

## Why
M9-00b S-C7: with a stream as the dead-letter target (a recipe of `M9-09`) every dead letter carries `x-opt-deaths`, a list of maps (`queue`, `reason`, `count`, `first-time`, `last-time`, `exchange`, `routing-keys`), and the app prints the Java array's identity. The owner browses exactly these streams to see why a message came. `docs/spec.md` "Measured facts of M9-00b", S-C7.

## Scope
In:
- Where it happens (read at step 3): `data-rabbit/.../StreamMessageMapping.kt` copies every message annotation into `StreamMessage.properties` as the client's raw value (an `Object[]` for a list, nested maps and arrays inside); then `core/.../PayloadFormatter.kt` (line 213 `properties.mapValues { it.value?.toString() }` and the copy text near line 262), `StreamScanner.kt` (line 162, the property filter `message.properties[name]?.toString() == value`), `ui/.../MessageBrowserView.kt` (line 636, content type) and `mcp-server/.../McpServer.kt` (lines about 796 and 830: `put(k, v?.toString() ?: "")` for `properties` and `applicationProperties`) all print `toString()`.
- One pure function in `core` (no `java.*`), for example `PropertyValueText.of(value: Any?): String`: text as is, number and boolean as their text, a list or an array as `[a, b]`, a map as `{key: value, ...}` with nested values rendered the same way, ByteArray as the existing binary treatment if there is one (check `PayloadFormatter`; do not invent a new one). Used at all five places above. Normalising `Array<*>` to `List` in `StreamMessageMapping` is allowed if it keeps `StreamMessage` comparable, but the text rule is in `core` and unit-tested once.
- The Messages detail view shows the value on one line or wrapped; no new component. Long lists are not cut by this task.
Out: a structured viewer for death information, a new screen, any change of what is read from the broker, a new MCP tool, MCP output field types (the values stay strings).

## Step 2.5: decisions (architect, 2026-11-17, round 0)
The tests of commit 2b027eb are the exact API spec; confirmed without change. No test and no scenario changes.

1. API: `object PropertyValueText { fun of(value: Any?): String }` in `core/src/commonMain/kotlin/dev/caerbannog/core/browser/PropertyValueText.kt`. No `java.*` (the `toString()` of `UUID` and the like is common Kotlin).
2. Rules as pinned in `PropertyValueTextTest`: top-level null is `""`, nested null is `null`; text as is and unquoted; number, boolean and anything else by `toString()`; list, `Array<*>`, primitive array other than `ByteArray`: `[a, b]`, empty `[]`; map `{k: v, k2: v2}`, empty `{}`, keys by the same rule; no length cap. **Map order is the iteration order (insertion), not sorted**: it is the broker's wire order, so the text is stable for a given message and the filter's whole-text rule (and the filter example `{queue: orders, reason: rejected, ...}`) stays what the user sees. Sorting would make the text differ from the wire and from other tools; rejected.
3. `ByteArray`: lowercase hex pairs separated by one space (`0a ff`), empty is `""`, also inside lists and maps; the same text as the scanner's `joinToString(" ") { byteToHex }` (reuse `byteToHex` if it is reachable from `core`, else the same one-liner; do not use `PayloadFormatter.formatHex`, a multi-line dump).
4. Call sites (verified by grep on 2026-11-17; the brief's line numbers were right except where noted):
   - `PayloadFormatter.kt:213` (properties) and `:214` (application properties) in `inspect`: `PropertyValueText.of(it.value)`.
   - `PayloadFormatter.kt` `copyHeadersAndProperties`, the two loops at `:262` and `:269` (`"  $k: ${v ?: ""}"`, an implicit `toString()` the brief did not list): use `PropertyValueText.of(v)`.
   - `StreamScanner.kt:162` (`Property`) and `:165` (`ApplicationProperty`, not named by the brief: IN SCOPE, same rule).
   - `McpServer.kt` four sites `put(k, v?.toString() ?: "")` at `:797`, `:802` (browse tool) and `:831`, `:836` (the paged read tool): `put(k, PropertyValueText.of(v))`.
   - NOT changed: `StreamMessageMapping.kt:17-18` and `:30-33` (the annotation copy stays raw; no `Array` to `List` normalising: the text rule is in `core`, so the mapper stays a mapper); `MessageBrowserView.kt:636` and `PayloadFormatter.kt:163` (content type, a plain string in practice, a list there would be an invalid message); `MessageBrowserView.kt:834-840` (shows the already-rendered strings of `inspect`); `QueueMessageInspection` (management API JSON, not a stream message); `McpServer.kt:300` (publish schema). No export of stream messages exists (grep found none); if one is added later it must call `PropertyValueText`.
5. Filter semantics: `PropertyValueText.of(value) == criteria.value`, whole text only (owner item 11). For a property that is absent, the filter does not match (keep: `message.properties[name]` missing is no match; do not compare `""` to a missing key, check `containsKey`). Help text: the UI placeholder `MessageBrowserView.kt:256` ("Filter by text, property or application property") and the MCP descriptions `McpServer.kt:249` and `:253` ("Application property key/value to filter by") say nothing about list values; no change required (the MCP tool filters only application properties). The senior developer adds no wording.
6. Decimal64 is OUT of scope; follow-up `M9-00b-d` (below).
7. `McpSteps` uses a `FakeStreamMessageReader`; acceptable (no earlier scenario used the reader provider). The harness refused temporary wiring of the stub, so the three viewer and MCP scenarios and `McpServerTest` were only verified red: step 4 (test developer) must verify them green with `./gradlew :acceptance-tests:...` and `:mcp-server:test`.
8. Safety and architecture: no new request, no queue message read (stream messages only), browsing stays unnamed consumer, `core` stays pure, no new dependency. MCP: no new tool, no schema change (values stay strings), output change only. The rendering format (brackets, `key: value`) is visible to the user and agents: see the Owner review list.

## Follow-up brief: M9-00b-d-undecodable-property-types
Milestone: M3 (defect found while writing M9-00b-c tests)    Depends on: none    Size: S (spike first, half a day)

Goal: a stream message with a property or annotation type the client's decoder cannot read (reported by the test developer: AMQP `Decimal64` gives `IllegalArgumentException: Type not supported`) does not make the whole message, or the page, unreadable, and the user sees why.

WIDENED (architect, 2026-11-17, review of M9-00b-c): the task covers ANY message the stream client's decoder cannot read, not only Decimal64. A second known case (found in the M9-00b-c review): a message whose properties or annotations nest more than about 30 levels makes the decoder throw `DecodeException`; the reader catches `Exception` per page (`RabbitMqStreamMessageReader`), so one hostile message could fail the whole page read, with what the user sees not verified. Measure these two live rows FIRST, each with a good message before and after the bad one: (row 1) a Decimal64 application property (`IllegalArgumentException: Type not supported`); (row 2) an annotation nested 40 levels deep (`DecodeException`). Record per row: page result, error text shown, whether the messages before and after are readable, whether the consumer survives. Title and slug stay `M9-00b-d-undecodable-property-types`; option (a) below then reads "per-message notice for any decode failure".

Why it matters: the decoder runs in the stream client before the app's message handler, so the app never sees the message. The app has NO catch there: `RabbitMqStreamMessageReader` only guards `consumerBuilder.build()` and waits up to 2000 ms for the page to fill. What the user sees today is NOT verified; the expectation is a page that is short or empty (`Empty`/`NoMessagesAtOrAfterTime`) after 2 s with no error text, and possibly a consumer that stops on that chunk. A message of that kind is rare (the broker's own tools and AMQP 1.0 and MQTT publishers do not write Decimal64; a third-party AMQP 1.0 publisher could).

Scope: In: a live spike (test developer: write the message with Proton as a raw frame, as the M9-00b-c test did; browse it with the app's reader; record: page, error, whether later messages are readable); then the decision, with options: (a) catch at the client level and show "Message at offset N cannot be decoded" and continue, if the client allows it (not known); (b) accept and document. Out: any change before the spike.

MCP evaluation: no new tool; if (a) is possible the two read tools show the same notice in their result (a string field), decided after the spike.

Open points: whether the client exposes a per-message error hook (unverified); whether the consumer survives; wording of the notice (owner). Acceptance: one `@broker` live test of the measured behaviour, then scenarios after the decision. DoD as the template.
