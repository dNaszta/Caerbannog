# M9-14: The topology export keeps arguments and policies

Milestone: M9 (a follow-up outside the planner's first version, ORDERED by the owner on 2026-11-15, O14)    Depends on: none of the planner tasks (it needs its own small live spike first, below); STARTS right after M9-03, the last task of the first slice (M9-01 to M9-03)    Size: M

PLANNED 2026-11-15, confirmed for the live run 2026-11-16 (a container runtime exists now). Found while planning M9 (spec "Topology planner (M9)", "Disagreements found while planning", item 2). The owner ordered it on 2026-11-15 ("1 - y, 2 - y, 3 - y, 4 - y", answering the architect's list; item 4 was this task) to be built right after the first slice, as the architect recommended: a check or a plan made from an incomplete export misleads.

## Goal
"Export current topology" writes a migration that declares what the virtual host really has: queues with their durable flag and arguments, exchanges and bindings with their typed arguments, and the policies. Applying the exported file to an empty broker gives the same topology.

## Why
`tests/bdd/features/10_topology_migrations.feature`, "Export the current topology as a migration", says the file "declares the queues, exchanges, bindings and policies of the broker", and the `@gate-M5` scenario says an exported topology can be applied to an empty broker. The code (`MigrationsViewModel.exportCurrentTopology`) writes queues by name and type only, exchanges without arguments, bindings without arguments and no policy; `MigrationsViewModelExportTest` pins "exported queues have no arguments"; the step definition of the scenario does not look at policies. So an export of a topology with dead-letter arguments, a headers binding, a super stream exchange (`x-super-stream`) or a policy is silently incomplete, and the gate passes only because its topology has none of these. With the planner such topologies become common.

## Scope
In:
- A short spike first (live, `rabbitmq:4-management`): which fields `GET /api/queues/{vhost}` gives with `columns=...,arguments,durable,auto_delete` and their JSON types; `GET /api/policies/{vhost}`; which arguments the broker adds on its own and must not be exported (`x-queue-type` is the `type` key).
- `core`: `TopologyCatalog` gains what the export needs behind the interface (typed arguments and flags of queues, typed arguments of exchanges and bindings, the policies of a virtual host), as new read methods or fields, all GET; the display rows of the Topology screen are unchanged.
- `MigrationsViewModel.exportCurrentTopology` writes them; a file without any of them stays byte for byte what it is today (the M8-04 rule).
- `data-rabbit`: the reads, through the catalog's existing guard (every request a GET of an allowed shape, never a path under a queue's name).
- The scenario's step checks policies and arguments; the gate topology gets a queue with an argument, a headers binding and a policy.

Out: users, virtual hosts and permissions (never exported; the access migration of M8 is the only place for them); a stream's own arguments (retention, `x-queue-leader-locator`) while `declareStream` has none (named in the one line under the export result, see "Spike results and API shape confirmed"; a later `declareStream` growth would lift it). CHANGED at step 2.5: streams themselves (plain and super stream partitions) and operator policies are IN scope (spike: the export dropped streams completely; operator policies are needed for equality).

### API shape (the tests are the spec)
- `core`: `QueueDeclaration(name, vhost, type, durable = true, autoDelete = false, exclusive = false, arguments: Map<String, ArgumentValue> = emptyMap())`; `PolicyRow(name, vhost, pattern, applyTo, priority, definition)` as the tests build it; `ExchangeRow.typedArguments` and `BindingRow.typedArguments` (default empty, display `arguments` unchanged); `TopologyCatalog.queueDeclarations(vhost)`, `policies(vhost)`, `operatorPolicies(vhost)` each `CatalogResult<List<...>>`, GET only, every queue and stream, no page parameter. `QueueRow`, `queues()` and the Topology screen stay untouched. `GuardedTopology` passes the three through the stale-connection guard (Unreachable once not current). `MigrationsScreenState.exportNote: String?` belongs to the last export (cleared by a later export or failed one).
- `data-rabbit`: `ManagementRequests.queueDeclarations/policies/operatorPolicies`, `QueueDeclarationPage`, `ManagementJson.parseQueueDeclarations/parsePolicies`, `ManagementTopologyCatalog` loops over pages itself (one GET per page, columns `name,type,durable,auto_delete,exclusive,arguments`, no partial list when a page fails, loop guard). The catalog guard's allow-list gains exactly three GET shapes: `/api/queues/{vhost}` (already there, new column list), `/api/policies/{vhost}`, `/api/operator-policies/{vhost}`; still never a path under a queue name.
- `x-queue-type` is never copied into `arguments` (it is the `type` key).
- Exporter rules: user bindings on built-in exchanges are exported, source `""` is dropped (E4); a binding whose queue or destination was left out is dropped; no secret exists in any of these reads.
- Fakes: `FakeTopologyCatalog.declare/addPolicy/addOperatorPolicy/addStream(arguments)`, `PagedTopologyCatalog` forwards the three. `MigrationsViewModel.allQueues` is dead after this task: delete it if nothing else uses it.

### Safety and MCP
