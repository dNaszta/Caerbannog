# Management HTTP: a GET that meets a connection the broker just closed is answered, not reported as a lost connection

Milestone: M2 (hardening)    Depends on: none (the pinned test is on main since 5ad11dd)    Size: S

## Goal
A refresh that lands on a management connection RabbitMQ is just closing is answered on a fresh connection and the screen stays live; a broker that really is gone is still reported at once as a lost connection (D2, unchanged); a POST, PUT or DELETE is still sent once, never twice.

## Why
`docs/spec.md` "Connection lifecycle", the bullet "Idle connections and what unreachable means" (written with this brief), and the D2 bullet above it. Found by CI run 43640828120 (`RealBrokerClientsTest`, the clients tab froze on "Connection lost" for good) and pinned by the test developer in commit 5ad11dd (`ManagementHttpClosedConnectionTest`). Today a user with the default 5 s refresh can be thrown into "Connection lost" by a broker that is perfectly healthy, on the stream list, the clients tab and the topology screen (the three users of `RefreshLoop`).

## Decision (architect, 2026-11-15)
Option (c): both measures. D2 and `RefreshLoop` stay as they are.

1. **(a) a bounded retry of the GET inside `ManagementHttp`.** It is the fix the pinned RED test asks for, it is protected by "at most two attempts", and it also covers a proxy or load balancer with an idle timeout shorter than 5 s, which no JVM setting reaches.
2. **(b) the JDK client's idle timeout below the broker's.** It is the only measure that helps the verbs rule (a) must never retry. The JDK retries a failed GET once, never a POST, PUT or DELETE (checked in the JDK 21 source, `MultiExchange.getExceptionalCF`: one retry through `expiredOnce`, `canRetryRequest` allows GET and HEAD only), and the app must not retry them either (a lost answer may hide an applied change). A write that meets the closing connection today is `Unreachable`, with no retry possible; with the client's idle timeout at 2 s it never reuses a connection older than 2 s, so the 5 s edge is gone for every verb. Measured by the test developer: with `-Djdk.httpclient.keepalive.timeout=2` the live test passed 30 of 30 (10 of 30 failed without it, broker at 0.3 CPU). Cost: none in the default setup (at 5 s intervals the broker has already closed the connection, so each tick opens one today as well); bursts inside one load still reuse the connection.
3. **`RefreshLoop.ask` does not treat the first `Unreachable` any differently.** Reasons: (i) D2 is a decision of the product owner (2026-11-04, "i confirm") and is written into the spec and `13` ("A lost connection offers a retry, not a silent reconnect"); (ii) the defect is that the transport called a healthy broker unreachable, and the transport is where it is fixed: after this task `Unreachable` means "the broker did not answer a fresh attempt"; (iii) a retry on the next tick would need the clients to stay open after `connectionLost` closed them, which is an automatic reconnect, a product feature (age display, Retry button, load token, stale rows all change) and the very thing D2 ruled out for M2; (iv) it would delay "a broker that is really gone is reported" by one refresh interval, up to 60 s. If the owner ever wants tolerance for a failed poll or reconnecting by itself, that is a separate product decision (see Open points); nothing here prevents it.

Facts checked by the architect: JDK 21 `HttpClientImpl.KEEP_ALIVE_TIMEOUT` is a `static final long` read from `jdk.httpclient.keepalive.timeout` when the class loads (default 30 s), so the property is JVM-global and only works when set before the first JDK client exists; `ConnectException` is already retried once by the JDK (`RETRY_CONNECT`, on by default); the only production code that creates a JDK client is `TlsSupport.buildHttpClient` (grep of `HttpClient(`, `HttpClient.newBuilder`, `java.net.http` in the main sources; `dev-seed` is a developer tool and not shipped); `RefreshLoop.ask` is the only caller of `ActiveConnection.connectionLost`, so a failed write or peek never turns into a lost connection by itself (it shows its own error), which makes the writes less urgent than the polls but not harmless (a failed Apply or Forward step is a confusing error).

2. **(a) in `ManagementHttp`** (data-rabbit, internal):
   - Only `get` changes. `post`, `put` and `delete` keep exactly one attempt.
   - At most two attempts per `get`, no loop, no delay between them, same method, same URL, the credential is added again by the same lambda, nothing is logged, no exception text is kept (the existing rule of the class).
   - The second attempt happens only after a failure that is a dropped connection: an `IOException` that is **none of** an `SSLException` (classified as today, `CertificateRejected` or `NoTlsAnswer`), any timeout (the JDK's `HttpTimeoutException` family, `java.net.SocketTimeoutException`, Ktor's `HttpRequestTimeoutException`, `ConnectTimeoutException` and `SocketTimeoutException`; a timeout means a slow or gone broker and retrying doubles the wait), `java.net.ConnectException` (refused: nobody listens, and the JDK already tried twice), `java.net.UnknownHostException` and `java.net.NoRouteToHostException`. Not retried either: `CancellationException`, `URISyntaxException`, `URLParserException`, `IllegalArgumentException`, any other `RuntimeException` (all as today).
   - The `closed` flag is checked again before the second attempt: a holder closed in between sends nothing more and answers `Unreachable` as today.
   - The outcome of the second attempt is final: its `Response`, or the same classification as today. One catch ladder only: keep the ladder in one function that returns a small sealed result (a reply, or "the connection dropped") and put the retry in `get` around it; do not duplicate the ladder and do not add a boolean parameter that switches the behaviour.

Comment says why: the broker closes idle keep-alive connections after 5 s, the property is JVM-global and read once by the JDK, and it only works before the first JDK client, which is why production code creates JDK clients in `TlsSupport.buildHttpClient` only. ## Design notes
Module `data-rabbit` only (`ManagementHttp.kt`, `TlsSupport.kt`, tests). No change in `core`, `ui`, `desktopApp` or `mcp-server`. The pinned server in `ManagementHttpClosedConnectionTest` drops every request on a reused connection regardless of idle time, so only (a) can turn it green; (b) is proven by the property test, the source guard and the one-off 30-run check. Where the broker is real: only the step 4 runs. Safety rules in `CLAUDE.md` hold: a 3.x broker still gets GET only (a retry repeats the same GET), no queue message path is added, no plain path is added (the transport choice stays the profile's), no secret enters a log or a reply.

## UX
None. No screen changes; the state "Connection lost" (D2) is unchanged and simply stops appearing for a healthy broker.

## MCP
None (internal transport behaviour). Every MCP tool that reads through a held connection (streams, topology, the 3.x analysis, shovel status) goes through the same `TlsSupport` and `ManagementHttp`, so it gets the fix without a change; no new tool, no new input, and the peek tool's POST is untouched.

## Open points
- Product, optional and **not asked now**: D2 treats one failed data call as a lost connection until the user presses Retry. A real network blip (a Wi-Fi drop of one second) still does that. Tolerating one failed poll, or reconnecting by itself, is a product decision with spec and screen consequences (D2, the `13` scenario, the stale banner); the owner can raise it any time. This task does not depend on it.
- Unverified: the exact exception type the JDK throws for every stale-connection shape (the pinned test shows a plain `IOException` "header parser received no bytes"; a reset may be a `SocketException`). The deny-list above is deliberately about what must not be retried, so an unlisted dropped-connection type is retried once; the developer adds any type seen in step 4 to the (iii) test row.
- Not verified by the architect: the 0.3 CPU runs and the value 2 (taken from the test developer's report; the property name, the one-time read and the retry rules were checked in the JDK 21 source).
