# Widen the migration action model for converted 3.x topology

Milestone: M8    Depends on: M8-00 (done), M8-01 (merged), M5-07 (merged)    Size: M

## Goal
The M5-04 migration format can express what a converted topology needs (typed queue arguments, exchange flags and arguments, binding arguments and exchange destinations, policies and operator policies with typed definitions, `apply-to` and priority); every existing migration file still loads, checksums and means the same; the request bodies that send these actions to the management API are built and proven on a real 4.x broker; the migrations screen shows the new details.

## Why
`core/.../migrations/MigrationModels.kt` has fields that the parser never reads (`DeclareQueue.arguments` and `DeclarePolicy.definition` are `Map<String,String>`, always empty) and no place for exchange flags, policy `apply-to`/priority or exchange destinations. A faithful conversion (`M8-05`) cannot be written in that format: a numeric `x-delivery-limit` would become a string. Spec "Format additions for converted topology (M8-04)" (added in step 1) and "Reuse of the migrations feature".

## Findings of step 1 (read the code as it is; the old brief was wrong on these)
1. **There is no real executor.** `TopologyMigrationExecutor` has only the fake (`core-testing`) and a no-op in `desktopApp/.../Main.kt` (`MigrationsWindowContent`: `execute` returns `Success`). `ManagementHttp` has `get` and `post` only (no PUT, no DELETE). The file repository and the history are in memory (`InMemoryMigrationFileRepository`, `InMemoryMigrationHistoryRepository`): files and applied-version history are lost on restart. The @broker scenarios "Apply a migration to a real broker" and "Exported topology can be applied to an empty broker" have no test. So the old brief's "executor support in `data-rabbit` (management PUT bodies)" has nothing to extend. See "Scope" for the split and "Product decision" for the owner.
2. The parser ignores `arguments` and `definition` today and `exportToJson` never writes them.
3. `unknown action` already works: `else -> Invalid("action '<name>' is not supported; which action is not supported")` (a `declareShovel` action is rejected). The message echoes the action name; this task keeps the phrase "which action is not supported" and stops echoing a name that is longer than 64 characters or holds anything but letters and digits (untrusted text, same rule as M5-07).
4. The export (`MigrationsViewModel.exportCurrentTopology`) drops `durable`, `autoDelete`, `internal` of exchanges and the destination type of bindings although `ExchangeRow` and `BindingRow` carry them.

## Scope
In (module `core` unless said):
1. **Typed value type, neutral package.** Move `ArgumentValue` and `MAX_ARGUMENT_DEPTH` from `dev.caerbannog.core.migrate3x` to `dev.caerbannog.core.json` (a package dependency from `migrations` to `migrate3x` would be a cycle: `M8-05` makes `migrate3x` depend on `migrations`). Move the JSON conversion that now sits private in `DefinitionsEntryReader.kt` (`toArgument`, `toScalarArgument`) into a public `object ArgumentValueJson` in the same package: `fun parse(element: JsonElement, maxDepth: Int = MAX_ARGUMENT_DEPTH): ArgumentValue?` (null when nested too deep, or when a primitive is not a string, boolean or finite number: the M8-01 F1/F2/F3 rules) and `fun encode(value: ArgumentValue): JsonElement`. `DefinitionsEntryReader` calls it and maps null to `MalformedSectionException`. This is an allowed refactor: the M8-01 and M8-03 files and tests that mention `ArgumentValue` or `MAX_ARGUMENT_DEPTH` change only their imports (list: `AnalysisContext`, `ClassicIndexRule`, `DefinitionsEntryReader`, `DefinitionsModel`, `DefinitionsReader`, `ProposalJson`, `ProposalText`, `QueueRules`, `ReportModel`, `DefinitionsDocuments` in `core-testing`, `Migrate3xDefinitionsSteps`, and the tests `DefinitionsDepthLimitsTest`, `DefinitionsModelNoSecretStringTest`, `DefinitionsParserFixtureTest`, `...LargeFileTest`, `...NestingTest`, `...NonJsonLiteralTest`, `...SingleVhostTest`, `...ToleranceTest`, `QueueRulesTest`, `ReportJsonTest`, `ReportSecretsTest`); no assertion changes.
2. **Model (additive; defaults keep old meaning).** In `MigrationModels.kt`:
   - `DeclareQueue(name, type = "quorum", vhost, durable = true, arguments: Map<String, ArgumentValue> = emptyMap(), autoDelete: Boolean = false)`. The `arguments` type changes from `Map<String,String>`; its only uses are the default (verify by grep at step 2; a test that passes strings is changed to `ArgumentValue.Text`).
   - `DeclareExchange(name, type, vhost, durable, autoDelete = false, internal = false, arguments = emptyMap())`.
   - `DeclareBinding(exchange, queue, routingKey, vhost, destinationType: BindingDestinationType = QUEUE, arguments = emptyMap())`. `queue` stays the name of the destination (source compatibility); `BindingDestinationType` is the existing enum in `dev.caerbannog.core.topology`. `description` for an exchange destination reads "Bind <exchange> to exchange <destination> [with <key>]".
   - `DeclarePolicy(name, pattern, definition: Map<String, ArgumentValue> = emptyMap(), vhost, applyTo: String = "all", priority: Int = 0)`.
   - NEW `DeclareOperatorPolicy(name, pattern, definition, vhost, applyTo = "all", priority = 0)` (`actionName` `declareOperatorPolicy`, description "Declare operator policy <name>", not destructive). Architect addition: without it the 3.x operator policies (for example `op-limit`) would be dropped by the conversion; 4.x accepts only limit keys there (S-E), which the broker enforces. No delete action for it.
   - New optional `val detail: String? get() = null` on `MigrationAction`: for the declare actions above, a one-line summary of arguments or definition, `key=value` pairs sorted by key joined by ", ", each value shown with `ArgumentValue` text (text as is, numbers plain, boolean, null as `null`, list and object as compact JSON), cut at 120 characters with an ellipsis; null when there is nothing to show. EXACT format (decided at step 2): queue, exchange, binding: `key=value, key=value` over the arguments, sorted by key (a queue or exchange or binding without arguments has `detail == null`). Policy and operator policy: `apply-to=<applyTo>, priority=<n>` first, then `; ` and the definition pairs `key=value, key=value` sorted by key; with an empty definition only `apply-to=<applyTo>, priority=<n>` (so a policy detail is never null). The whole string is one line: every control character in a key or value becomes a space; it is cut at 120 characters in total (119 characters plus `…`). Example: `apply-to=quorum_queues, priority=7; max-length=1000, overflow=reject-publish`. `description` text is NOT changed (tests pin it).
   - Validation at parse time, fixed messages, nothing from the input echoed: `applyTo` must be one of `all`, `queues`, `classic_queues`, `quorum_queues`, `streams`, `exchanges` else "the policy apply-to is not supported"; `destinationType` must be `queue` or `exchange` else "the binding destination type must be queue or exchange"; `arguments` or `definition` not an object, or a value that `ArgumentValueJson.parse` refuses, else "the arguments are not valid or nested too deep"; a `declareQueue` argument named `x-queue-type` else `the queue type belongs in "type"`; `priority` not a whole number else "the policy priority must be a whole number". Only `all` and `queues` are measured on 4.x; the others come from RabbitMQ's documentation and are checked by the live test below.
3. **Parser and exporter.** Keep the public API (`MigrationParser.parse`, `exportToJson`, `computeChecksum`) byte for byte. Refactor the 265-line `when` into one small codec per action (`interface ActionCodec { val name: String; fun read(obj: JsonObject): ActionReadResult; fun write(action, builder) }` and a registry map in one file); M8-12 adds four more codecs and must not grow the `when`. Allowed refactor: all existing migration tests pass unchanged. Reading: new keys are optional; the existing `queue`/`destination` synonym stays. Writing: a new key is written only when it differs from its default, in this fixed order after the existing keys: `autoDelete`, `internal`, `destinationType` (the destination name is always written under `queue`, also for an exchange destination; `destinationType` says which), `arguments`, `definition`, `applyTo`, `priority`. So an export of a topology that uses no new feature is byte-identical to today's export (same checksum).
4. **Checksum.** `computeChecksum` is untouched and still runs over the raw text. A test proves that a golden old-format file (checked in from the M5-04 tests) gives the same parsed actions and the same checksum before and after the change.
5. **Export of the current topology** (`MigrationsViewModel.exportCurrentTopology`) keeps working and now carries what the rows hold: exchange `durable`, `autoDelete`, `internal`, and the binding destination type. "Keeps working" means: the same rows give the same file when every flag has its default (byte-identical), and a non-default flag is written instead of being lost. Queue arguments are not in `QueueRow`, so exported queues have none (unchanged, documented).
6. **`data-rabbit`: request bodies, no executor.** New `internal object MigrationRequests` (file `MigrationRequests.kt`, uses `ManagementRequests.encode` for path segments) with `fun requestFor(action: MigrationAction): ManagementWrite?` (`data class ManagementWrite(val method: String, val path: String, val body: JsonObject?)`, methods `PUT` or `POST`) for the declare actions only (delete actions and streams are the executor's job, `M5-08`; they return null here and a test says so):
   - `declareQueue`: `PUT /api/queues/{vhost}/{name}` body `{"durable":d,"auto_delete":a,"arguments":{"x-queue-type":"<type>", <typed arguments>}}` (`x-queue-type` first).
   - `declareExchange`: `PUT /api/exchanges/{vhost}/{name}` body `{"type":t,"durable":d,"auto_delete":a,"internal":i,"arguments":{...}}`.
   - `declareBinding`: `POST /api/bindings/{vhost}/e/{source}/q/{destination}` for a queue, `.../e/{source}/e/{destination}` for an exchange, body `{"routing_key":k,"arguments":{...}}`.
   - `declarePolicy`: `PUT /api/policies/{vhost}/{name}` body `{"pattern":p,"definition":{...},"priority":n,"apply-to":a}`.
   - `declareOperatorPolicy`: `PUT /api/operator-policies/{vhost}/{name}`, same body.
   Numbers stay numbers (`Whole` becomes a JSON integer, `Decimal` a JSON number, `Flag` a boolean, `Nothing` JSON null) through `ArgumentValueJson.encode`. No request is sent by this task: the real executor (HTTP PUT/DELETE, read-back after each action, persistent file and history repositories, wiring in the desktop app) is the separate task `M5-08-real-migration-execution` (see Product decision).
7. **Fake executor** (`core-testing` `FakeTopologyMigrationExecutor`): `DeclareExchange` fills `durable`, `autoDelete`, `internal` of the `ExchangeRow` from the action; `DeclareBinding` uses the action's destination type; it records declared policies and operator policies and declared queues with their arguments in read-only maps (`declaredPolicies`, `declaredOperatorPolicies`, `declaredQueues`, keyed by vhost and name, holding the action) so tests can assert typed values; `executedActions` keeps working. No other behaviour change.
8. **Migrations screen.** In `MigrationsScreen.kt` the dry-run action row (the `actionDryRun.action.description` text at about line 515) shows `action.detail` as a second line (`bodySmall`, `onSurfaceVariant`, test tag `actionDetail:<index>`) when it is not null. The raw JSON view already shows everything. No secret can appear (queue arguments and policy keys; `SecretValue` is not in this format until `M8-12`, which redacts its own fields). `docs/ux/Migrations.dc.html` gets a one-line secondary text under an action title: the architect adds it at step 1b before the UI work, it is not drawn yet.
Out: the real executor, persistence and read-back (`M5-08`), Shovel (never a migration action), vhost, user and permission actions (`M8-12`), delete actions for operator policies, queue arguments in the export, any new screen, any MCP change.

## Design notes
Backward compatibility is the whole risk: the checksum is over raw text, old applied files are untouched, and the parsed action of an old file is equal to the old one (the new fields default). `ArgumentValue` is a sealed type, never `Any`. One codec per action keeps the parser extensible for `M8-12`. `MigrationRequests` is a pure function in `data-rabbit` (internal), so it is unit tested without a broker and reused by the real executor (`M5-08`). The live test is the only place that talks to a broker and it does not use production code that does not exist. `core` stays free of `java.*` and of anything that reads queue messages.

None. Internal model. The existing migration MCP tools (the M5-04 brief lists them, they are not built: see the M5-04 and M8-10 notes) would benefit automatically. No tool creates or removes a Shovel; the format has no such action and a test says so.
