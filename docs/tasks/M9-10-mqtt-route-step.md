## Goal
The wizard kind "MQTT route" asks for a topic filter and a destination queue or stream and adds one `declareBinding` on `amq.topic`. The step, the review graph and the Migrations screen show it as an MQTT route with its topic filter, also when a file is opened again (a step of an opened file is recognised, not only one built by the form).

## Why
Owner decision O2 ("add MQTT ability too"). Spec "Topology planner (M9)": A10, "MQTT routes"; spec "MQTT support (M6)" for the existing dialog and the `amq.topic` rule.

## Scope
In:
- `core.planner` (or `core.mqtt`, next to the existing model): `MqttTopicTranslation.toBindingKey(filter): Translation` (`Key(text)` or `Refused(reason)`) and `toFilter(key): String?`, exact inverses of each other on what the form accepts (rule A16, measured by M9-00a S-A1 to S-A3). `toBindingKey`: `/` to `.`, a whole-level `+` to `*`, `#` kept (`devices/+/answer` is `devices.*.answer`, `+` is `*`, `a/b/c` is `a.b.c`). `toFilter` is `.` to `/`, `*` to `+`, and returns null for a key with an empty word, a word that mixes `*` or `#` with other characters, or a `#` that is not the last word. Refusals as typed reasons (an enum, not strings in the logic): empty filter, `#` not last, `+` not a whole level (fixed texts "Enter a topic filter", "# must be the last level", "+ must stand for a whole level"), and, new from the measurement: `DotInLevel` (the broker reads it as another level), `StarInLevel` (any level that holds `*`, also a whole-level `*`, which was not measured and is refused as the safe side), `EmptyLevel` (an empty level, a leading or a trailing `/`: they work on the broker, refusing them is a product choice against typing mistakes). The texts of these three are proposals held in one constants object (Owner review list items 1 to 3). Accepted and carried unchanged: a space, a leading `$`, upper case (not measured: case, length above 255 bytes, non-ASCII). No "cannot be translated safely" message exists any more: each refusal names its reason.
- `MqttRouteForm(filter, destination, destinationKind)`; `actions`: `DeclareBinding(exchange = "amq.topic", queue = destination, routingKey = key)`; the form shows the key, a matching concrete topic (the existing `StreamInboundRoute.routingKeyToSuggestedMqttTopic`) and the sentence that `amq.topic` is an ASSUMPTION (Owner review list item 4: the old sentence "Uses the broker's default MQTT exchange amq.topic." is dropped, because the app cannot read the broker's MQTT exchange (S-B1) and a route on a broker with another one is applied without error and routes nothing for MQTT (S-B2); the sentence never states it as a fact).
- Recognition (A10): `MqttRoutes.routeOf(action)`: a `DeclareBinding` on `amq.topic` to a queue (a stream is a queue for a binding), without arguments, whose key gives a filter that gives the same key again. Its words: "MQTT route <filter> to stream <name>", "to queue <name>" or, when the planner cannot tell the kind (not in the plan, not known on the broker), "to <name>"; its second line names the binding and the key.
- `planPreview`: `edgeLabels` for a route (the filter, and "MQTT route").
- Migrations screen: the action rows of a migration use the same words (the planner step list, the Migrations screen and the review graph share one function, `MqttRoutes.routeOf`). The button "Send a test message" is `M9-10b`.
- `ui`: the kind card, `MqttRouteFormView` (testTags chosen by the test developer, written in the report), the edge label.

Out: "Send a test message", the sample-value dialog, the correlation-id header and its warning (all `M9-10b`); MQTT subscriptions, QoS or retained settings of a route (a route is only a binding; measured: QoS 0, QoS 1 and retained publishes all arrive, a retained one is not marked); another MQTT exchange than `amq.topic` (S-B1: it cannot be read through the management API; the optional hint from subscriber bindings is `M9-10c`); publishing from the planner itself; MQTT 5 correlation data and response topic in the dialog (the dialog has no such fields; only if S-A7 and the owner ask for them); the optional MQTT ticks of a stream pair (`M9-07b`).

## Design notes
The translation is the one place that knows the rule; the existing display helper `StreamInboundRoute.routingKeyToMqttFilter` (it splits on `.` and `/` and drops empty parts) is left alone unless S-A shows it wrong for a key, which is then a small follow-up named in the report. The binding is applied by the existing executor: no new request. Technical decisions of step 1 (2026-11-17), checked against main: (1) `StepForms.formOf` today turns every `DeclareBinding` without arguments into `BindingForm`; it must try `MqttRoutes.routeOf` first and return `MqttRouteForm`, else the binding keeps its form; the step words (planner list, Migrations rows, graph) come from the action through `routeOf`, so a binding typed in the binding form on `amq.topic` that is a plain route is worded as a route too (consistent, no second path). (2) A stream destination is a `DeclareBinding` with `destinationType = QUEUE` (a stream is a queue for a binding); an exchange destination is never a route. (3) The kind word comes from the plan's own `DeclareQueue` and `DeclareStream` steps, then `KnownTopology`; else "to <name>". (4) The filter's suggested topic uses the existing `StreamInboundRoute.routingKeyToSuggestedMqttTopic`: for every key the form accepts (no empty word, no `.` inside a level) it is right; `routingKeyToMqttFilter` is NOT used (it drops empty words). (5) Problems are `FieldProblem("filter", text)` and `FieldProblem("destination", PlannerTexts.BINDING_DESTINATION_MISSING)`; the action is round-tripped through `FormChecks.parserReason`, as the binding form does. (6) All texts live in `PlannerTexts` (or one `MqttRouteTexts` object next to the translation), none inline in a composable. (7) No new dependency; no new broker request: the executor is the existing one. Where the broker is faked: `FakeTopologyCatalog` and `FakeManagementBroker` in the unit and BDD tests; real in the live test.

### F1 (major): the labels of the review graph overlap. FIX IN THIS TASK
Cause (read in code): `buildBindingGraph` places the label of a labelled edge at the middle of its curve and, when labels collide (`resolveEdgeLabelPositions`, 60 dp across, 18 dp down), staggers them by about 18 dp. In the review graph one edge carries up to four things (key pill 18 dp, "new" pill, filter text, "MQTT route" tag), drawn as separate elements at fixed offsets (`+18` for "new", `MQTT_LABEL_OFFSET = 34` for the route lines), so a stagger of 18 dp makes them sit on the neighbour's. Two plain bindings already overlapped before this task; the route lines made it worse. Edges from one exchange to one destination share one curve, so labels have nowhere better to go than a stack in the gap between the layers.

REMEDY (the simplest that leaves the Topology path untouched): in `BindingGraphCanvas`, ONLY when `plan != null`, draw the labels of an edge as ONE block (a `Column`, centred on `labelX`): the key pill (when the key is not empty), under it the "new" pill, under it for a route the filter text and the "MQTT route" tag. Blocks whose anchors collide (labelX within 60 dp and labelY within the height of one block) are stacked vertically around the common anchor, in edge order, with at least 4 dp between two blocks; the stack is moved down as a whole when it would start above 8 dp. The graph box height grows to hold the lowest block plus the existing 48 dp margin (the review graph is already "as big as its content"; the Topology graph keeps its 640 x 400 minimum and is not touched). `MQTT_LABEL_OFFSET` and the `+18` offset of the "new" pill disappear in the plan path (they are replaced by the block); the stacking is a small pure `internal` function in `ui/.../topology` (the senior developer names it) with its own unit test. No change to `buildBindingGraph`, `resolveEdgeLabelPositions`, `BindingsGraphView`, the layer spacing or any core type. No new words. All tags stay (`edgePill:<key>`, `planGraphNew:edge-<i>`, `planGraphEdgeLabel:<id>`, `planGraphEdgeTag:<id>`, `planGraphNode:*`); ONE tag is added on the inner graph box of the review path only: `planner:reviewGraphContent` (the `Box(Modifier.size(graphWidth, graphHeight))` when `plan != null`; a tag changes no pixel).
Rejected: more space between layers (it widens every plan, does not help labels that share one curve, and the vertical collision is what fails); per-edge placement without stacking (the same problem); ONE pill `sensors.*.temp (sensors/+/temp)` (hides that the key and the filter are two things, drops the "MQTT route" words that O15 and the spec ask for, and still needs the "new" pill, so stacking is needed anyway).

### F2 (minor): `amq.topic` reads "not in this plan". FIX NOW, as a general rule

When the broker is read, the real reader lists the `amq.*` exchanges (`PlanReviewGraphUiTest` style rigs list what the fake is given), so the mark shows only when nothing was read or the reader's list lacks it.
