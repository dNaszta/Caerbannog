# M9-10: MQTT route step: a topic filter to a queue or stream, saved as a binding on amq.topic

Milestone: M9    Depends on: M9-00a (measured 2026-11-16: S-A1 to S-A4, S-B, S-A6, S-A7), M9-03, M9-04; the refusal texts, the `amq.topic` assumption sentence and the sentence under the correlation-id header wait for the owner (Owner review list of `M9-00a`, items 1 to 5), the logic does not; "Edit steps" scenarios also need M9-12    Size: M (the largest of M9; if step 3 passes its third day, the sample-value dialog, which depends on nothing else in this task, is cut out as `M9-10b`)

PLANNED 2026-11-15. Not started.

## Goal
The wizard kind "MQTT route" asks for a topic filter and a destination queue or stream and adds one `declareBinding` on `amq.topic`. The step, the review graph and the Migrations screen show it as an MQTT route with its topic filter, also when a file is opened again. After the migration is applied, "Send a test message" opens the existing Publish MQTT dialog with a topic that matches.

## Why
Owner decision O2 ("add MQTT ability too"). Spec "Topology planner (M9)": A10, "MQTT routes"; spec "MQTT support (M6)" for the existing dialog and the `amq.topic` rule.

## Scope
In:
- `core.planner` (or `core.mqtt`, next to the existing model): `MqttTopicTranslation.toBindingKey(filter): Translation` (`Key(text)` or `Refused(reason)`) and `toFilter(key): String?`, exact inverses of each other on what the form accepts (rule A16, measured by M9-00a S-A1 to S-A3). `toBindingKey`: `/` to `.`, a whole-level `+` to `*`, `#` kept (`devices/+/answer` is `devices.*.answer`, `+` is `*`, `a/b/c` is `a.b.c`). `toFilter` is `.` to `/`, `*` to `+`, and returns null for a key with an empty word, a word that mixes `*` or `#` with other characters, or a `#` that is not the last word. Refusals as typed reasons (an enum, not strings in the logic): empty filter, `#` not last, `+` not a whole level (fixed texts "Enter a topic filter", "# must be the last level", "+ must stand for a whole level"), and, new from the measurement: `DotInLevel` (the broker reads it as another level), `StarInLevel` (any level that holds `*`, also a whole-level `*`, which was not measured and is refused as the safe side), `EmptyLevel` (an empty level, a leading or a trailing `/`: they work on the broker, refusing them is a product choice against typing mistakes). The texts of these three are proposals held in one constants object (Owner review list items 1 to 3). Accepted and carried unchanged: a space, a leading `$`, upper case (not measured: case, length above 255 bytes, non-ASCII). No "cannot be translated safely" message exists any more: each refusal names its reason.
- `MqttRouteForm(filter, destination, destinationKind)`; `actions`: `DeclareBinding(exchange = "amq.topic", queue = destination, routingKey = key)`; the form shows the key, a matching concrete topic (the existing `StreamInboundRoute.routingKeyToSuggestedMqttTopic`) and the sentence that `amq.topic` is an ASSUMPTION (Owner review list item 4: the old sentence "Uses the broker's default MQTT exchange amq.topic." is dropped, because the app cannot read the broker's MQTT exchange (S-B1) and a route on a broker with another one is applied without error and routes nothing for MQTT (S-B2); the sentence never states it as a fact).
- Recognition (A10): `MqttRoutes.routeOf(action)`: a `DeclareBinding` on `amq.topic` to a queue (a stream is a queue for a binding), without arguments, whose key gives a filter that gives the same key again. Its words: "MQTT route <filter> to stream <name>", "to queue <name>" or, when the planner cannot tell the kind (not in the plan, not known on the broker), "to <name>"; its second line names the binding and the key.
- `planPreview`: `edgeLabels` for a route (the filter, and "MQTT route").
- Migrations screen: the action rows use the same words, and an MQTT route of an applied migration gets "Send a test message" (A15); disabled with the reason when the profile has no MQTT port or the existing publish gate refuses; not offered for a pending or modified file.
- The test message with sample values (A15, proposed by the architect and wanted by the owner: O14, 2026-11-15): `MqttTopicSample.fill(filter, values): SampleResult` in `core.mqtt`, pure: one value for every `+` (the dialog starts the field as `item` and says "Value for the + in level N", with the hint "for example a device id") and one for a `#` (starts as `test`, "Value for the rest of the topic"); a filter without wildcards asks nothing. Fixed refusals: "Enter a value", "One level only: no /" (for a `+`), "No + or # in a value"; a refused value never opens the dialog. Then the existing Publish MQTT dialog opens with the concrete topic (the dialog accepts no wildcards) and one header, key `correlation-id` (constant, Q17), value from an injected `CorrelationIdSource` (a UUID in the composition root, a counter in tests), as an MQTT 5 user property in the dialog's own headers list, editable like any header. For that, `PublishMqttViewModel` gets one optional parameter `initialHeaders: List<MqttHeader> = emptyList()` beside `initialTopic` (additive; its existing tests stay unedited). Nothing is published until Publish; the MQTT port and the write permission rules of the dialog are unchanged. The owner can then play the device and watch the answer arrive in the response stream with the existing stream browser.
- `ui`: the kind card, `MqttRouteFormView`, the edge label, the button on the Migrations screen.

Out: MQTT subscriptions, QoS or retained settings of a route (a route is only a binding; measured: QoS 0, QoS 1 and retained publishes all arrive, a retained one is not marked); another MQTT exchange than `amq.topic` (S-B1: it cannot be read through the management API; the optional hint from subscriber bindings is `M9-10c`); publishing from the planner itself; MQTT 5 correlation data and response topic in the dialog (the dialog has no such fields; only if S-A7 and the owner ask for them); the optional MQTT ticks of a stream pair (`M9-07b`).

## Design notes
The translation is the one place that knows the rule; the existing display helper `StreamInboundRoute.routingKeyToMqttFilter` (it splits on `.` and `/` and drops empty parts) is left alone unless S-A shows it wrong for a key, which is then a small follow-up named in the report. The binding is applied by the existing executor: no new request. "Send a test message" publishes only through the existing `MqttMessagePublisher` behind the existing dialog and gate; the sample-value dialog is a small dialog of the Migrations screen with no broker access. Where the broker is faked: `FakeMqttMessagePublisher` and `FakeTopologyCatalog`; real in the live test.

## Open points
- S-A and S-B are measured (M9-00a). The table and the refusals are in rule A16; the sentence about `amq.topic` stays an assumption for good (S-B1: not readable). The form text is the owner's to approve (review list item 4).
- What this task may rely on (all asserted by the spike classes, RabbitMQ 4.4.0): the translation table of S-A1 (also `devices/+/answer`); that a hand-written key matches exactly what the MQTT subscription of the same filter matches, in a stream and in a quorum queue (S-A2; `sensors/#` also matches `sensors`, `+` matches a one-level topic); that a stream message's `x-routing-key` is the topic with `/` turned to `.` and `x-exchange` the exchange; that QoS 0, QoS 1 and retained publishes arrive.
- What it must NOT claim: that a key always maps back to the typed topic (a dot does not, S-A3); that the app knows the MQTT exchange; that a `#` filter skips `$` topics (the broker delivers `$SYS/...` to `#` too, so the sample-value dialog does not apply the MQTT rule); QoS 2, topic length and non-ASCII topics are not measured.
- The test message check: the header `correlation-id` is a user property and arrives as the application property `correlation-id` on a stream message and as an entry of the headers table on a queue message; MQTT 5 correlation data and a response topic are not offered (the dialog cannot send them). A stream message from MQTT shows `creation-time` and `absolute-expiry-time` as 0 in the Java client: the app's reader already leaves zero out (`StreamMessageMapping.kt:34-35`), and the live test of this task adds one assertion that the reader shows the route (`routingKey`, `exchange`) and the user property under `applicationProperties` and no date. A response topic would show as `reply-to` = `/exchanges/amq.topic/<key with dots>`.
- The display helper `StreamInboundRoute.routingKeyToMqttFilter` drops empty words and splits on `/` too: wrong for `sensors..temp` (the broker's filter keeps the empty level). The planner uses its own function; fixing or retiring the helper is a small follow-up named in this task's report.
- Recognition (A10) keeps `sensors..temp` and any key `toFilter` refuses as an ordinary binding (the outline of 'A binding on amq.topic that is not a plain MQTT route stays a binding' is unchanged).
- The wording of the disabled reason without write permission reuses the existing text of the publish gate.
- Q17 (decided by the owner on 2026-11-15, O14): the header key of the test message is `correlation-id`, an MQTT 5 user property only, editable in the dialog.
- Four scenarios carry `@needs-decision` for wording only (refusals, assumption sentence, sentence under the header; Owner review list of `M9-00a`, items 1 to 5). Build them with the proposed texts and keep them out of the suite until the owner has answered; the other scenarios of this task are unaffected.
- The owner's service may read the standard AMQP `correlation-id` rather than the application property (review list item 8): the test message would then not exercise it. Not a blocker of this task.
- A custom MQTT exchange (S-B2) is the largest risk of this task: a route on `amq.topic` applies without error and routes nothing. The assumption sentence is the whole answer here; `M9-10c` is the optional hint.
