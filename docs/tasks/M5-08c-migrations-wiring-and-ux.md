# M5-08c: desktop wiring and the Migrations screen states

Milestone: M5    Depends on: M5-08a, M5-08b (both merged)    Size: M, delivered in two parts (recommended split below)    Umbrella: `M5-08-real-migration-execution`

## Goal
The desktop app applies migrations for real: the Migrations screen uses the connection's real executor, the folder-backed repository and the history on disk, the profile's own topology control level and virtual host, a native folder chooser and folder opener, and shows every state of the new behaviour clearly. Profile rename and delete keep the history in step and say so when they cannot.

## Why
`MigrationsWindowContent` in `desktopApp/.../Main.kt` (read on main b99c778) still wires a no-op executor, `InMemoryMigrationFileRepository`, `InMemoryMigrationHistoryRepository` and `val controlLevel = ...FULL_CONTROL` (the level is hard-coded: a Read-only profile can apply). `MigrationsViewModel` and the ports from `M5-08a/b` exist but nothing in `desktopApp` uses them; `MigrationsScreen` shows none of the new states. The composition root does not pass the history repository to `ConnectionsViewModel`, so a rename or delete never reaches the history.

## Recommended split (decided by the architect)
Two parts, each a normal loop round (tests first, build, verify, review), one branch each:
- **Part 1 `M5-08c1`: wiring and view-model states** (`core`, `data-rabbit` one line, `desktopApp`): the typed failure kind and progress hook, the new view-model state, the adapters, the composition root and `Main.kt`, the composition-root tests, the manual DMG check. The screen still shows existing banners (errors arrive as `errorMessage`), so a real apply already works end to end for the manual check.
- **Part 2 `M5-08c2`: the screen** (`ui`): the 11 states of the mockup, the Connections banner, all UI tests and test tags.
Reason: part 1 is logic and wiring with real files and a real broker; part 2 is visual and needs the owner's review of the mockup, which comes first anyway. If the coordinator prefers one branch, do the two parts in this order inside it.

## Scope
### Part 1 (`M5-08c1`): wiring and view-model
1. **Typed failure kind (`core` plus one line in `data-rabbit`).** `ActionResult.Failed(reason, kind: FailureKind = FailureKind.Other)` with `enum FailureKind { Other, Conflict }`; `ExecutorReasons.conflict(...)` returns `Conflict`; `MigrationApplyResult.ActionFailed` carries `kind`. The screen never decides "conflict" by reading text.
2. **Progress hook (`core`).** `MigrationRunner.applyPending(..., onAction: (ApplyStep) -> Unit = {})` with `data class ApplyStep(val version: String, val index: Int, val total: Int)`, called before each action is sent (additive, default empty; decision 1 option A).
3. **View-model state (`core`, `MigrationsScreenState`).** Add `applyProgress: ApplyProgress?` (`version`, `index`, `total`), `applyOutcome: ApplyOutcome?` (`sealed`: `Failed(version, index, total, reason)`, `Conflict(version, index, total, reason)`, `NotRecorded(version, reason)`), `unavailableReason: String?` and `canShowFolder: Boolean`. The view model takes a constructor parameter `migrationUnavailableReason: String? = null` (from `StreamSource.migrationUnavailableReason`); a non-null value disables Apply pending and Apply single (import, export and the dry run keep working) and sets `unavailableReason`. `applyPending` and `applySingle` fill `applyProgress` while running and `applyOutcome` when they end (and clear both at the next apply or at `dismissOutcome()`); the old `errorMessage` text "Action 'x' failed on version 'v': ..." is REPLACED by the structured outcome (the tests that pinned the old string change: the replacement text is shown by the screen as "Action k of n failed: <reason>"); `errorMessage` stays for the other messages (blocked reasons, write failures, history not moved). `canShowFolder` is true unless the folder problem is `MISSING` (or no folder). New `fun dismissOutcome()`.
4. **Adapters (`desktopApp`).** `SwingMigrationFolderChooser : MigrationFolderChooser` (`javax.swing.JFileChooser`, `DIRECTORIES_ONLY`, dialog run on the AWT event thread through `SwingUtilities.invokeAndWait` off the composition thread, starts in the current folder or the user's home, returns null on cancel) and `DesktopFolderOpener : FolderOpener` (`java.awt.Desktop.open` on the folder; a file path opens its parent; does nothing when `Desktop.isDesktopSupported()` is false; never throws). Both behind the `core` ports; no new dependency (`java.desktop` ships with the Compose runtime; verified once on the packaged DMG, below).
5. **Wiring (`CompositionRoot.kt`, `Main.kt`).** One `JsonFileMigrationHistoryRepository(history file ~/.caerbannog/migration-history.json, NowProvider { System.currentTimeMillis() })` and the existing `JsonFileAppSettings` (as the `MigrationFolderStore`) are created ONCE in the composition root. The history repository is passed to `ConnectionsViewModel` as `historyKeys` (so rename and delete reach it), and into `MigrationFolderPorts(store, chooser = SwingMigrationFolderChooser, repositoryFor = { FolderMigrationFileRepository(Path.of(it), ...) }, history)`. In `MigrationsWindowContent`: remove the no-op executor, `InMemoryMigrationFileRepository`, `InMemoryMigrationHistoryRepository` and `FULL_CONTROL`; the runner is built from the history repository and `composition.active.source?.migrationExecutor` (a null executor gets a runner whose apply is never reachable because the view model blocks it with `migrationUnavailableReason`); the level is the current connection's profile `topologyControlLevel` (the self-constraint ceiling) combined with the permission result exactly as the Topology screen does, the virtual host is the connection's, the configure permission comes from the permission check; the view model is rebuilt when the connection, the vhost, the permission or the level changes. Folder change keeps the same view model (it reloads through its ports).
6. **Connections (`ui`, `core`).** `SaveConnectionResult.HistoryNotUpdated` and `ConnectionsState.errorMessage` already exist; this part only makes sure the view model keeps `errorMessage` set until the next Save, Delete or selection (it already clears it on success); the screen is part 2.
### Part 2 (`M5-08c2`): the screen (`ui`)
7. **`MigrationsScreen` states** exactly as drawn in `docs/ux/Migrations.dc.html`, section ids in brackets, test tags in the table below. New callbacks on `MigrationsScreen`: `onChooseFolder`, `onChangeFolder`, `onRetry`, `onShowFolder(path)`, `onStartWithEmptyHistory`, `onConfirmEmptyHistory`, `onCancelEmptyHistory`, `onDismissOutcome` (state in, events out; `Main.kt` forwards them to the view model and to the `FolderOpener`).
8. **Connections screen.** `ConnectionsScreen` handles `SaveConnectionResult.HistoryNotUpdated` (every `when` over `SaveConnectionResult`) and shows `ConnectionsState.errorMessage` and the `HistoryNotUpdated` message as the error banner above the action bar of the edit panel (same place as "A connection named ... already exists"), test tag `connections:historyNotUpdatedBanner`; the delete confirmation closes first, the banner follows (`docs/ux/Main.dc.html`, last card).
Out: executor and persistence internals (done), MCP (`M5-09`), the 3.x connection pill, the forced Read-only level and live 3.x reading (`M8-02`), a dry run that compares with the broker (idea).

## Design notes
UI is state in, events out; no file or network code in `ui`; the screen reads `MigrationsScreenState` and calls callbacks. The ports keep `core` free of `java.*` (the chooser and opener adapters are in `desktopApp`). A native dialog runs off the composition thread; a cancelled chooser changes nothing. The composition root owns the single history repository instance (one lock). Failure and conflict wording are screen texts built from structured data (`index`, `total`, `reason`, `kind`), so they can change in one place.
